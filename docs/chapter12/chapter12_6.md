# 12.6 启动限制、权限与异常路径

Activity 启动不是每次都能成功。

系统可能因为权限、后台限制、组件不存在或 Intent 不匹配而拒绝或改变启动行为。

## 本节剧情钩子

不是每张页面启动申请表都会被批准。

有的目标不存在，有的权限不够，有的申请来自后台，有的 Intent 写得含糊不清。系统服务不只是“帮你打开页面”，也负责拦住不合理的启动。

## 本节定位

本节从工程风险角度理解 Activity 启动失败和限制。

## 学习目标

学完本节后，你应该能够：

- 知道 Activity 启动可能失败。
- 理解显式 Intent 和隐式 Intent 的差异。
- 知道后台启动限制会影响页面拉起。
- 能为启动失败增加保护和日志。

## 第一部分：目标组件不存在

如果 Intent 找不到目标 Activity，可能出现异常或启动失败。

例如隐式 Intent 没有任何应用能处理，就需要提前判断。

常见保护方式：

```kotlin
if (intent.resolveActivity(packageManager) != null) {
    startActivity(intent)
}
```

## 第二部分：权限和导出限制

Android 组件有导出和权限规则。

如果你想启动其他应用组件，系统会检查：

- 目标组件是否 exported。
- 是否需要权限。
- 调用方是否满足条件。

这能避免应用随意调用不该访问的组件。

## 第三部分：后台启动限制

现代 Android 对后台拉起 Activity 有更多限制。

这是为了避免应用在用户不知情时突然打断前台体验。

所以有些启动在前台能成功，在后台可能被限制或需要通过通知等方式引导。

## 第四部分：Intent Flag 组合风险

Flag 组合不当也会造成异常体验：

- 返回栈被清空得太多。
- 页面被意外复用。
- 深链入口返回路径混乱。
- 通知点击和普通入口行为不一致。

工程里应该为关键跳转写清预期路径。

## 第五部分：启动日志很重要

遇到页面跳转问题时，建议记录：

- 发起页面。
- 目标页面。
- Intent action / data / flags。
- 当前前后台状态。
- 是否命中异常保护。
- 生命周期日志。

这些信息能帮助你还原启动现场。

## 本节小结

Activity 启动也有失败路径。权限、导出、后台限制、Intent 解析和 Flag 组合都会影响结果。越是核心跳转，越需要明确日志和保护策略，这也是工程经验和 Framework 理解相遇的地方。
