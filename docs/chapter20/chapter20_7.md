# 20.7 稳定性体验问题：误判、漏报、恢复和降级

前面几节讲了 ANR、Crash、tombstone、Watchdog 和系统证据。

但真实项目里，稳定性治理不只是“看懂日志”。

更难的是：

```text
哪些问题会被误判？
哪些问题没有上报？
哪些问题用户感知很糟，但没有 Crash？
哪些问题不能完全避免，只能恢复和降级？
```

这一节把稳定性从“系统机制”带回“工程体验”。

## 本节定位

本节负责回答：

- 为什么没有 Crash 日志也可能是严重问题？
- 为什么后台进程死亡经常被误判成闪退？
- 为什么 ANR、Crash、卡顿和业务失败需要分层治理？
- 恢复、降级和兜底在稳定性里扮演什么角色？
- 如何建立稳定性问题闭环？

## 学习目标

学完本节后，你应该能够：

- 区分 Crash、ANR、低内存回收和业务异常。
- 知道哪些稳定性问题容易漏报。
- 能设计基本的恢复和降级策略。
- 能写稳定性问题分级和回归 checklist。
- 能从单点修复走向治理闭环。

## 第一部分：没有 Crash 不代表没有事故

有些问题不会留下 Java Crash：

```text
后台进程被杀，回来状态丢失
页面卡住但没有达到 ANR 阈值
接口失败后页面空白
图片解码失败显示占位
remote 进程死亡后功能不可用
任务被系统取消但没有恢复
```

这些问题可能不会出现在 Crash 平台，但用户体验一样很差。

所以稳定性指标不能只有：

```text
Crash rate
```

还要关注：

```text
ANR rate
页面成功率
启动成功率
核心流程完成率
白屏率
后台恢复成功率
关键任务成功率
native crash
低内存恢复
```

## 第二部分：常见误判

### 后台回来重建被误判成闪退

用户说：

```text
App 闪了一下回首页了
```

团队可能以为是 Crash。

但证据可能是：

```text
没有崩溃栈
pid 已变化
Application 重新创建
oom_score_adj 之前较高
页面状态没有持久化
```

这更像低内存回收后的恢复问题。

### Native Crash 被误判成 Java Crash

如果只看 Java 崩溃平台，可能看不到 native 崩溃。

用户感知都是闪退，但证据不同：

```text
Java Crash
  -> FATAL EXCEPTION + Java stack

Native Crash
  -> signal + tombstone + native backtrace
```

### 卡顿被误判成 ANR

用户说“卡死了”，可能只是掉帧严重，也可能是真 ANR。

判断需要：

- 是否有 ANR reason。
- 是否有 traces。
- 是否达到系统超时。
- 主线程是否长时间不可响应。

### 业务失败被误判成稳定性问题

例如：

```text
支付失败
登录失败
课程加载失败
```

它们可能没有进程或线程异常，而是业务链路失败。

这类问题要靠业务成功率和错误码监控，而不是 Crash 平台。

## 第三部分：恢复比保活更重要

第 19 章已经强调过，后台进程被杀是系统策略的一部分。

工程上更应该做：

```text
状态持久化
页面恢复
任务续跑
失败重试
用户无损提示
```

而不是沉迷：

```text
如何让进程永远不死
```

稳定性治理里，“恢复”是一等能力。

例如：

| 场景 | 不可靠做法 | 更可靠做法 |
| --- | --- | --- |
| 登录态 | 只存在单例 | 持久化 token + 过期刷新 |
| 草稿 | 只存在 ViewModel | DataStore / Room 持久化 |
| 下载 | 只靠内存任务 | WorkManager / 前台服务 / 断点续传 |
| 页面参数 | 只靠内存缓存 | Intent 参数 + savedState + 持久化 ID |
| remote 进程 | 假设永远存活 | Binder death + 重连 + 降级 |

## 第四部分：降级不是失败，是保护用户体验

有些能力不能保证永远成功。

例如：

- 推荐服务超时。
- 图片服务失败。
- remote 进程死亡。
- native 功能初始化失败。
- 某个实验功能崩溃率升高。

这时可以考虑：

```text
超时
重试
缓存
降级 UI
关闭实验开关
回退到旧实现
提示用户稍后再试
```

降级的目标不是掩盖问题，而是：

```text
在局部能力失败时，保护主流程继续可用
```

## 第五部分：稳定性分级

可以按影响范围分级：

| 级别 | 例子 | 处理策略 |
| --- | --- | --- |
| P0 | 大面积启动崩溃、主流程不可用 | 立即止血、回滚、热修、全员响应 |
| P1 | 核心流程高频 Crash / ANR | 快速定位、灰度修复、重点监控 |
| P2 | 特定页面或设备稳定性问题 | 版本修复、补充回归 |
| P3 | 低频、边缘、可绕过问题 | 排期治理、增加监控 |

分级的价值是让团队知道：

```text
该不该立刻停线？
该不该回滚？
该不该热修？
该不该等下个版本？
```

## 第六部分：稳定性闭环

一个完整闭环应该是：

```text
发现
  -> 分类
      -> 收集证据
          -> 定位根因
              -> 修复
                  -> 回归
                      -> 灰度
                          -> 监控
                              -> 复盘
```

每一步都要有产物：

| 步骤 | 产物 |
| --- | --- |
| 发现 | 监控告警、用户反馈、测试报告 |
| 分类 | ANR / Crash / Native / Low Memory / 业务失败 |
| 证据 | stack、trace、tombstone、logcat、bugreport |
| 定位 | 根因分析 |
| 修复 | PR / patch |
| 回归 | 测试用例 |
| 灰度 | 版本和人群 |
| 监控 | 指标变化 |
| 复盘 | 机制改进 |

这才叫稳定性治理，而不是“修一个 bug”。

## 第七部分：稳定性 checklist

每次修复稳定性问题，可以问：

```text
是否明确问题类型？
是否有原始证据？
是否能解释触发条件？
是否修复根因而不是隐藏异常？
是否增加了回归用例？
是否覆盖低端机、后台、弱网、多进程、横竖屏等条件？
是否需要灰度？
是否需要报警？
是否需要补日志？
是否需要写复盘？
```

这份 checklist 很朴素，但很管用。

## 本节小挑战

### 误判分析题

用户反馈：

```text
从后台回来后，详情页显示空白，过几秒回到首页。
Crash 平台没有记录。
日志显示 pid 已变化。
```

你需要回答：

- 这更像 Crash、ANR，还是后台进程被回收？
- 还需要哪些证据？
- 修复方向是什么？
- 应该监控哪个指标？

## 本节实践任务

### 基础任务

- 给一个已有问题写稳定性分类。
- 为一个页面补充启动成功率或加载成功率日志。
- 为后台恢复路径增加 pid 变化记录。

### 进阶任务

- 写一份稳定性问题分级标准。
- 写一份稳定性修复 checklist。
- 为 remote 进程能力设计 Binder death 降级方案。

## 本节小结

稳定性治理不是追求“永远不出错”。

更现实的目标是：

```text
问题能被发现
证据能被收集
根因能被定位
用户能被保护
修复能被验证
经验能被沉淀
```

这也是资深工程师在复杂系统里真正创造价值的地方。
