# 26.6 用证据链完成一次事故诊断

终章项目必须有一次完整事故诊断。

不是为了制造问题。

而是为了训练一种资深工程师非常重要的能力：

```text
把混乱现场变成可以推理的证据链。
```

## 本节先记住三句话

```text
没有证据的判断，只是猜测。
只有单份证据的判断，容易误判。
能串起现象、时间、线程、状态和修复前后对比，才叫诊断。
```

## 事故剧本：课程详情偶尔卡住

假设用户反馈：

```text
点击课程详情后，有时页面卡住一两秒，偶尔还会出现无响应提示。
```

这句话不能直接得出结论。

你不能立刻说：

```text
应该是网络慢。
应该是 Compose 重组太多。
应该是数据库问题。
应该是系统问题。
```

正确做法是先把问题变成可诊断对象。

## 第一步：定义现象

先写清楚：

```text
发生页面：课程首页 -> 课程详情
用户动作：点击课程卡片
问题表现：详情页 loading 停留 1 到 2 秒，偶现卡住
影响范围：部分设备、部分章节、非每次复现
版本信息：appVersion、buildType、commit、设备系统版本
```

如果现象不清楚，后面的证据都会漂。

## 第二步：建立时间线

用 `traceId` 串起事件：

```text
[course-open-1024] 10:01:12.120 click course card
[course-open-1024] 10:01:12.130 navigate detail
[course-open-1024] 10:01:12.146 load local cache start
[course-open-1024] 10:01:13.420 local cache end
[course-open-1024] 10:01:13.450 compose content visible
```

这条时间线已经透露出一个线索：

```text
本地缓存读取耗时 1.2 秒。
```

但还不能立刻定案。

因为你还要确认：

```text
这 1.2 秒发生在哪个线程？
是否阻塞主线程？
是否同时存在 Binder 等待？
是否只是日志时间不准？
是否有 GC、锁等待或磁盘 I/O？
```

## 第三步：收集证据

建议至少收集：

| 证据 | 说明 |
| --- | --- |
| 结构化日志 | 确认业务事件顺序和 traceId |
| logcat | 查看异常、主线程警告、系统限制提示 |
| Perfetto | 查看主线程、Binder、I/O、调度和帧时间线 |
| gfxinfo | 查看是否出现明显掉帧 |
| dumpsys activity | 查看 Activity / Task 状态 |
| dumpsys meminfo | 查看内存压力和 GC 线索 |
| WorkManager 状态 | 排除后台任务影响 |

如果只是本地 Demo，可以先用页面模拟这些证据。

但文档和报告里要写清楚每份证据能说明什么。

## 第四步：提出假设

可以提出多个假设：

| 假设 | 需要什么证据支持 |
| --- | --- |
| 主线程做了磁盘 I/O | Perfetto 中主线程出现长时间 I/O 或方法耗时 |
| 数据库查询过慢 | query 开始结束日志、simpleperf 或 trace section |
| Compose 重组过重 | 重组计数、帧耗时、UI 状态更新频率 |
| Binder 等待 | Perfetto 中主线程等待 Binder reply |
| 内存抖动 | meminfo、GC 日志、分配峰值 |

资深工程师不会只找支持自己想法的证据。

还要找反证。

例如：

```text
如果主线程没有被阻塞，那 ANR 假设就要调整。
如果本地缓存很快，那网络或渲染路径要继续检查。
如果只有 release 版本慢，要检查 R8、资源、日志和构建配置差异。
```

## 第五步：定位根因

假设最终发现：

```text
CourseDetailViewModel 初始化时在主线程读取了大段本地 JSON。
读取后又同步解析并构造了过大的 UI State。
导致点击后主线程连续忙碌超过 1 秒，部分低端设备触发明显卡顿。
```

根因描述要包含三层：

```text
直接原因
  -> 主线程执行重 I/O 和解析

触发条件
  -> 某些章节内容较大，本地缓存命中时同步读取

治理缺口
  -> 没有主线程 I/O 检查，没有详情页点击耗时基线，没有低端设备回归
```

这样才不是简单地说“代码写错了”。

## 第六步：修复与回归

修复方案可以是：

```text
把本地读取切到 Dispatchers.IO
把大对象解析移动到后台线程
对 UI State 做分段加载
增加 loading / skeleton 体验
给详情页打开链路增加 trace section
把点击到内容可见耗时纳入治理基线
```

回归证据要写成前后对比：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 点击到内容可见 | 1320ms | 240ms |
| 主线程最长连续忙碌 | 1180ms | 32ms |
| 最大帧耗时 | 96ms | 22ms |
| ANR / 卡死反馈 | 偶现 | 未复现 |

这张表比“已优化”更有说服力。

## 事故报告模板

毕业项目可以内置一份事故诊断报告：

```text
事故标题：
影响版本：
影响范围：
复现路径：

用户现象：
关键时间线：
证据列表：
  - logcat：
  - Perfetto：
  - dumpsys：
  - gfxinfo：
  - meminfo：

排除项：
根因判断：
修复方案：
回归证据：
治理动作：
```

其中“排除项”很重要。

它证明你不是只靠一个线索就下结论。

## 本节复盘

本节我们完成了一次终章事故诊断：

```text
先定义现象。
再建立时间线。
再收集多份证据。
再提出假设和反证。
再定位根因。
最后用修复前后指标证明结果。
```

下一节，我们会把诊断能力继续往前推：上线前，如何用工程治理尽量拦住问题。
