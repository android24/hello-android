# 26.1 为什么需要一个毕业项目

从第 1 章到第 25 章，我们已经走完了一条很长的 Android 路线。

你写过页面，处理过状态，接过网络，落过本地数据，拆过架构，做过测试，也沿着 Framework 继续向下追问：

```text
Activity 为什么能启动
窗口为什么能显示
触摸为什么能分发
一帧为什么能刷新
资源为什么能匹配
代码为什么能加载
进程为什么会被创建和回收
ANR、Crash 和 bugreport 为什么能留下事故现场
后台、存储、安全和观测工具为什么都不是孤立知识
大型工程为什么需要治理
```

第 26 章要做的事情，是把这些能力收束成一个完整作品。

它不是再多讲一个知识点。

它是一次毕业项目。

## 本节先记住三句话

```text
学完课程，不等于拥有工程能力；能把知识组织进一个项目，才算真正上手。
资深工程师不是记住更多名词，而是能把需求、架构、系统链路、证据和治理连成闭环。
毕业项目不是炫技，而是证明自己能负责一个真实 Android 工程。
```

## 本章定位

第 26 章是整门课程的终章。

它的角色可以理解为：

```text
第 1 到 9 章
  -> 让你会写一个 App

第 10 到 24 章
  -> 让你能读懂 App 背后的系统链路

第 25 章
  -> 让你知道大型工程如何长期运转

第 26 章
  -> 让你把这些能力放进一个可展示、可复盘、可扩展的毕业项目
```

如果前面的章节像一块块拼图，第 26 章就是把拼图铺到桌面上，看看它们能不能组成一张完整地图。

## 前 25 章能力如何进入毕业项目

终章项目不是凭空出现的。

它应该把前面每个阶段的能力重新安放到一个真实项目里：

| 课程阶段 | 毕业项目中的落点 |
| --- | --- |
| 第 1 到 3 章：Kotlin、Compose、Activity 与导航 | 完成课程首页、章节列表、详情页、状态保存和页面跳转 |
| 第 4 到 6 章：网络、本地数据、协程、Flow 与后台任务 | 完成课程数据加载、学习进度保存、离线任务和后台同步模拟 |
| 第 5 到 8 章：架构、Hilt、模块化、测试与质量 | 拆出 feature / domain / data / core，建立可测试的业务链路 |
| 第 9 章：性能与稳定性 | 为冷启动、详情打开、列表滑动和异常场景建立观察入口 |
| 第 10 到 15 章：Framework、Binder、Activity、Window、Input、渲染 | 从一次课程点击追到系统服务、窗口、输入和一帧刷新链路 |
| 第 16 到 18 章：PMS、资源、ClassLoader、ART 与动态加载 | 解释安装包、组件、资源匹配、混淆、加载和动态能力的工程边界 |
| 第 19 到 20 章：进程、内存、ANR、Crash 与稳定性诊断 | 模拟卡顿、崩溃、进程恢复和事故证据链 |
| 第 21 到 23 章：后台、存储、安全、权限、签名与 AppOps | 完成后台调度、离线存储、权限拒绝、安全检查和签名治理 |
| 第 24 到 25 章：观测工具与大型工程治理 | 输出诊断报告、发布门禁、风险评分、灰度策略和复盘材料 |

如果读者能在毕业项目里指出这些对应关系，他就不只是“学过这些章节”，而是开始把知识变成工程结构。

## 贯穿案例：Hello Android Capstone

本章建议做一个毕业项目：

```text
Hello Android Capstone
```

它不是一个复杂到失控的大项目，而是一个“足够小、但链路完整”的课程学习 App。

它至少包含：

```text
课程首页
章节列表
课程详情
学习进度
收藏与笔记
离线下载模拟
后台同步模拟
权限与存储体验
性能观察入口
事故诊断入口
工程治理入口
```

这个 App 的价值不在于业务多复杂，而在于它能承载整门课程的关键能力。

例如：

```text
点击一门课程
  -> 进入详情页
      -> 读取本地缓存
          -> 必要时触发网络刷新
              -> 更新学习进度
                  -> 写入 DataStore / Room
                      -> 发起后台同步
                          -> 记录 traceId
                              -> 观察帧率、日志、权限和存储行为
                                  -> 输出一次工程诊断报告
```

这才是终章项目应该训练的东西：不是把所有技术堆上去，而是把它们串起来。

## 为什么不能只停在章节 Demo

前面的每个章节 Demo 都有明确边界。

第 14 章关注输入事件，第 17 章关注资源系统，第 20 章关注稳定性诊断，第 24 章关注证据链，第 25 章关注工程治理。

但真实工程从来不会这样贴心地把问题分好类。

真实问题通常长这样：

```text
用户点击课程详情后偶尔卡住。
日志里看不到明显异常。
后台同步有时没有执行。
某些机型图片资源显示模糊。
release 后 crash 堆栈被混淆。
线上版本出现问题，但 mapping 没有归档。
新模块直接依赖 data 实现，绕过了 domain contract。
```

这些问题会同时涉及：

```text
UI 状态
生命周期
协程和线程
本地存储
后台任务
资源匹配
权限边界
性能观测
稳定性诊断
工程治理
```

所以终章项目必须训练综合能力。

## 资深 Android 工程师要证明什么

本章不是为了证明你“看过很多内容”。

而是证明你具备四类能力：

| 能力 | 你需要能做到什么 |
| --- | --- |
| 需求建模 | 能把业务需求拆成页面、状态、数据、异常和边界条件 |
| 架构设计 | 能设计模块边界、依赖方向、数据流和可测试结构 |
| 系统理解 | 能从用户操作追到 Activity、Window、Input、Render、PMS、Resources、ClassLoader、进程和稳定性链路 |
| 工程闭环 | 能用证据定位问题，用治理机制降低问题再次出现的概率 |

如果你只能写功能，还不够。

如果你只能讲源码，也不够。

如果你能把功能、源码、证据和治理连在一起，才开始接近资深工程师的工作方式。

## 本章交付物

完成第 26 章后，建议至少产出这些材料：

```text
一个可运行的毕业项目 App
一份项目 README
一张模块边界图
一份关键链路分析文档
一份性能 / 稳定性 / 安全 / 存储检查报告
一份事故诊断证据链报告
一份发版治理评审报告
一份终章答辩材料
```

这些材料比“我学完了”更有说服力。

它们可以让别人看到：

```text
你如何拆需求
你如何组织代码
你如何理解系统
你如何定位问题
你如何保护工程长期可维护
```

## 本章学习方式

建议按这样的节奏推进：

```text
先确定毕业项目需求
  -> 再设计模块架构
      -> 再实现核心链路
          -> 再补齐系统观察点
              -> 再模拟事故
                  -> 再输出治理报告
                      -> 最后完成答辩材料
```

第 26 章最重要的不是“快点写完”。

而是每完成一个功能，都问自己：

```text
这个功能在架构中属于哪一层？
它依赖了谁？
它的数据从哪里来？
失败时会发生什么？
它经过了哪些系统机制？
出了问题我能拿到什么证据？
上线前如何发现风险？
```

如果你能习惯这样思考，课程真正想训练的东西就已经开始发生了。

## 本节复盘

本节我们明确了第 26 章的定位：

```text
它是整门课程的毕业项目。
它不再新增一条孤立知识线，而是整合前 25 章。

它要能把每个阶段的知识重新映射到一个真实项目里。
```
