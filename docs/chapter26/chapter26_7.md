# 26.7 用工程治理完成一次发版评审

如果第 26 章只做到事故诊断，还不够。

资深工程师不仅要会救火，还要努力减少起火的机会。

所以终章项目还要完成一次发版评审。

## 本节先记住三句话

```text
发布不是点击一个按钮，而是把风险带到用户面前之前的最后检查。
治理不是让团队变慢，而是让高风险问题不要偷偷穿过流程。
一个成熟工程的价值，体现在它能不能持续稳定地交付。
```

## 发版评审对象

假设毕业项目准备发布：

```text
Hello Android Capstone 1.0.0
```

这次发版包含：

```text
课程首页
章节详情
学习进度
收藏与笔记
离线任务模拟
诊断工作台
治理报告
终章答辩页面
```

发版前不能只问：

```text
功能测了吗？
```

还要问：

```text
模块边界有没有破？
release 配置有没有变？
权限有没有新增？
mapping 有没有归档？
性能基线有没有退化？
稳定性风险有没有覆盖？
监控指标有没有接上？
回滚方案有没有写清楚？
```

## 发布门禁

建议把检查项分成四类：

| 等级 | 含义 | 示例 |
| --- | --- | --- |
| P0 | 绝对阻塞 | release 构建失败、签名错误、核心路径不可用、mapping 缺失 |
| P1 | 高风险 | crash / ANR 指标恶化、权限异常新增、关键性能退化 |
| P2 | 可控风险 | 构建耗时回退、非核心页面体验问题、局部技术债 |
| P3 | 观察项 | 文档不完整、命名不清、后续优化项 |

注意：

```text
健康分不能覆盖 P0。
```

例如：

```text
总分 92 分，但 release mapping 没有归档。
```

结论仍然应该是：

```text
暂停发布。
```

因为线上 crash 发生后无法还原堆栈，这不是平均分能抵消的问题。

## 评审清单

毕业项目可以提供这样的发版清单：

| 检查项 | 通过标准 |
| --- | --- |
| release 构建 | release variant 可构建、可安装、可启动 |
| 签名 | 使用正确 keystore，版本升级签名一致 |
| R8 / 混淆 | 关键反射、序列化、DI、JNI keep 规则正确 |
| mapping / symbols | mapping、native symbols、commit、buildId 已归档 |
| 权限变化 | 新增权限有理由，拒绝后有降级体验 |
| exported 组件 | 暴露组件有明确目的和保护条件 |
| 资源变化 | 包体积、图片密度、语言资源、主题资源无异常 |
| 性能基线 | 冷启动、详情打开、列表滑动、后台任务指标无明显退化 |
| 稳定性 | 核心路径异常可捕获，事故报告模板完整 |
| 监控告警 | crash、ANR、启动、卡顿、核心业务指标可观察 |
| 回滚方案 | 灰度比例、停止条件、回滚方式明确 |

这张表应该进入 Demo 的治理工作台。

## 毕业项目验收清单

发版评审之前，先给毕业项目做一次总验收。

可以使用这份清单：

| 验收项 | 通过标准 |
| --- | --- |
| App 可运行 | Android Studio 可以打开工程，`app` 模块可以安装和启动 |
| 主路径完整 | 首页、列表、详情、进度、收藏、笔记、离线任务能串起来 |
| 状态可恢复 | 旋转屏幕、进程恢复或重新进入后，关键状态不丢失 |
| 模块边界清晰 | feature、domain、data、core 职责明确，依赖方向可解释 |
| traceId 可追踪 | 关键用户操作能在日志、诊断页面和报告中串起来 |
| 事故可模拟 | 至少能模拟卡顿、任务失败、权限拒绝或资源异常中的三类 |
| 证据可阅读 | 事故页面能展示时间线、证据、假设、排除项和修复建议 |
| 风险可决策 | 治理工作台能区分 P0、P1、P2、P3，并给出发布建议 |
| README 可交付 | 新读者能在 5 分钟内理解项目定位、运行方式和学习任务 |

这份清单的意义是把“我觉得差不多了”变成“它确实可以被验收”。

## 灰度策略

毕业项目可以模拟三种发布策略：

| 策略 | 适合场景 | 默认动作 |
| --- | --- | --- |
| 保守发布 | 核心链路、权限、安全、支付类功能 | P1 也先修复再发 |
| 平衡灰度 | 普通功能迭代 | P1 允许小流量灰度，但要有监控 |
| 快速实验 | 内部实验、低风险 UI 调整 | P2 / P3 可记录后发布 |

但无论哪种策略：

```text
P0 都不能发布。
```

治理的底线要清楚。

## 监控基线

发版评审不能只看发布前。

还要定义发布后的观察窗口：

```text
1% 灰度观察 2 小时
5% 灰度观察 6 小时
20% 灰度观察 24 小时
全量前复核核心指标
```

建议观察：

```text
crash-free
ANR rate
冷启动 P50 / P90 / P95
详情页打开耗时
列表帧耗时
后台同步成功率
离线任务失败率
权限拒绝率
核心路径完成率
```

这些指标可以先在 Demo 中用 fake 数据模拟。

关键是让学习者理解：上线不是结束，而是观察的开始。

## 治理报告

终章项目最后要输出一份发版评审报告：

```text
版本：Hello Android Capstone 1.0.0
构建号：
Git commit：
检查时间：

发布结论：
  -> 可以发布 / 暂停发布 / 小流量灰度 / 修复后再评审

阻塞问题：
  -> P0 / P1 风险、证据和负责人

可延期问题：
  -> P2 / P3 技术债、影响范围、计划时间

模块边界：
构建效率：
依赖与资源：
权限与安全：
性能与稳定性：
监控与回滚：

最终决策：
```

报告要能支撑一句明确结论：

```text
我们为什么敢发，或者为什么不能发。
```

## 趣味任务：你是发版守门人

给毕业项目设计三张事故卡：

```text
mapping 未归档，但功能测试全部通过。
新增一个 exported Activity，但没有权限保护。
详情页打开 P95 从 300ms 退化到 1200ms。
```

然后判断：

```text
是否阻塞发布？
是否允许灰度？
需要谁修？
需要什么证据证明修复完成？
```

这个任务的关键不是答案唯一，而是要能讲清楚判断依据。

## 本节复盘

本节我们完成了一次发版评审：

```text
发布要有门禁。
门禁要区分 P0、P1、P2、P3。
健康分不能掩盖底线问题。
毕业项目要有可执行的验收清单。
灰度要绑定监控基线。
最终报告要给出清晰发布决策。
```
