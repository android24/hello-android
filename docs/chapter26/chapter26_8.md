# 26.8 终章答辩：如何证明自己具备资深 Android 工程师能力

第 26 章最后一节，也是整门课程的最后一节。

现在要回答一个很重要的问题：

```text
我如何证明自己已经不只是“会写 Android”，而是具备资深 Android 工程师的能力？
```

答案不是背一组源码类名。

答案是一份能被别人阅读、运行、追问和复盘的毕业作品。

## 本节先记住三句话

```text
资深能力不是自称出来的，是通过作品、证据和判断力呈现出来的。
好的答辩不是展示所有细节，而是把关键选择讲清楚。
终章不是结束，而是你开始独立构建 Android 知识体系的入口。
```

## 答辩材料应该包含什么

建议准备这些内容：

```text
项目 README
功能演示路径
模块架构说明
关键业务链路说明
Framework 链路分析
性能 / 稳定性 / 安全 / 存储检查报告
事故诊断证据链报告
发版治理评审报告
后续演进计划
```

这些材料对应的不是形式，而是能力。

| 材料 | 证明的能力 |
| --- | --- |
| README | 能让别人快速理解和运行项目 |
| 功能演示 | 能交付一个完整可用体验 |
| 模块架构 | 能控制复杂度和依赖方向 |
| 关键链路 | 能把业务行为讲成工程链路 |
| Framework 分析 | 能从 App 行为追到系统机制 |
| 检查报告 | 能用指标和边界评估质量 |
| 事故诊断 | 能用证据定位问题 |
| 发版评审 | 能把风险管理放进交付流程 |
| 演进计划 | 能看到项目下一步应该怎么长 |

## 终章 Demo 任务板

为了让读者真正做完毕业项目，Demo 可以内置一张任务板。

本章配套示例工程位于：

```text
examples/26-senior-android-capstone/
```

它不是一个单点功能 Demo，而是一张毕业项目控制台：课程主路径、阶段路线、任务板、Framework 因果链、事故剧本、证据时间线、能力雷达、发布门禁和答辩报告都会在同一个页面里出现。

为了让它真正承担终章回顾的作用，Demo 还应该提供“课程回顾地图”和“动手回顾实验室”：前者把第 1 到第 26 章重新串成能力路线，后者把每个阶段变成可点击、可修改、可验收的实践任务。这样读者不是被动看完终章，而是在最后一章把前面的知识重新做一遍。

精品版 Demo 还应该让反馈动起来：任务状态、动手证据、事故剧本和发布门禁会共同影响能力雷达与毕业结论。读者修复一个 P0、补齐一个证据、完成一次事故诊断后，页面应该立刻给出新的评分、短板和答辩建议。

为了避免终章 Demo 只停留在“页面上模拟工程”，它还应该接入少量真实工程信号：

```text
Trace.beginSection("CapstoneRunTrace")
Trace.beginSection("CapstoneIncident:<scenarioId>")
Logcat Tag：HelloCapstone
SystemClock.elapsedRealtime()
BuildConfig.BUILD_PROFILE
```

这些点不复杂，却很关键。

因为它们让读者知道：一次点击不是只在 UI 上变化，它还可以进入 trace；一次事故不是只在文案里出现，它还可以写入 Logcat；一次报告不是只写结论，它还应该带上 appId、version、build profile 和本次会话时间。

资深工程师的表达，往往就从这种细节开始变得可信。

终章 Demo 还可以加入一个“毕业挑战模式”。

它把最后一章拆成 6 个关卡：

```text
选定回顾路线
跑一次真实点击链路
注入一次事故
补一条动手证据
修复 P0 门禁
生成答辩材料
```

挑战模式的意义不是把课程游戏化得很热闹，而是给读者一条明确的完成路线。

没有这条路线，读者很容易只是把页面从上到下看一遍；有了这条路线，读者会知道：自己现在不是在浏览内容，而是在逐步证明能力。

任务板不只是待办列表，它应该像一条毕业路线：

| 任务 | 目标 | 通关标准 |
| --- | --- | --- |
| 任务 1：跑通课程主路径 | 首页、列表、详情、进度形成闭环 | 能从首页进入详情，并标记一个章节为已完成 |
| 任务 2：接入本地状态 | 收藏、笔记、学习进度可保存 | 重新进入 App 后关键状态仍在 |
| 任务 3：加入 traceId | 关键操作可以被串起来 | 点击详情、离线任务、发布检查都有 traceId |
| 任务 4：追踪 Framework 链路 | 把一次点击讲清楚 | 页面能展示 Input、ActivityThread、Window、Choreographer、RenderThread 等节点 |
| 任务 5：模拟一次卡顿事故 | 制造并观察主线程阻塞 | 能看到现象、时间线、风险提示和修复建议 |
| 任务 6：模拟一次后台失败 | 观察任务调度与重试 | 能区分条件不满足、执行失败和系统限制 |
| 任务 7：完成安全与存储检查 | 检查权限、日志、组件和存储位置 | 能指出至少三个风险点或通过项 |
| 任务 8：生成事故报告 | 把诊断过程文档化 | 报告包含现象、证据、假设、排除项、根因和回归方式 |
| 任务 9：完成发版评审 | 判断版本能不能发布 | 能根据 P0 到 P3 风险给出发布结论 |
| 任务 10：完成终章答辩 | 展示完整工程能力 | 能用 10 到 15 分钟讲清项目目标、架构、链路、诊断和治理 |

任务板可以设计成可点击状态：

```text
未开始
进行中
已完成
需要补证据
```

其中“需要补证据”非常重要。

它提醒读者：工程里很多事情不是没做，而是做了却无法证明。

更进一步，事故剧本不应该只是替换一段文字。

当读者注入“详情打开卡顿”时，事故诊断任务和 Framework 因果链任务应该被自动推进；当读者注入“权限拒绝后导出失败”时，安全检查和存储任务应该被自动推进；当读者注入“签名证书指纹异常”时，安全检查和发版治理任务应该被自动推进。

这背后的课程含义是：

```text
事故会改变工程优先级。
证据会改变任务状态。
门禁会改变发布结论。
```

如果 Demo 能让这三件事动起来，读者才会真正感受到工程治理不是静态文档，而是一套会影响决策的系统。

最后，还应该给 Demo 加一条“操作记录”。

它记录最近的关键动作：

```text
切换阶段
选择章节
追踪点击链路
选择事故剧本
注入事故
推进任务
推进动手实验
切换发布门禁
生成答辩报告
```

这条记录很朴素，却能让毕业报告更可信。

因为报告不再只是说“当前状态是什么”，而是能说明“我是如何一步步走到这个状态的”。

真实工程验收也一样。一次发布评审、一场事故复盘、一份性能报告，都不只看最终结论，还要看过程证据。

## 终章项目能力雷达

毕业项目可以用六个维度做自评。

这张表不只是打分工具，更像一面镜子：它能告诉你自己现在更像功能开发者、架构维护者、系统问题诊断者，还是已经开始具备工程负责人的视角。

| 维度 | 低分表现 | 高分表现 |
| --- | --- | --- |
| 功能交付 | 页面能打开，但主路径不完整，异常状态缺失 | 主路径完整，状态可恢复，失败有反馈 |
| 架构设计 | 代码堆在 `app`，依赖方向说不清 | feature / domain / data / core 边界清晰，可测试、可替换 |
| Framework 理解 | 只会说几个类名，不能解释现象 | 能从一次点击追到输入、窗口、主线程、渲染和系统服务 |
| 诊断能力 | 出问题靠猜，日志和指标散落 | 能用 traceId、日志、Perfetto、dumpsys 和报告串起证据链 |
| 工程治理 | 发布靠人工记忆，风险没有分级 | 有门禁、风险等级、监控基线、回滚策略和复盘机制 |
| 表达答辩 | 只讲代码细节，听众难以跟上 | 能从问题出发，讲清目标、取舍、证据和结论 |

建议自评时不要只看总分。

可以给每个维度写一句短评：

```text
功能交付：主路径完整，但离线失败态还不够细。
架构设计：模块方向清楚，但 core-observability 还需要更严格边界。
Framework 理解：能讲点击到渲染，但对后台调度链路还不够熟。
诊断能力：有 traceId 和事故报告，但缺少真实 Perfetto 证据。
工程治理：有发布门禁，但 CI 自动化还没有接入。
表达答辩：能讲项目目标，但需要减少源码细节堆叠。
```

这种自评比单纯打 85 分更有价值。

它会告诉你下一步该补哪里。

## 终章答辩 Rubric

除了五个评分维度，还可以给读者一张更容易自检的 Rubric。

这张 Rubric 不看“你写了多少代码”，而看“你能被追问到哪一层”。

| 分数 | 标准 | 追问方式 |
| --- | --- | --- |
| 60 分 | 主路径可以运行 | 你能不能完整演示首页、章节、详情和进度变化？ |
| 70 分 | 架构可以解释 | 你能不能说清 feature / domain / data / core 的职责和依赖方向？ |
| 80 分 | Framework 因果链可以讲清 | 你能不能把一次点击追到 Input、ViewRootImpl、ActivityThread 和 Choreographer？ |
| 90 分 | 事故诊断和发布门禁形成闭环 | 你能不能用证据解释事故，并判断 P0 / P1 是否阻塞发布？ |
| 95 分以上 | 具备持续演进和治理意识 | 你能不能提出 CI 门禁、真实 Perfetto、Baseline Profile、DataStore 持久化等后续方案？ |

这里有一个很实用的判断：

```text
60 分看功能。
70 分看边界。
80 分看系统理解。
90 分看事故和发布判断。
95 分以上看持续演进。
```

如果读者只能演示功能，却不能解释为什么这样拆模块，他大概还停在 60 到 70 分之间。

如果读者能讲架构，却不能把卡顿、ANR、资源错乱、签名异常放进证据链，他还没真正进入 90 分区间。

如果读者能说明当前做得不完美，并且能给出下一步最值得投入的工程方案，那反而说明他开始具备资深工程师的判断力。

## 项目 README 推荐结构

毕业项目 README 可以这样组织：

```text
# Hello Android Capstone

## 项目定位
## 功能预览
## 运行环境
## 模块结构
## 核心链路
## Framework 观察点
## 性能与稳定性实验
## 安全与存储检查
## 工程治理工作台
## 事故诊断报告
## 发版评审报告
## 学习任务
## 后续演进
```

README 不是堆文字。

它要让第一次打开项目的人在 5 分钟内知道：

```text
这个项目解决什么问题
怎么运行
怎么体验主路径
哪里能看到课程重点
哪里能继续修改和练习
```

## 答辩路线

建议按这个顺序讲：

```text
1. 先讲项目目标
2. 再演示用户主路径
3. 再讲模块架构
4. 再追一条 Framework 链路
5. 再展示一次挑战模式进度
6. 再展示一次事故诊断
7. 再展示一次发版治理
8. 最后讲后续演进
```

不要一上来就讲源码细节。

答辩最怕进入这种状态：

```text
这里有个类。
那里有个方法。
这个地方调用了一下那个地方。
```

听众很快会迷路。

更好的方式是从问题出发：

```text
这个项目要解决什么问题？
我为什么这样拆模块？
一次点击会经过哪些链路？
如果它卡住，我怎么拿证据？
如果它要上线，我怎么判断能不能发？
```

这样讲，别人会看到你的思考，而不只是看到代码。

## 优秀答辩示例大纲

一场终章答辩建议控制在 10 到 15 分钟。

可以这样安排：

| 时间 | 内容 | 重点 |
| --- | --- | --- |
| 1 分钟 | 项目定位 | 说明它是课程学习 App，也是工程能力展示台 |
| 2 分钟 | 主路径演示 | 从首页到详情、进度、收藏、离线任务跑一遍 |
| 3 分钟 | 架构设计 | 讲清 feature / domain / data / core 的职责和依赖方向 |
| 3 分钟 | Framework 链路 | 选择一次点击，追到 Input、ActivityThread、Window、Choreographer 和渲染链路 |
| 3 分钟 | 事故诊断 | 展示一个卡顿或后台失败剧本，说明现象、证据、假设、根因和回归 |
| 2 分钟 | 发版治理 | 展示发布门禁、风险等级、监控基线和最终发布结论 |
| 1 分钟 | 后续演进 | 说明下一步最值得投入的方向，而不是列一堆愿望 |

答辩时要避免平均用力。

如果时间不够，优先讲：

```text
项目目标
主路径
一个关键架构取舍
一条 Framework 因果链
一次证据链诊断
一个发布决策
```

这六件事讲清楚，听众就能判断你是否真的完成了终章项目。

## 评分标准

可以用这张表给毕业项目评分：

| 维度 | 分值 | 标准 |
| --- | --- | --- |
| 功能完整性 | 20 | 主路径可运行，状态可保存，异常有反馈 |
| 架构清晰度 | 20 | 模块职责明确，依赖方向合理，核心逻辑可测试 |
| Framework 理解 | 20 | 能把至少一条用户操作追到系统链路 |
| 质量与诊断 | 20 | 有性能、稳定性、安全、存储检查和事故证据链 |
| 工程治理 | 20 | 有发布门禁、风险等级、监控基线和复盘机制 |

总分不是唯一目标。

更重要的是找出短板：

```text
功能能跑，但没有证据。
源码能讲，但项目不可维护。
架构漂亮，但用户路径不完整。
治理表很多，但没有真实判断。
```

这些短板，就是下一轮成长路线。

## 答辩前最终验收

真正答辩前，请再做一次最终检查：

```text
项目是否能独立运行
主路径是否能完整演示
模块边界是否能讲清楚
至少一条 Framework 链路是否能讲到关键类和系统服务
至少一次事故是否有完整证据链
至少一次发版评审是否有明确结论
README 是否能让陌生读者快速理解项目
后续演进是否有优先级，而不是愿望清单
```

如果这些问题都能回答，第 26 章就不是“读完了”，而是真的完成了一次毕业。

## 终章自测问题

完成项目后，请回答这些问题：

```text
1. 如果首页变慢，你先看哪三份证据？
2. 如果详情页偶现打不开，你如何区分导航问题、数据问题和系统限制？
3. 如果后台同步丢失，你如何判断是代码没执行，还是系统调度限制？
4. 如果某个资源在夜间模式显示错乱，你会从 R、resources.arsc、Theme、Configuration 哪些位置排查？
5. 如果 release 版本 crash 堆栈不可读，问题出在哪个治理环节？
6. 如果新模块直接依赖 data 实现，你会如何调整模块边界？
7. 如果权限被拒绝，产品还要求继续完成核心路径，你如何设计降级体验？
8. 如果要把项目交给新人维护，哪些文档和自动化检查最重要？
```

这些问题比“记住某个 API”更接近真实工作。

## 后续演进方向

课程到第 26 章结束，但 Android 学习不会结束。

毕业项目后可以继续演进：

```text
接入真实后端
接入真实 Perfetto trace 导入分析
接入真实 crash / ANR 上报
加入 Baseline Profile
加入多模块构建性能统计
加入插件化实验分支
加入 Compose 性能专项实验
加入 CI 门禁和自动报告
加入更多 AOSP 源码阅读笔记
```

这些不是第 26 章必须完成的内容。

它们是你从课程走向真实工程之后，可以继续深挖的方向。

## 给读者的一段话

如果你一路学到这里，已经不只是“跟着写了几个 Demo”。

你已经完成了一次从应用层到系统层，再从系统层回到工程治理的完整往返。

Android 很大。

大到一个人永远不可能一次性掌握全部细节。

但你已经有了一条路线：

```text
遇到功能问题，回到状态和数据流。
遇到架构问题，回到边界和依赖方向。
遇到系统问题，回到 Framework 链路。
遇到线上问题，回到证据链。
遇到团队问题，回到治理机制。
```

这条路线，比任何单个知识点都重要。

## 本节复盘

本节我们完成了整门课程的终章答辩设计：

```text
毕业项目要有作品、有文档、有链路、有证据、有治理。
终章 Demo 要有任务板，让读者知道自己离毕业还差哪一步。
能力雷达帮助读者看见短板，而不只是得到一个总分。
答辩要从问题出发，而不是从类名出发。
资深 Android 工程师能力，需要通过完整交付来证明。
```

至此，《从零开始的 Android 全栈开发课程》的主线课程来到终点。

但真正的 Android 旅程，才刚刚开始。
