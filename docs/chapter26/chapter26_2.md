# 26.2 毕业项目需求：做一个可诊断、可治理的课程 App

毕业项目不能只说“我要做一个 App”。

这句话太空了。

第 26 章的毕业项目需要更具体：

```text
做一个可运行、可观察、可诊断、可治理的课程学习 App。
```

它既要有正常用户能感知的功能，也要有工程师能观察和复盘的内部链路。

## 本节先记住三句话

```text
需求不是功能清单，而是用户目标、系统边界和异常场景的组合。
毕业项目要小而完整，不要大而空。
每个功能都要留下可观察入口，否则它只是“看起来能用”。
```

## 项目名称

建议命名为：

```text
Hello Android Capstone
```

中文可以叫：

```text
Hello Android 毕业项目
```

它的核心定位是：

```text
一个课程学习中心，同时也是一个 Android 工程能力展示台。
```

## 用户侧需求

从普通用户视角，它应该至少支持：

| 功能 | 说明 |
| --- | --- |
| 课程首页 | 展示课程阶段、章节进度和最近学习内容 |
| 章节列表 | 按基础、应用、架构、Framework、系统工程分组 |
| 章节详情 | 展示章节介绍、学习目标、关键问题和练习任务 |
| 学习进度 | 标记已读、练习中、已完成 |
| 收藏与笔记 | 收藏章节，记录自己的理解和疑问 |
| 离线下载模拟 | 模拟把章节内容加入离线队列 |
| 后台同步模拟 | 模拟学习进度上传、失败重试和系统限制 |
| 主题切换 | 支持明暗主题或课程风格切换 |

这些功能不需要做成复杂商业产品。

但它们要形成一条完整用户路径：

```text
打开 App
  -> 浏览课程
      -> 进入章节
          -> 标记进度
              -> 收藏 / 写笔记
                  -> 加入离线
                      -> 后台同步
                          -> 观察诊断数据
```

## 工程侧需求

从工程师视角，它还要提供一些“内部驾驶舱”：

| 区域 | 目标 |
| --- | --- |
| 架构观察区 | 展示模块、依赖方向和数据流 |
| Framework 链路区 | 展示一次点击从 UI 到系统链路的关键节点 |
| 性能观察区 | 展示冷启动、列表滑动、详情页打开、同步任务的指标 |
| 稳定性实验区 | 模拟主线程阻塞、异常崩溃、任务超时和状态恢复 |
| 存储与权限区 | 展示本地缓存、文件访问、媒体选择、权限拒绝后的体验 |
| 安全检查区 | 展示敏感日志、组件暴露、明文存储、签名校验等风险 |
| 治理工作台 | 展示发布清单、风险等级、监控基线和复盘报告 |

这部分是毕业项目区别于普通 Demo 的关键。

普通 Demo 只证明功能能跑。

毕业项目要证明：

```text
功能为什么这样设计
系统如何参与执行
出问题时如何观察
上线前如何治理
```

## 核心场景一：打开课程详情

这是最重要的主链路。

```text
用户点击课程卡片
  -> UI 发送事件
      -> ViewModel 接收 intent
          -> UseCase 获取课程详情
              -> Repository 查询本地缓存
                  -> 必要时模拟网络刷新
                      -> 更新 UI State
                          -> 记录 traceId
                              -> 展示 Framework 链路卡片
```

这个场景可以串起：

```text
Compose
ViewModel
协程
Flow
Repository
Room / DataStore
Navigation
Input
ActivityThread
Choreographer
性能埋点
```

所以它应该是毕业项目的第一条黄金路径。

## 核心场景二：离线下载与后台同步

用户把一个章节加入离线下载。

```text
点击离线按钮
  -> 写入下载任务
      -> WorkManager 接管
          -> 模拟网络 / 电量 / 存储条件
              -> 任务成功、失败或重试
                  -> 更新通知或页面状态
                      -> 记录后台调度日志
```

这个场景可以串起：

```text
后台任务
前台服务边界
WorkManager
Doze / App Standby
存储访问
权限体验
日志与证据链
```

它能让学习者明白：后台任务不是“开个线程就行”，而是必须接受系统规则。

## 核心场景三：事故诊断

毕业项目应该能模拟几类可控问题：

| 事故 | 训练目标 |
| --- | --- |
| 详情页点击后卡住 | 观察主线程阻塞、帧耗时、traceId |
| 后台同步延迟 | 区分代码没执行、系统限制和条件未满足 |
| 资源显示异常 | 观察 density、locale、theme、资源合并问题 |
| 权限拒绝后功能不可用 | 设计合理降级体验 |
| release 后堆栈不可读 | 理解 mapping / symbols 归档价值 |
| 模块依赖越界 | 用治理规则阻止架构腐化 |

这些事故不一定都要真的制造严重问题。

但 Demo 至少要能让读者“看到现象、拿到证据、做出判断”。

## 需求边界：哪些先不做

毕业项目要克制。

不建议一开始就做：

```text
真实账号体系
真实支付
复杂后端服务
完整 IM
视频播放平台
高度拟真的商业推荐系统
```

这些东西会把课程目标带偏。

第 26 章要训练的是 Android 工程能力，不是做一个商业产品原型。

更合适的策略是：

```text
业务数据用 fake repository 或本地 JSON。
网络请求可以模拟延迟、失败和重试。
下载任务可以模拟状态，不必真正下载大文件。
监控数据可以由本地事件和假指标生成。
治理报告可以由规则引擎和静态数据生成。
```

这样项目足够完整，又不会被外部系统拖住。

## 分阶段实现路线

毕业项目不建议一口气写完。

更好的方式是按版本推进：

| 版本 | 目标 | 完成后你应该看到什么 |
| --- | --- | --- |
| V1：主路径可运行 | 课程首页、章节列表、详情页、学习进度 | 用户可以打开 App，完成一次从浏览到学习的闭环 |
| V2：数据与任务可观察 | 收藏、笔记、离线任务、后台同步模拟 | 用户操作能保存，任务状态能被观察 |
| V3：架构与链路可解释 | 模块图、数据流、Framework 链路卡片、traceId | 读者能说清一次点击经过了哪些应用层和系统层节点 |
| V4：事故可诊断 | 卡顿、异常、任务失败、权限拒绝、资源异常剧本 | 问题发生时能看到现象、证据、假设和修复建议 |
| V5：发布可治理 | 发布清单、风险等级、监控基线、治理报告、答辩材料 | 项目可以给出“能不能发、为什么”的工程结论 |

这条路线能降低终章项目的压力。

先让项目站起来，再让它会说话，最后让它能接受评审。

## 需求验收标准

完成本节后，毕业项目需求应该满足：

| 验收项 | 标准 |
| --- | --- |
| 用户路径 | 能从首页进入详情，完成学习、收藏、笔记、离线、同步 |
| 工程路径 | 能看到架构、Framework、性能、稳定性、安全、治理入口 |
| 异常路径 | 至少能模拟 3 类问题并展示诊断线索 |
| 数据路径 | 本地状态可保存，任务状态可观察 |
| 文档路径 | README 能说明项目目标、模块结构、运行方式和练习任务 |
| 演进路径 | 能按 V1 到 V5 逐步完成，不要求一开始就做满 |

如果一个需求无法被验收，它就只是愿望。

毕业项目不能只收集愿望，要收集可以落地的目标。

## 本节复盘

本节我们定义了第 26 章毕业项目的需求边界：

```text
它是一个课程学习 App。
它也是一个工程能力展示台。
它要覆盖用户功能、工程观察、事故诊断和治理评审。
它应该按 V1 到 V5 分阶段实现，避免终章项目一开始就变得过重。
```

下一节，我们会把需求拆成模块架构。

从这一刻开始，项目不再只是“页面集合”，而要有清晰的边界和方向。
