# 21.5 JobScheduler 与 WorkManager：可靠后台任务如何被系统调度

如果 AlarmManager 关注的是“时间到了”，那么 JobScheduler 和 WorkManager 更关注：

```text
条件是否合适？
任务是否需要可靠完成？
失败后是否需要重试？
任务之间是否有依赖关系？
```

现代 Android 工程里，很多后台任务都不应该自己手写线程、Service 或轮询，而应该交给系统调度。

## 本节定位

本节负责回答：

- JobScheduler 和 WorkManager 分别是什么？
- WorkManager 为什么适合可靠后台任务？
- 为什么任务入队后不一定立刻执行？
- 约束、重试、唯一任务和任务链应该怎么理解？
- 如何排查 Work 没执行、延迟、重复或失败？

## 学习目标

学完本节后，你应该能够：

- 知道 WorkManager 是推荐的可靠后台任务框架之一。
- 理解 WorkManager 底层会根据系统版本和能力使用合适的调度方案。
- 能设计约束条件、重试策略和唯一任务。
- 能解释任务延迟不一定是 bug，而可能是系统调度结果。
- 能为同步、上传、清理、预缓存等任务选择 WorkManager。

## 第一部分：什么任务适合 WorkManager

WorkManager 适合：

```text
需要可靠完成
可以延迟执行
可以根据条件执行
失败后可以重试
需要任务链或唯一任务
即使 App 退出也希望继续被系统调度
```

典型场景：

| 场景 | 为什么适合 |
| --- | --- |
| 上传学习记录 | 不一定立刻，但要可靠 |
| 同步课程进度 | 可等待网络，可重试 |
| 清理缓存 | 可延迟，可设置条件 |
| 预下载课程封面 | 可在 Wi-Fi 下执行 |
| 上报诊断日志 | 可批量，可退避重试 |

不适合：

| 场景 | 更合适方案 |
| --- | --- |
| 正在播放音乐 | Foreground Service |
| 正在导航定位 | Foreground Service |
| 精确闹钟提醒 | AlarmManager |
| 页面内短暂请求 | 协程 + 生命周期 |
| 超高频后台轮询 | 重新设计业务 |

## 第二部分：JobScheduler 的角色

JobScheduler 是系统级任务调度机制。

它允许 App 提交一个 Job，并声明：

```text
需要网络
需要充电
需要设备空闲
需要持久化
最小延迟
截止时间
```

系统根据设备状态决定什么时候运行。

JobScheduler 的核心价值是：

```text
让系统统一管理后台任务
而不是让每个 App 自己随意唤醒设备
```

## 第二部分补充：JobScheduler 为什么要看配额

JobScheduler 不只是“条件满足就运行”。

系统还要考虑：

```text
这个 App 最近是否常用？
它已经消耗了多少后台执行机会？
设备是否处于省电状态？
系统当前是否繁忙？
有没有更高优先级的任务？
```

这就是配额和待机桶存在的原因。

可以粗略理解为：

```text
Active App
  -> 后台机会相对多

Rare / Restricted App
  -> 后台机会明显减少
```

同一个 Job 在两台设备上表现不同，不一定是代码不一致，而可能是：

```text
用户使用频率不同
设备状态不同
待机桶不同
省电策略不同
厂商调度策略不同
```

所以 `dumpsys jobscheduler` 不是可选项，它是后台任务排查的主证据之一。

## 第三部分：WorkManager 的角色

WorkManager 更偏工程层。

它提供：

```text
统一 API
约束条件
重试策略
唯一任务
任务链
状态观察
持久化调度
和协程更好的结合
```

你可以把它理解成：

```text
面向 App 工程的可靠后台任务抽象
```

WorkManager 会根据系统版本和环境选择合适的底层执行方式。对多数 App 来说，比直接使用 JobScheduler 更容易形成清晰、可测试、可维护的后台任务代码。

但要特别强调：

```text
WorkManager 的可靠
  -> 是指任务会被持久化、可重试、可观察、可在合适条件下继续执行
      -> 不是指任务一定立刻执行
```

如果你把 WorkManager 当成立刻执行的线程池，就会误判很多现象。

## 第三部分补充：从 WorkRequest 到 Worker 的状态机

WorkManager 的核心不是“开线程”，而是维护一个后台任务状态机。

可以把它理解成：

```text
WorkRequest
  -> 生成 WorkSpec
      -> 写入 WorkManager 数据库
          -> Scheduler 选择调度方式
              -> SystemJobScheduler / JobScheduler
                  -> 约束满足后启动 Worker
                      -> Worker 返回 Result
                          -> 更新状态、重试、失败或触发后续任务
```

其中几个概念要分清：

| 概念 | 含义 |
| --- | --- |
| `WorkRequest` | 开发者提交的任务请求 |
| `WorkSpec` | WorkManager 内部持久化的任务描述 |
| `Constraints` | 网络、充电、存储、电量等执行条件 |
| `Scheduler` | 把任务交给合适底层调度器的组件 |
| `Worker` | 真正执行任务逻辑的地方 |
| `Result` | 告诉 WorkManager 成功、失败或需要重试 |

这条链路解释了一个常见现象：

```text
Work 已经 ENQUEUED
  -> 不代表 Worker 已经 RUNNING
```

因为中间还隔着：

```text
约束判断
系统调度
配额
省电状态
进程状态
```

所以排查 WorkManager 问题时，要先问：

```text
它卡在状态机的哪一步？
```

而不是直接问：

```text
为什么代码没执行？
```

## 第三部分补充：WorkManager 的几种工作语义

WorkManager 不是只有一种用法。

常见语义可以这样拆：

| 语义 | 适合场景 | 注意点 |
| --- | --- | --- |
| OneTimeWork | 上传、同步、清理等一次性任务 | 关注约束和重试 |
| PeriodicWork | 周期性维护任务 | 周期不适合太短，执行时间受系统调度 |
| UniqueWork | 同一业务只允许一个任务 | 选择 keep、replace、append 等策略 |
| ChainWork | 多步骤依赖任务 | 处理前一步失败后的行为 |
| Expedited Work | 需要尽快执行的短任务 | 受配额限制，不适合滥用 |
| Long-running Worker | 需要较长时间运行的任务 | 通常会使用前台服务通知，仍要注意系统限制 |

这张表的关键不是 API 名称，而是任务语义。

先说清任务语义，再决定 Work 类型。

## 第四部分：约束条件

约束条件是后台任务设计的灵魂。

常见约束：

```text
网络可用
非低电量
充电中
存储空间足够
设备空闲
```

例如：

```text
上传学习记录
  -> 需要网络
  -> 失败可重试

下载大资源
  -> 需要 Wi-Fi
  -> 最好充电
  -> 用户可感知时考虑前台服务

清理缓存
  -> 不紧急
  -> 可在设备空闲时执行
```

约束不是越多越好。

约束越多，任务越可能延迟。

## 第五部分：重试策略

后台任务一定要考虑失败。

失败原因可能是：

```text
网络断开
接口超时
服务端限流
本地数据库被占用
进程被杀
系统调度中断
```

WorkManager 支持重试和退避策略。

设计重试时要注意：

- 任务是否幂等。
- 重试是否会造成重复上传。
- 是否需要本地去重 key。
- 是否需要最大重试次数。
- 失败是否要降级或上报。

一个没有幂等设计的重试，可能比不重试更危险。

## 第五部分补充：退避不是拖延，而是保护系统

后台任务失败后，很多人第一反应是：

```text
立刻重试。
```

但如果失败原因是网络抖动、服务端限流或系统资源紧张，立刻重试可能让情况更糟。

退避策略的意义是：

```text
第一次失败
  -> 稍后再试
      -> 多次失败后拉长间隔
          -> 给网络、服务端和设备状态恢复机会
```

设计退避时要问：

- 失败是否可恢复？
- 重试是否幂等？
- 是否会造成重复扣费、重复上传或重复通知？
- 是否需要把最终失败暴露给用户？
- 是否需要服务端去重？

## 第六部分：唯一任务

很多任务不应该同时存在多个实例。

例如：

```text
同步课程进度
上传诊断日志
刷新离线课程索引
清理缓存
```

如果用户连续触发多次，可能需要：

```text
保留已有任务
替换旧任务
追加到任务链
取消后重新开始
```

这就是唯一任务策略的意义。

它让后台任务从“随便排队”变成“有业务语义的调度”。

## 第七部分：任务链

任务链适合表达依赖关系：

```text
拉取课程列表
  -> 下载封面
      -> 更新本地索引
          -> 上报同步成功
```

如果某一步失败，后续步骤是否继续，要根据业务设计。

任务链的核心价值是：

```text
把后台工作从一团异步回调
变成可观察、可推理的流程
```

## 第八部分：排查 Work 没执行

遇到 WorkManager 没执行，先不要猜。

检查：

```text
任务是否入队成功
当前 state 是 ENQUEUED、RUNNING、SUCCEEDED、FAILED 还是 CANCELLED
约束条件是否满足
是否处于省电模式
是否处于 Doze
App 是否被系统限制
是否有唯一任务策略覆盖
是否因为重试退避在等待
Worker 是否抛异常
输入数据是否有效
是否触发 expedited work 或 long-running worker 配额限制
是否被 App Standby / Battery Saver 限制
是否被唯一任务策略替换或合并
```

常用命令：

```bash
adb shell dumpsys jobscheduler
adb shell dumpsys deviceidle
adb shell dumpsys activity processes
adb logcat | grep -i WorkManager
```

## 第九部分：长任务、前台服务和用户主动数据传输

有些任务比较特殊：

```text
用户点了“下载 2GB 离线课程”
用户点了“上传诊断包”
用户点了“导出学习记录”
```

这些任务既不是普通的“稍后同步”，也不一定适合简单地放在 WorkManager 里等系统调度。

它们有三个特征：

```text
用户主动发起
数据量可能较大
用户希望看到进度和结果
```

面对这类任务，可以考虑：

- 是否需要 Foreground Service 展示持续通知。
- 是否应该使用系统支持的用户主动数据传输能力。
- 是否需要分片、断点续传和状态持久化。
- 是否需要在网络变化、进程死亡后恢复。
- 是否要提供暂停、取消和重试。

这类任务最怕两个极端：

```text
极端一：偷偷在后台跑，用户不知道为什么耗电耗流量。
极端二：完全依赖页面生命周期，用户切后台就丢进度。
```

成熟方案通常会把“用户感知”和“可靠恢复”一起设计。

## 本节小结

WorkManager 的关键不是“后台执行”，而是：

```text
可靠
可约束
可重试
可观察
可恢复
```

如果一个后台任务不需要立刻执行，但需要最终完成，WorkManager 往往是比手写线程和普通 Service 更适合的选择。

但请记住：

```text
可靠不等于立刻。
系统调度不等于失控。
任务延迟不等于 bug。
```
