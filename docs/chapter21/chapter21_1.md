# 21.1 为什么要学习后台任务、前台服务与系统调度限制

第 20 章我们进入了稳定性事故调查室：

```text
App 卡住、崩溃、native 异常或系统服务异常
  -> 系统如何记录证据
      -> 工程师如何从证据走向根因和修复
```

第 21 章继续追问另一个真实工程里非常高频的问题：

```text
为什么我的后台任务没有执行？
为什么定时任务不准时？
为什么 Service 在后台启动失败？
为什么前台服务必须展示通知？
为什么 WorkManager 有时候也会延迟？
为什么保活方案越来越不可靠？
```

这些问题背后，不是某一个 API 的用法，而是 Android 对后台执行、耗电、用户感知和系统资源的长期治理。

## 本章通关画面

学完第 21 章后，你应该能画出这张后台任务地图：

```text
业务想做一件后台事情
  -> 判断用户是否正在感知
      -> 判断是否必须立即执行
          -> 判断是否需要可靠完成
              -> 判断是否需要网络、充电、空闲等条件
                  -> 选择 Service / Foreground Service / WorkManager / JobScheduler / AlarmManager
                      -> 观察系统限制、执行窗口和失败原因
                          -> 给出合规、稳定、可解释的后台方案
```

如果第 19 章像进程调度室，第 20 章像事故调查室，那么第 21 章就是后台任务调度台。

在这个调度台上，工程师要做的不是“想办法让 App 永远醒着”，而是像调度员一样判断：

```text
这班车是不是现在必须发？
它是否载着用户正在等待的东西？
能不能和下一班合并？
如果路上堵了，乘客是否能看到进度？
如果失败了，系统能不能重新安排？
```

很多业务都想在后台继续运行：

- 同步课程进度。
- 上传学习记录。
- 下载离线课程。
- 定时提醒复习。
- 清理缓存。
- 上报日志。
- 接收远端指令。

但系统不会允许所有 App 在后台随意运行。原因很简单：如果每个 App 都能长期占用 CPU、网络、定位、唤醒和内存，手机就会发热、耗电、卡顿，用户体验会迅速崩掉。

## 本章核心判断：三问法

面对任何后台需求，先问三句话：

```text
第一问：用户是否正在感知它？
第二问：它是否必须现在完成？
第三问：它失败后是否必须恢复？
```

这三句话会把大多数争论拉回工程判断。

例如：

| 需求 | 用户感知 | 是否必须现在 | 是否必须恢复 | 倾向方案 |
| --- | --- | --- | --- | --- |
| 正在下载离线课程 | 是 | 是 | 是 | Foreground Service + 通知 + 持久化 |
| 上传学习进度 | 否 | 否 | 是 | WorkManager |
| 每天 8 点提醒学习 | 是 | 接近精确 | 是 | AlarmManager + 通知 |
| 页面离开后保存草稿 | 弱 | 尽快 | 是 | 本地持久化 + 生命周期内任务 |
| 每 10 秒轮询服务端 | 否 | 通常不是 | 不一定 | 重新设计为 Push / 批量同步 |

如果一个需求无法解释“用户为什么需要它现在在后台运行”，那它大概率不是后台任务问题，而是产品语义还没想清楚。

## 本章剧情线

真实项目里，后台问题通常不是这样出现的：

```text
请你帮我选择一个后台任务 API。
```

而是这样出现的：

```text
用户说离线课程没有下载完。
运营说学习提醒没有准时弹。
测试说 App 切后台后上传任务丢了。
产品说一定要实时同步。
老板说竞品能保活，我们为什么不行。
线上日志说任务排队很久没有执行。
Android 14 上前台服务启动直接异常。
```

这些问题看起来都叫“后台任务”，但它们的答案可能完全不同。

```text
立即可见的任务
  -> 前台服务

可靠但不要求立刻完成的任务
  -> WorkManager / JobScheduler

指定时间提醒
  -> AlarmManager / 通知体系

短时间离开页面仍要完成的任务
  -> 生命周期内协程 / 业务状态恢复

长期保活
  -> 通常不是一个合规目标，而是需求需要重新设计
```

## 本章探索任务

```text
理解 Android 为什么限制后台执行
  -> 区分 Service、Foreground Service、JobScheduler、WorkManager、AlarmManager
      -> 理解后台启动限制、前台服务类型和通知要求
          -> 理解 Doze、App Standby、Battery Saver 对任务的影响
              -> 学会观察任务为什么没执行
                  -> 建立后台任务的设计决策表
                      -> 做一个后台调度观察实验室
```

## 学习目标

学完本节后，你应该能够：

- 区分“正在后台运行”和“被系统调度执行”。
- 知道 Android 限制后台任务的核心原因：耗电、性能、公平性和用户感知。
- 初步区分 Service、Foreground Service、WorkManager、JobScheduler 和 AlarmManager。
- 知道后台任务失败时不能只猜代码，要看系统状态、约束条件、权限和执行窗口。
- 建立一个原则：先判断业务语义，再选择后台机制。

## 第一部分：后台任务不是一个 API，而是一组业务语义

很多初学者会问：

```text
后台任务到底应该用 Service 还是 WorkManager？
```

这个问题本身还不够精确。

真正应该先问的是：

```text
这个任务是否必须让用户立刻感知？
是否必须现在执行？
是否必须可靠完成？
是否可以等待系统选择合适时机？
是否依赖网络、充电、空闲或存储空间？
用户是否允许它消耗电量？
失败后是否可以重试？
```

例如：

| 业务场景 | 关键语义 | 倾向方案 |
| --- | --- | --- |
| 正在下载离线课程 | 用户能感知、持续进行 | Foreground Service + 通知 |
| 上传学习进度 | 可靠完成、不一定立刻 | WorkManager |
| 每天 8 点提醒复习 | 时间触发、用户感知 | AlarmManager + 通知 |
| 页面离开后继续保存草稿 | 短任务、可恢复 | 协程 + 本地持久化 |
| 长期监听远端指令 | 容易变成保活误区 | Push / 服务端设计 / 合规后台能力 |

后台任务设计的第一步，不是选类名，而是给任务定性。

## 第一部分补充：不要把“后台”混成一团

第 21 章里会反复出现几个词，它们很像，但不是一回事：

| 名词 | 真正含义 | 常见误解 |
| --- | --- | --- |
| 后台进程 | App 不在前台或进程优先级较低 | 只要进程在就能随便干活 |
| 后台线程 | 不在主线程执行的线程 | 开了线程就不受系统限制 |
| Service | 没有界面的组件生命周期 | Service 自动等于后台线程 |
| Foreground Service | 用户可感知的持续任务契约 | 用通知就能保活 |
| WorkManager | 可靠、可约束、可重试任务 | 入队后一定立刻执行 |
| AlarmManager | 时间触发入口 | 到点一定准时做任何事 |

把这些概念分开，是学懂本章的第一道门。

它回答的是：

```text

```

第 21 章把这些连起来：

```text
一个后台任务
  -> 写法上要符合异步结构

```

所以第 21 章不是第 6 章的重复，而是从系统限制和工程决策角度重新理解后台任务。

## 第三部分：为什么系统越来越限制后台

早期 Android 里，很多 App 会通过长期 Service、频繁 Alarm、广播拉起、互相唤醒等方式试图常驻后台。

短期看，业务似乎更“实时”。

长期看，问题很严重：

- CPU 被频繁唤醒，手机更耗电。
- 网络被零散占用，系统无法批量调度。
- 后台进程过多，内存压力上升。
- 用户无法感知谁在消耗资源。
- 低端设备更容易卡顿、发热、杀进程。

于是 Android 逐步引入：

```text
Doze
App Standby
后台 Service 启动限制
后台广播限制
JobScheduler
WorkManager
Foreground Service 类型限制
精确闹钟权限
通知权限
电池优化策略
```

这些限制背后的目标不是为难开发者，而是让后台工作变得可调度、可感知、可约束。

## 本节小结

后台任务的本质，不是“让 App 偷偷运行”，而是：

```text
在合适的业务语义下
  -> 使用合适的系统机制
      -> 接受系统对电量、性能和用户感知的调度
          -> 在失败时能解释原因并设计恢复
```

学第 21 章时，请先放下一个执念：

```text
后台任务的目标不是保活。
后台任务的目标是可靠、合规、可解释地完成用户认可的事情。
```
