# 21.6 Doze、App Standby、Battery Saver 与厂商限制

后台任务最让人头疼的地方在于：

```text
代码没报错
任务也入队了
但它就是没有按你预期执行
```

这时候你可能遇到的不是代码 bug，而是系统省电和后台策略。

## 本节定位

本节负责回答：

- Doze 是什么，它为什么会延迟后台任务？
- App Standby 为什么会影响任务配额？
- Battery Saver 会限制哪些能力？
- 厂商限制为什么会让后台行为更复杂？
- 如何用命令观察这些状态？

## 学习目标

学完本节后，你应该能够：

- 理解 Doze 的目标是降低待机耗电。
- 理解 App Standby 会根据用户使用情况影响后台执行机会。
- 知道省电模式下网络、Job、Alarm、后台执行都可能被限制。
- 知道厂商策略可能比原生 Android 更激进。
- 能用 dumpsys 观察 device idle、jobscheduler、alarm 等状态。

## 第一部分：Doze 是什么

Doze 可以理解为设备待机省电机制。

当设备长时间未使用、熄屏、静止时，系统可能进入更深的省电状态。

进入 Doze 后，系统会减少后台活动：

```text
限制网络访问
推迟 Job
推迟普通 Alarm
限制 WakeLock
减少后台 CPU 活动
通过维护窗口集中执行任务
```

这不是为了让 App 难受，而是为了让手机待机更久。

## 第一部分补充：DeviceIdleController 在做什么

从系统侧看，Doze 不是一个简单的“开关”，而是一套设备空闲状态机。

可以粗略理解为：

```text
设备熄屏、静止、长时间未使用
  -> DeviceIdleController 逐步进入 idle 相关状态
      -> 限制网络、WakeLock、Job、普通 Alarm
          -> 定期开维护窗口
              -> 允许部分任务集中执行
                  -> 再次回到更深的省电状态
```

这解释了一个关键现象：

```text
后台任务不是永远不执行
而是被系统挪到更省电的时间窗口执行
```

所以你看到任务延迟时，应该先问：

```text
设备是不是处于 idle？
当前是否在维护窗口？
这个任务是否被允许 idle 下触发？
```

而不是只问：

```text
为什么我的代码没有马上跑？
```

## 第二部分：维护窗口

Doze 不代表所有后台任务永远不执行。

系统会开放维护窗口：

```text
进入低功耗状态
  -> 暂停大多数后台活动
      -> 到达维护窗口
          -> 批量执行一些任务
              -> 再次进入低功耗状态
```

所以你可能看到：

```text
任务不是不执行
而是被集中到某个窗口执行
```

这也是为什么后台任务常常延迟。

## 第三部分：App Standby

App Standby 会根据用户使用情况，把 App 放进不同待机桶。

概念上可以理解为：

```text
用户越常用
  -> 后台机会越多

用户越少用
  -> 后台机会越少
```

不同待机桶会影响：

- Job 执行机会。
- Alarm 触发频率。
- 网络访问机会。
- 后台任务配额。

这意味着同一个 App 在不同用户设备上，后台表现可能不同。

可以用一个更生活化的方式理解待机桶：

| 桶 | 可以粗略理解为 | 后台机会 |
| --- | --- | --- |
| Active | 用户最近正在用 | 相对充足 |
| Working set | 用户经常用 | 有一定机会 |
| Frequent | 用户偶尔用 | 机会变少 |
| Rare | 用户很少用 | 机会很少 |
| Restricted | 系统认为需要强限制 | 限制更明显 |

不同 Android 版本和厂商实现可能会有差异，但核心思路一致：

```text
用户越不常用
  -> 系统越不愿意给它后台资源
```

这不是系统“偏心”，而是资源分配。

## 第三部分补充：AppStandbyController 的视角

App Standby 的核心问题是：

```text
这个 App 最近和用户有多近？
```

系统会根据用户使用、通知、前台服务、交互、安装状态等信息，调整 App 的待机状态。

可以想象系统在问：

```text
用户刚刚打开过它吗？
它有没有用户可见活动？
它是否通过通知和用户互动？
它是不是长期没被使用？
它是否消耗了过多后台资源？
```

待机桶影响的不是某一个 API，而是一组后台机会：

```text
Job 执行机会
Alarm 触发机会
后台网络机会
后台执行配额
```

因此同一段 WorkManager 代码：

```text
在重度用户设备上很快执行
在很久没打开 App 的设备上明显延迟
```

并不矛盾。

系统看到的不是“同一段代码”，而是“不同 App 使用状态下的后台资源请求”。

## 第四部分：Battery Saver

Battery Saver 是用户或系统启用的省电模式。

省电模式下，系统可能限制：

```text
后台网络
后台同步
动画和性能
定位
Job 调度
Alarm 频率
```

业务上要理解：

```text
用户开启省电模式
  -> 本质上是在告诉系统优先保护电量
      -> App 应该降低后台期待
```

如果你的任务在省电模式下延迟，这不一定是错误。

## 第五部分：厂商限制

Android 生态里还有一个现实变量：厂商策略。

不同厂商可能会对后台行为做额外限制：

```text
更激进地杀后台进程
限制自启动
限制后台网络
限制后台定位
限制通知
限制前台服务启动
要求加入白名单
```

这也是为什么后台任务问题常常呈现：

```text
只在某些机型复现
只在某些系统版本复现
只在低电量或熄屏后复现
```

课程不会鼓励学习“保活黑科技”，因为这条路越来越不可靠，也不符合系统治理方向。

更推荐的思路是：

```text
业务降级
状态持久化
用户可感知
系统推荐 API
合理重试
必要时引导用户配置权限或电池策略
```

## 第五部分补充：Push 也不是后台万能钥匙

很多团队会说：

```text
既然后台任务受限，那我们用 Push 把 App 拉起来。
```

Push 可以解决一部分“服务端通知客户端”的问题，但它不是后台万能钥匙。

需要注意：

- Push 适合通知用户或触发轻量同步，不适合承载大量后台计算。
- 高优先级消息应服务于真正紧急、用户相关的场景。
- Push 到达后仍然要面对权限、通知、进程状态和后台限制。
- 如果收到 Push 后立刻做长时间工作，仍然可能需要 WorkManager 或前台服务。

更健康的设计是：

```text
服务端 Push 提供事件入口
  -> App 做轻量判断
      -> 必要时入队可靠任务
          -> 用户可感知时展示通知或前台服务
```

不要把 Push 当成绕过系统后台限制的暗门。

## 第六部分：如何观察系统状态

常用命令：

```bash
adb shell dumpsys deviceidle
adb shell dumpsys jobscheduler
adb shell dumpsys alarm
adb shell dumpsys activity processes
adb shell dumpsys battery
adb shell dumpsys usagestats
```

可以观察：

```text
设备是否 idle
Job 是否排队
Alarm 是否注册
App 进程状态
电池状态
App 使用情况
```

调试 Doze 时常见命令：

```bash
adb shell dumpsys deviceidle force-idle
adb shell dumpsys deviceidle step
adb shell dumpsys deviceidle unforce
```

使用这些命令时要知道：它们用于学习和调试，不代表真实用户设备上的完整厂商策略。

## 第六部分补充：观察日志应该怎么记

光执行 dumpsys 还不够，你需要把系统状态和任务状态对齐。

建议记录成下面这种时间线：

```text
10:00:00 用户点击同步
10:00:01 Work 入队，约束：Wi-Fi + charging
10:00:03 当前网络：4G，未充电
10:15:20 用户插上电源
10:16:00 Wi-Fi 连接
10:16:10 Work 开始执行
10:16:42 Work 成功
```

或者：

```text
23:30:00 注册学习提醒 Alarm
23:40:00 设备熄屏进入 idle
08:00:00 期望触发
08:06:30 实际触发
08:06:31 通知展示
```

只有把“期望时间、实际时间、系统状态、任务状态”放在一起，后台问题才会从玄学变成证据。

## 第七部分：后台任务诊断表

排查后台任务时，可以填这张表：

| 问题 | 需要确认 |
| --- | --- |
| 任务是否入队 | 本地日志、Work 状态、Job 状态 |
| 条件是否满足 | 网络、充电、空闲、电量、存储 |
| 是否进入 Doze | dumpsys deviceidle |
| 是否处于省电模式 | dumpsys battery / 系统设置 |
| App 是否很少使用 | App Standby / usagestats |
| 是否厂商限制 | 机型、系统版本、电池策略 |
| 是否用户可感知 | 通知、前台服务、权限 |
| 是否可恢复 | 本地状态、重试、幂等 |

## 第八部分：从状态反推系统判断

排查后台问题时，可以按这条路线反推：

```text
任务没执行
  -> 是否入队 / 注册成功？
      -> 约束是否满足？
          -> App 是否被限制？
              -> 设备是否 idle / 省电？
                  -> 是否还有任务配额？
                      -> 是否被厂商策略拦住？
```

对应证据：

| 判断点 | 证据入口 |
| --- | --- |
| 是否入队 | App 日志、Work state、本地任务表 |
| 是否被 JobScheduler 接收 | `dumpsys jobscheduler` |
| 是否被 AlarmManager 接收 | `dumpsys alarm` |
| 是否 idle | `dumpsys deviceidle` |
| 电池 / 充电状态 | `dumpsys battery` |
| 进程状态 | `dumpsys activity processes` |
| 通知和前台服务 | `dumpsys notification`、`dumpsys activity services` |

## 本节小结

Doze、App Standby、Battery Saver 和厂商策略共同告诉我们：

```text
后台任务不是只由 App 决定
它是 App、系统、设备状态、用户行为和厂商策略共同决定的结果
```

资深工程师面对后台问题时，不会只说“我代码没问题”。

他会继续问：

```text
任务是否符合系统调度语义？
当前设备状态是否允许执行？
失败后是否可恢复？
用户是否知道这个任务存在？
```
