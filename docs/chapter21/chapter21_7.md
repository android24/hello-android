# 21.7 后台任务体验问题：任务丢失、耗电、保活误区与合规风险

后台任务最容易把工程师带进误区。

因为它的失败不像 Crash 那样直接，也不像 ANR 那样明显。很多时候，用户只是说：

```text
怎么没同步？
怎么没提醒？
怎么没下载完？
怎么一晚上掉了好多电？
为什么通知一直关不掉？
```

第 21 章前面几节讲机制，本节把这些机制落到体验问题上。

## 本节定位

本节负责回答：

- 后台任务常见体验问题有哪些？
- 任务丢失到底可能是什么原因？
- 为什么耗电问题常常来自错误的后台设计？
- 为什么保活不是一个健康的工程目标？
- 如何把后台任务设计成可解释、可恢复、可监控？

## 学习目标

学完本节后，你应该能够：

- 对后台任务问题进行分类。
- 为任务丢失建立排查清单。
- 识别耗电和频繁唤醒风险。
- 解释保活误区和合规风险。
- 设计后台任务的监控、恢复和用户沟通方案。

## 第一部分：任务丢失

用户说“任务丢了”，可能有很多含义：

```text
任务没有入队
任务入队但没执行
任务执行了但失败
任务成功了但 UI 没更新
任务执行结果被进程死亡丢掉
任务被取消
任务被唯一任务策略替换
任务被系统延迟
任务被厂商策略限制
```

所以排查时不要只问：

```text
为什么没执行？
```

要拆成：

```text
是否创建任务？
是否入队成功？
是否满足约束？
是否开始运行？
是否运行成功？
结果是否持久化？
UI 是否读取了最新结果？
失败是否重试？
用户是否收到反馈？
```

### 事故剧本：离线课程消失了

```text
用户在地铁上点了“下载离线课程”
  -> 下载到 42%
      -> 用户切到聊天 App
          -> 半小时后回来，下载不见了
```

不要急着说“系统杀了进程”。

先拆证据：

| 问题 | 证据 |
| --- | --- |
| 下载任务是否持久化 | 本地任务表有没有记录 |
| 下载是否只绑定页面生命周期 | 页面销毁日志、协程作用域 |
| 是否启动前台服务 | 通知是否出现、service 日志 |
| 进程是否死亡 | pid 是否变化、Application 是否重建 |
| 是否支持断点续传 | 已下载文件、range 信息 |
| 用户是否能重试 | UI 是否展示失败原因 |

如果所有进度只存在内存里，那根因不是“后台不可靠”，而是任务状态设计不可靠。

## 第二部分：任务重复

后台任务还有另一类问题：重复执行。

例如：

```text
学习记录上传了两次
同一课程重复下载
日志重复上报
通知重复弹出
缓存清理任务并发执行
```

常见原因：

- 没有唯一任务策略。
- 没有幂等 key。
- 重试和手动触发叠加。
- 进程重建后重复恢复。
- 多进程同时调度。
- 服务端没有去重。

后台任务必须设计幂等。

一个好的后台任务应该能回答：

```text
重复执行会不会造成错误？
失败重试会不会重复提交？
多设备、多进程、多次点击会不会产生脏数据？
```

幂等不是服务端一个人的事。

客户端也应该尽量提供：

```text
业务唯一 key
本地任务状态
重复点击保护
任务合并策略
失败重试标记
```

例如学习记录上传可以设计：

```text
userId + courseId + lessonId + progressVersion
```

这样即使 Work 重试，服务端也能判断这是不是同一份进度。

## 第三部分：耗电

耗电问题通常不是某一行代码造成的，而是一组后台行为叠加造成的：

```text
频繁唤醒
频繁网络请求
短周期轮询
滥用精确闹钟
长时间前台服务
持有 WakeLock
后台定位
重复任务
失败后疯狂重试
```

后台任务设计时要问：

```text
这个任务是否可以合并？
是否可以批量？
是否可以延迟？
是否必须现在联网？
是否需要用户感知？
失败后是否退避？
```

省电不是“少做功能”，而是用更合适的时机做功能。

### 事故剧本：一晚上掉电 20%

```text
用户反馈晚上没用 App，早上起来手机掉电明显。
```

这类问题不要只看 Crash 平台，因为它可能完全没有 Crash。

你应该看：

```text
后台任务是否频繁失败重试
Alarm 是否短周期唤醒
是否持续持有 WakeLock
是否后台定位
是否前台服务通知常驻
是否网络请求无法合并
是否日志上报过于频繁
```

耗电问题的修复往往不是“优化一个函数”，而是改变后台策略：

```text
短周期 -> 批量
立即 -> 延迟
精确 -> 非精确
无限重试 -> 退避重试
偷偷执行 -> 用户感知
内存状态 -> 持久化状态
```

## 第四部分：保活误区

很多团队会提出：

```text
我们要让 App 一直活着。
```

这句话要非常谨慎。

Android 的设计方向不是让所有 App 常驻后台，而是让后台能力符合系统调度和用户感知。

常见保活误区：

```text
互相拉起
常驻无意义前台服务
频繁 Alarm 唤醒
后台轮询
监听大量广播
滥用无障碍或其他敏感权限
引导用户关闭所有电池优化
```

这些方案的问题是：

- 不稳定，系统版本越高越容易失效。
- 用户体验差，通知和耗电容易引起反感。
- 合规风险高。
- 难以通过应用市场审核。
- 工程上掩盖了真正的业务设计问题。

更健康的问题应该是：

```text
用户真正需要哪个后台结果？
这个结果是否必须实时？
是否可以由服务端 Push？
是否可以下一次打开 App 时恢复？
是否可以通过 WorkManager 可靠完成？
是否需要前台服务让用户感知？
```

### 需求评审时应该怎么说

当有人提出“我们要保活”时，可以把问题翻译成更可讨论的版本：

```text
你希望用户在什么场景下得到什么结果？
这个结果晚几分钟是否可以接受？
用户是否需要看到通知或进度？
服务端是否可以主动通知？
App 下次打开时恢复是否可以接受？
失败后是否可以重试？
```

这样讨论会从“怎么绕过系统”回到“用户到底需要什么”。

## 第五部分：合规风险

后台任务不仅是技术问题，也是合规问题。

需要特别注意：

- 通知权限。
- 前台服务类型。
- 后台定位。
- 麦克风、相机、蓝牙、健康数据。
- 精确闹钟权限。
- 敏感权限滥用。
- 隐私数据后台上传。
- 用户未感知的长期后台行为。

一个技术上能跑的方案，不一定是合规方案。

资深工程师要能在需求评审时说清楚：

```text
这个能力需要什么权限？
用户是否知道？
是否可以关闭？
是否有更低侵入的替代方案？
是否会被系统或应用市场限制？
```

## 第五部分补充：权限不是越多越专业

后台任务常常会牵涉权限：

```text
通知
精确闹钟
后台定位
蓝牙
麦克风
相机
健康数据
文件访问
```

权限申请越多，用户越需要理由。

一个成熟的权限设计应该能回答：

- 为什么现在申请？
- 拒绝后是否可以继续使用核心功能？
- 用户在哪里能重新开启？
- 权限和后台任务之间有什么关系？
- 是否可以用更低权限的方案替代？

权限不是功能的装饰，它是用户信任的一部分。

## 第六部分：后台任务监控

后台任务如果没有监控，出了问题很难查。

建议记录：

```text
taskId
taskType
enqueueTime
startTime
finishTime
constraints
processName
pid
networkState
batteryState
retryCount
result
failureReason
triggerSource
userVisible
```

监控指标可以包括：

- 入队成功率。
- 执行成功率。
- 平均等待时间。
- 平均执行耗时。
- 重试次数。
- 取消率。
- 超时率。
- 不同 Android 版本、机型、厂商分布。

这会把后台任务从玄学变成可观察系统。

## 第七部分：后台任务恢复

后台任务不要假设进程一直活着。

要设计：

```text
本地任务状态表
幂等提交
失败重试
启动后扫描未完成任务
用户可见状态恢复
取消和暂停
通知进度恢复
```

例如离线下载：

```text
不要只把进度存在内存
要把下载状态、文件路径、任务 id、失败原因持久化
App 重启后能恢复列表
任务失败后用户能重试
```

## 本节小结

后台任务体验问题，本质上是四件事：

```text
能不能执行
什么时候执行
执行结果是否可信
用户是否理解和接受
```

第 21 章不是教你绕过系统限制，而是教你在系统限制内设计可靠任务。

成熟的后台任务方案应该是：

```text
符合业务语义
接受系统调度
用户可以感知
失败可以恢复
证据可以追踪
权限和合规说得清楚
```
