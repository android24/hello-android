# 21.4 AlarmManager：定时任务为什么不一定准时

AlarmManager 看起来很简单：

```text
我告诉系统一个时间
系统到点叫醒我
```

但在现代 Android 里，定时任务从来不只是“到点执行”这么简单。

它要和 Doze、省电策略、精确闹钟权限、系统批处理、用户感知和 App 待机状态一起工作。

## 本节定位

本节负责回答：

- AlarmManager 适合解决什么问题？
- 为什么普通 Alarm 可能不准时？
- 精确闹钟为什么需要更严格的理由？
- Alarm 和 WorkManager、JobScheduler 有什么区别？
- 如何设计一个合规的提醒或定时任务？

## 学习目标

学完本节后，你应该能够：

- 区分普通定时、精确定时和可靠后台任务。
- 知道 AlarmManager 主要面向时间触发，而不是复杂任务调度。
- 理解 Doze 下 Alarm 为什么会被延迟或合并。
- 知道精确闹钟应该用于用户强感知、时间敏感的场景。
- 能为学习提醒、课程开播、日志上传等场景选择合适方案。

## 第一部分：AlarmManager 解决的是时间触发

AlarmManager 的核心问题是：

```text
某个时间点或时间窗口到了
  -> 请通知 App 做一件事
```

典型场景：

| 场景 | 是否适合 Alarm |
| --- | --- |
| 每天 8 点学习提醒 | 适合 |
| 课程直播开始前提醒 | 适合 |
| 生日 / 日程 / 闹钟 | 适合 |
| 后台上传日志 | 通常不适合，WorkManager 更合适 |
| 每隔几秒轮询接口 | 不适合 |
| 下载大文件 | 不适合，前台服务或 WorkManager 更合适 |

Alarm 是时间入口，不是任务执行框架。

如果任务被触发后要做大量工作，仍然需要考虑：

- 是否需要前台服务。
- 是否交给 WorkManager。
- 是否需要通知用户。
- 是否能在短时间内完成。

## 第二部分：普通 Alarm 为什么可能不准时

系统希望减少设备被频繁唤醒。

如果很多 App 都设置：

```text
8:00:01 唤醒
8:00:03 唤醒
8:00:07 唤醒
8:00:10 唤醒
```

手机会被频繁打断睡眠状态，耗电会明显增加。

所以系统会倾向于：

```text
合并相近时间的任务
延迟不紧急的任务
在维护窗口批量执行
根据待机桶控制频率
```

这意味着：

```text
普通 Alarm 的语义更像“尽量在这个时间附近执行”
而不是“必须精确到这一秒执行”
```

## 第二部分补充：AlarmManagerService 的批处理思想

从系统侧看，Alarm 不是一个个孤立闹钟，而是一批等待触发的时间事件。

大致可以这样理解：

```text
App 注册 Alarm
  -> AlarmManagerService 收到请求
      -> 根据类型、触发时间、窗口、是否精确进行归类
          -> 尽量把相近 Alarm 合并成批次
              -> 到达合适时间窗口
                  -> 唤醒或通知目标 PendingIntent
```

批处理的目标是省电。

如果系统能把十个 App 的唤醒合并到一个时间窗口，就可以减少设备从低功耗状态被唤醒的次数。

所以 `setWindow` 的意义不是“不准确”，而是：

```text
开发者告诉系统
  -> 只要在这个窗口内执行就可以
      -> 系统可以用更省电的方式安排
```

精确 Alarm 则是在说：

```text
这个时间点很重要
  -> 请尽量不要合并或延迟
```

这就是为什么精确能力必须谨慎使用。

## 第三部分：Doze 下的 Alarm

Doze 是 Android 为了降低待机耗电引入的机制。

当设备长时间未使用、静止、熄屏时，系统可能进入 Doze。

进入 Doze 后，系统会限制：

```text
网络访问
WakeLock
JobScheduler
普通 Alarm
后台执行
```

系统会开放维护窗口，让任务集中执行。

所以你可能看到：

```text
设置了 10:00 的任务
实际 10:07 才执行
或者更晚才执行
```

这不一定是代码错，而是系统在做省电调度。

## 第三部分补充：idle 下的临时执行机会

有些 API 可以表达：

```text
即使设备 idle，我也希望在某个时间点获得一次执行机会。
```

但这不是无限通行证。

系统通常会对 idle 下的触发频率做限制，并且即使允许触发，也只是给 App 一个有限窗口。

你可以把它理解成：

```text
系统短暂打开门
  -> 让 App 做一小段真正必要的事
      -> 然后继续回到省电状态
```

所以 idle 下的 Alarm 触发后，不应该立刻做大量工作。

更稳妥的设计是：

```text
Alarm 到点
  -> 展示通知或记录轻量事件
      -> 必要时入队 WorkManager
          -> 用户主动进入时继续完成
```

如果你用 idle 下 Alarm 来高频轮询，系统会越来越不愿意配合你。

## 第四部分：精确闹钟

精确闹钟适合非常少数场景：

```text
真正的闹钟
日历提醒
强时间敏感的用户可感知事件
```

它不适合滥用为：

```text
后台轮询
保活
频繁同步
偷偷唤醒
```

较新的 Android 版本对精确闹钟越来越谨慎，因为它会打断系统省电策略。

判断一个场景是否适合精确闹钟，可以问：

```text
如果晚几分钟执行，用户是否明显受损？
用户是否知道这个时间点的意义？
这个任务是否必须在那个精确时间发生？
是否可以改成通知、WorkManager 或服务端 Push？
```

## 第五部分：精确、非精确和窗口

AlarmManager 里最容易被忽略的是：不同调度方式承诺不同。

可以把它们理解成三种语义：

| 语义 | 你在表达什么 | 工程含义 |
| --- | --- | --- |
| 非精确 Alarm | 在大致时间附近执行即可 | 系统可以批量、合并、延迟，更省电 |
| 窗口 Alarm | 在某个时间窗口内执行即可 | 给系统更多调度空间，也给业务保留时间边界 |
| 精确 Alarm | 必须尽量在指定时间触发 | 只适合闹钟、日程等强时间敏感场景 |

不要把精确 Alarm 当作“后台轮询增强版”。

如果你只是想：

```text
过一会儿同步数据
网络好时上传日志
设备空闲时清缓存
```

那通常应该优先考虑 WorkManager / JobScheduler，而不是精确 Alarm。

## 第六部分：精确闹钟权限和用户承诺

较新的 Android 版本会对精确闹钟能力做更明确的权限和审核约束。

这背后的逻辑很简单：

```text
精确闹钟会打断系统省电节奏
  -> 只有真正时间敏感、用户能理解的任务才应该使用
```

判断是否应该申请精确闹钟能力，可以用这张表：

| 场景 | 是否适合精确闹钟 | 原因 |
| --- | --- | --- |
| 早上 7 点叫醒用户 | 适合 | 用户明确需要精确时间 |
| 课程直播开播提醒 | 可能适合 | 与用户约定时间强相关 |
| 每天学习提醒 | 视产品承诺而定 | 如果允许几分钟浮动，可用非精确 |
| 后台同步学习记录 | 不适合 | 可靠即可，不需要精确时间 |
| 每隔 5 分钟拉接口 | 不适合 | 容易耗电，通常应改成 Push / 批量同步 |

精确闹钟一旦使用，就等于向用户和系统做了承诺：

```text
这个时间点对用户真的重要。
```

如果说不清这句话，就不要轻易使用。

## 第七部分：Alarm、WorkManager 与 JobScheduler 的区别

可以这样理解：

| 机制 | 关注点 | 典型语义 |
| --- | --- | --- |
| AlarmManager | 时间到了 | 到点提醒或触发 |
| JobScheduler | 系统条件满足 | 网络、充电、空闲等条件下执行 |
| WorkManager | 可靠工作链 | 可重试、可约束、可观察的后台任务 |
| Foreground Service | 用户感知持续任务 | 正在下载、播放、导航 |

不要用 AlarmManager 承担所有后台任务。

一个常见组合是：

```text
AlarmManager 到点触发提醒
  -> 展示通知
      -> 用户点击通知
          -> App 前台打开或启动明确任务
```

另一个组合是：

```text
AlarmManager 提供时间入口
  -> WorkManager 执行可靠后台工作
```

但要注意：如果任务不需要精确时间，直接 WorkManager 可能更好。

## 第八部分：提醒场景设计

以“每天提醒学习”为例。

你需要回答：

```text
这是精确提醒还是大致提醒？
用户是否可以配置时间？
是否需要通知权限？
设备重启后是否要恢复提醒？
时区变化后如何处理？
用户关闭提醒后是否取消 Alarm？
任务触发时 App 是否必须启动？
```

提醒不是单个 Alarm 调用，而是一套用户承诺。

可以进一步拆成两种产品语义：

```text
柔性提醒
  -> 早上 8 点附近提醒即可
      -> 非精确 Alarm / 通知策略更合适

强提醒
  -> 8 点整必须提醒，例如考试、直播、日程
      -> 才考虑精确 Alarm，并明确权限与用户设置
```

这能避免为了“看起来准时”而滥用精确闹钟。

## 第九部分：排查 Alarm 问题

遇到提醒没有触发或不准时，可以检查：

```text
Alarm 是否真的注册成功
PendingIntent 是否一致
是否被取消或覆盖
设备是否处于 Doze
App 是否处于受限待机桶
是否缺少精确闹钟权限
通知权限是否关闭
设备是否重启后没有重新注册
厂商省电策略是否限制
PendingIntent 的 action / requestCode / flags 是否一致
是否被同一个 PendingIntent 覆盖
```

常用命令：

```bash
adb shell dumpsys alarm
adb shell dumpsys deviceidle
adb shell dumpsys jobscheduler
adb shell dumpsys activity processes
```

## 第十部分：如何读 dumpsys alarm

`dumpsys alarm` 的输出很多，初学者容易迷路。

建议先找四类信息：

```text
你的包名是否存在
  -> 说明 Alarm 是否注册进去

触发时间和窗口
  -> 看系统认为它什么时候可以触发

是否 exact / allow while idle
  -> 看你的语义是否符合预期

是否有被延迟、合并或 idle 影响的线索
  -> 看系统状态和批处理痕迹
```

读 `dumpsys alarm` 时不要只问：

```text
为什么没准点？
```

要问：

```text
我注册的 Alarm 在系统眼里是什么类型？
系统给了它多大的调度窗口？
当前设备状态是否允许它马上触发？
```

## 本节小结

AlarmManager 的正确理解是：

```text
它提供时间触发
但不保证所有任务都能无条件精确执行
```

定时任务设计时，要先区分：

```text
提醒
  -> 用户感知，时间重要

同步
  -> 可靠完成，时间可以弹性

保活
  -> 通常不是合规目标
```

如果你能把这三者分清，AlarmManager 的使用就不会走偏。
