# 25.7 团队协作、代码评审、技术债与治理节奏

大型 Android 工程最后一定会回到人。

工具很重要。

但真正让工程长期稳定的，是团队如何协作、如何评审、如何处理技术债、如何持续改进。

## 本节先记住三句话

```text
团队协作不是让所有人写一样的代码，而是让所有人理解共同边界。
代码评审不是挑毛病，而是保护工程未来。
技术债不可怕，可怕的是没人记录、没人排序、没人偿还。
```

## 贯穿案例：一次 PR 争论

一个同学提交 PR：

```text
新增课程下载功能。
为了赶进度，直接在 feature:course 里调用 feature:download 的实现类。
顺手把 DownloadState 放进 core:common。
为了方便排查，release 里也留下了一些详细日志。
```

功能能跑。

但 review 时有人提出问题：

```text
模块依赖方向不对。
公共模块混入业务状态。
日志可能泄露用户路径。
没有后台任务失败监控。
没有下载中断恢复测试。
```

这时 review 容易变成情绪对抗。

第 25 章要告诉你：好的评审不是“我觉得你写得不好”，而是“这条规则保护了哪些工程风险”。

## 现场侦探问题

如果一个 PR 功能正确，但破坏了模块边界，要不要放过？

短期看，放过很轻松。

长期看，它会让后面每个修改都变重。

资深工程师要学会在两件事之间平衡：

```text
业务交付
工程可持续
```

工程治理不是阻止业务，而是保护业务以后还能继续快。

## 学习目标

学完本节后，你应该能够：

- 设计有效的 code review checklist。
- 区分必须立刻修的问题和可以记录的技术债。
- 使用 ADR 记录重要技术决策。
- 建立团队模块边界、发布、监控和复盘节奏。
- 让治理动作进入日常开发，而不是变成阶段性运动。

## 第一部分：代码评审看什么

Android 大型工程的 review 可以看这些层次：

| 层次 | 问题 |
| --- | --- |
| 功能正确性 | 是否满足需求，边界条件是否处理 |
| 架构边界 | 模块依赖、接口、数据流是否清晰 |
| 并发与生命周期 | 协程取消、线程切换、生命周期泄漏 |
| 性能 | 主线程耗时、重组、内存、图片、I/O |
| 稳定性 | crash、ANR、异常恢复、降级 |
| 安全与隐私 | 权限、日志、存储、组件暴露 |
| 可测试性 | 是否有单测、Fake、关键路径测试 |
| 可观测性 | 是否有必要日志、埋点、错误码和 traceId |
| 发布风险 | 配置、开关、灰度、回滚、兼容 |

review 不应该只看代码风格。

风格可以自动化，判断要靠工程经验。

## 第二部分：Review Checklist

可以为团队准备一份轻量清单：

```text
这个改动影响哪些模块？
有没有新增不合理依赖？
有没有主线程 I/O 或长任务？
有没有生命周期泄漏风险？
有没有新增权限、组件或外部入口？
有没有新增日志，是否脱敏？
有没有对应测试或手动验证说明？
有没有埋点、监控或错误码？
有没有灰度和回滚方案？
```

清单不需要每次变成繁琐流程。

它的价值是提醒团队不要漏掉高风险点。

## 第三部分：技术债怎么处理

技术债不是坏代码的礼貌叫法。

技术债应该具备：

```text
上下文
风险
影响范围
偿还方案
优先级
负责人
截止时间或触发条件
```

例如：

```text
问题：feature:course 直接依赖 feature:download
风险：后续下载模块改造会影响课程模块编译和发布
影响：课程详情页、离线课程入口
方案：抽出 DownloadNavigator contract，由 app 层装配实现
优先级：P1
触发条件：下载中心二期开始前必须完成
```

这样的技术债才可管理。

只写“后续优化”，基本等于没有写。

## 第四部分：ADR：记录重要决策

ADR 是 Architecture Decision Record。

它适合记录：

```text
为什么拆这个模块？
为什么选择 WorkManager 而不是前台服务？
为什么从 KAPT 迁移到 KSP？
为什么使用某个监控方案？
为什么保留或废弃某个动态化方案？
```

一个简单 ADR 可以包含：

```text
标题
背景
决策
备选方案
取舍
影响范围
回滚方式
```

ADR 的价值不是证明当时永远正确。

而是让后来的人知道：

```text
当时为什么这么选。
```

## 第五部分：治理节奏

工程治理不能只在项目快崩时做。

可以建立节奏：

| 节奏 | 动作 |
| --- | --- |
| 每个 PR | review checklist、测试、lint、依赖边界 |
| 每周 | CI 慢点、失败率、线上告警回看 |
| 每个版本 | 发布复盘、包体积、crash / ANR / 性能指标 |
| 每月 | 技术债排序、依赖升级、模块依赖图 |
| 每季度 | 架构回顾、工具链升级、治理规则调整 |

治理像整理书桌。

每天一点点，就不容易变成灾难现场。

## 第六部分：不要让治理变成负担

治理也会过度。

常见问题：

```text
规则太多，没人记得住。
流程太重，改一行代码也要填一堆表。
指标太多，但没人负责行动。
review 变成主观争论。
技术债列表很长，但没有优先级。
```

好的治理应该满足：

```text
少而关键
能自动化就自动化
能给反馈就给反馈
能减少重复事故
能让新人更快理解工程
```

如果一条规则不能保护风险，也不能提升效率，就应该重新审视它。

## 本节自测

- code review 为什么不应该只看代码风格？
- 一个技术债条目至少应该包含哪些信息？
- ADR 解决的是什么协作问题？
- 治理节奏为什么比一次性大整顿更重要？
- 怎样避免工程治理变成团队负担？

## 本节总结

大型工程治理最终是团队协作问题。

工具、脚本、CI、监控都很重要，但它们背后的目标是：

```text
让团队形成共同判断。
让风险提前暴露。
让经验可以传递。
让事故不白发生。
让工程越长越稳，而不是越长越乱。
```

这就是资深工程师需要承担的工程责任。
