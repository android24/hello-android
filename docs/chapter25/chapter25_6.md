# 25.6 监控、告警、性能基线与事故复盘

第 24 章讲的是如何拿证据。

第 25 章要继续追问：

```text
线上问题出现时，系统能不能主动告诉我们？
问题修复后，团队能不能避免下一次再踩同一个坑？
```

这就是监控、告警、基线和复盘。

## 本节先记住三句话

```text
没有监控，线上事故只能等用户告诉你。
没有基线，性能好坏只能凭感觉。
没有复盘，同类事故会换个姿势回来。
```

## 贯穿案例：用户比监控更早发现问题

课程 App 新版本上线后，用户在社区反馈：

```text
打开详情页很慢。
下载进度偶尔卡住。
晚上同步失败。
某些机型闪退。
```

团队打开监控平台，发现：

```text
crash 有，但没有按版本和机型聚合。
ANR 有，但没有关联用户路径。
启动耗时有平均值，但没有 p95。
业务失败有日志，但没有和 release 版本关联。
Perfetto trace 只有本地采集，没有线上巡检。
```

问题不是没有数据。

问题是数据没有变成可行动的信号。

## 现场侦探问题

一个告警响了，你会马上叫醒所有人吗？

不一定。

你要先判断：

```text
是否超过阈值？
是否持续发生？
是否影响核心路径？
是否集中在新版本？
是否集中在某些设备或系统版本？
是否有自动止血方式？
```

告警不是越多越好。

好的告警应该让人行动，而不是让人麻木。

## 学习目标

学完本节后，你应该能够：

- 区分 crash、ANR、性能、业务和体验监控。
- 设计启动、卡顿、内存、网络、后台任务等指标基线。
- 理解告警阈值、分级、聚合和降噪。
- 把第 24 章证据链接入线上事故诊断。
- 编写事故复盘报告，并把复盘动作落到工程改进。

## 第一部分：监控要覆盖哪些层

大型 Android 工程至少要关注：

| 层级 | 指标 |
| --- | --- |
| 稳定性 | crash-free、ANR rate、native crash、OOM |
| 性能 | 启动耗时、慢帧、卡顿、内存、包体积 |
| 业务 | 登录成功率、课程加载成功率、下载成功率、支付成功率 |
| 后台任务 | 同步成功率、任务延迟、重试次数、失败原因 |
| 安全与合规 | 权限拒绝、组件异常访问、敏感日志、证书异常 |
| 发布 | 版本分布、灰度比例、渠道、配置版本 |

只看 crash 不够。

用户体验坏掉时，App 不一定会崩。

## 第二部分：性能基线

性能基线是“正常状态”的记录。

例如：

```text
冷启动 p50 / p90 / p95
课程详情首帧 p50 / p95
列表滑动 jank rate
首页内存 PSS
下载任务成功率
后台同步延迟
包体积大小
```

没有基线时，你只能说：

```text
好像变慢了。
```

有基线时，你可以说：

```text
2.5.0 版本课程详情首帧 p95 从 680ms 上升到 1450ms，
问题集中在 Android 13、低内存设备和首次打开场景。
```

这就是可行动信息。

## 第三部分：告警设计

告警要分级：

| 级别 | 例子 | 动作 |
| --- | --- | --- |
| P0 | 大面积崩溃、核心功能不可用 | 立即止血、暂停发布、回滚 |
| P1 | 新版本 crash / ANR 明显升高 | 降灰度、定位根因、热修或回滚 |
| P2 | 性能 p95 回退、局部业务失败 | 排期修复、观察趋势 |
| P3 | 指标轻微波动、非核心路径异常 | 记录和持续观察 |

阈值不要凭空拍脑袋。

可以先用历史基线设计一张观察表：

| 指标 | 正常范围 | P1 示例 | P0 示例 |
| --- | --- | --- | --- |
| crash-free | >= 99.90% | 新版本低于 99.70% 且持续 30 分钟 | 核心路径崩溃导致大面积不可用 |
| ANR rate | <= 0.20% | 新版本翻倍并集中在同一入口 | Top 页面大面积无响应 |
| 冷启动 p95 | <= 1800ms | 比基线上升 40% | 首屏长时间不可用并影响转化 |
| 慢帧率 | <= 8% | 新版本上升到 15% | 核心列表或播放页严重卡顿 |
| 登录成功率 | >= 99.50% | 下降超过 1% | 登录链路不可用 |
| 下载成功率 | >= 98.00% | 下降超过 3% | 离线能力大面积失败 |

真实阈值要结合业务规模、历史数据和容忍度调整。

表里的数字不是标准答案，它们的价值是提醒你：

```text
告警应该围绕基线、变化幅度、持续时间和影响范围设计。
```

告警还要降噪：

```text
同类异常聚合
按版本和设备分组
设置持续时间窗口
过滤已知问题
避免重复通知
```

告警如果每天乱响，团队最后会学会不看它。

## 第四部分：证据链如何接入线上事故

第 24 章的证据链可以进入线上流程：

```text
监控告警
  -> 版本 / 设备 / 用户路径聚合
      -> log / crash / ANR 证据
          -> dumpsys / bugreport / trace 复现采集
              -> 根因分析
                  -> 修复和灰度
                      -> 指标回归
                          -> 复盘沉淀
```

线上不一定能拿到完整 Perfetto。

但本地复现、灰度设备、测试机和专项巡检可以补齐证据。

关键是报告格式统一：

```text
现象
影响范围
证据
根因
止血
修复
回归
预防
```

## 第五部分：事故复盘

复盘不是追责。

复盘是让系统变好。

一份复盘至少回答：

```text
发生了什么？
什么时候发现？
影响了谁？
监控为什么没有及时发现？
为什么发布流程没有拦住？
为什么测试没有覆盖？
修复是什么？
如何证明修复有效？
如何防止再次发生？
```

如果复盘最后只有“以后注意”，那就等于没有复盘。

有效改进应该进入：

```text
测试用例
lint 规则
CI 门禁
发布 checklist
监控指标
告警规则
文档和培训
```

## 第六部分：监控也要保护隐私

监控和日志会接触用户数据。

所以要注意：

```text
不要上传 token、手机号、身份证、精确定位等敏感信息。
用户标识要脱敏或哈希。
日志字段要分级。
本地 debug 日志和线上日志策略不同。
bugreport、trace 和截图外发要控制范围。
```

第 23 章讲安全，第 24 章讲证据，第 25 章要把它们变成团队流程。

## 本节自测

- 为什么 crash-free 不能代表完整用户体验？
- 性能基线为什么要看 p95，而不是只看平均值？
- 告警为什么需要分级和降噪？
- 事故复盘为什么不能只写“以后注意”？
- 监控体系和隐私保护之间如何平衡？

## 本节总结

监控、告警、基线和复盘，是大型工程的反馈系统。

它们让团队从：

```text
用户反馈了才知道
```

走向：

```text
系统先发现，团队能定位，修复能验证，经验能沉淀。
```

这就是工程治理真正落地的样子。
