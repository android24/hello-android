# 25.8 综合实践：大型工程治理工作台

第 25 章最后一节，我们把模块边界、构建效率、依赖资源治理、发布流程、监控告警和团队协作放进一个综合实践。

目标不是做一个华丽页面。

而是让读者体验一次真实的大型 Android 工程体检。

## 本节先记住三句话

```text
治理实践要从风险开始，不要从表格开始。
每一项检查都应该对应一个真实工程事故。
最终输出不是“看起来规范”，而是一份可行动的工程治理报告。
```

## 贯穿案例：课程 App 发版前体检

假设 `Hello Android 学习中心` 准备发布 `2.5.0`。

发布前要检查：

```text
模块依赖有没有越界
构建耗时有没有恶化
依赖版本有没有冲突
资源和权限有没有异常变化
release 配置是否正确
mapping 和 symbols 是否归档
灰度指标是否准备
监控告警是否覆盖
技术债是否影响本次发布
```

这个实践就是一次“工程治理体检”。

## 现场侦探问题

如果只能在发版前做五项检查，你会选什么？

推荐优先级：

```text
release 构建是否成功
签名 / mapping / symbols 是否正确
权限 / 组件 / 配置是否异常变化
crash / ANR / 性能基线是否准备
灰度和回滚方案是否明确
```

因为它们直接决定事故能否被拦住、发现和止血。

## 本节定位

本节是第 25 章综合实践。

配套示例工程位于：

```text
examples/25-engineering-governance-lab/
```

它是一个“工程治理工作台”：页面中展示模块图、构建耗时、依赖风险、发布清单、监控指标和技术债看板；代码中用 fake 数据模拟真实工程状态，让读者通过切换事故剧本、选择风险证据、完成检查任务和阅读自动生成的治理报告，完成一次发版前体检。

## 学习目标

学完本节后，你应该能够：

- 为大型 Android 工程设计治理检查项。
- 把模块、构建、依赖、资源、发布和监控风险放到同一张图里。
- 输出一份发版前工程治理报告。
- 区分阻塞发布的问题和可延期技术债。
- 把第 24 章的证据链能力接入第 25 章的治理流程。

## 第一部分：Demo 应该包含哪些区域

第 25 章 Demo 可以设计成这些区域：

- `治理总览`：显示工程健康分、阻塞项、风险项、可延期项。
- `模块边界图`：展示 feature / core / app 的依赖方向，并标出越界依赖。
- `组件治理区`：展示组件独立运行、路由契约、接口隔离和跨组件调用风险。
- `构建效率面板`：展示本地构建、CI、最慢 task、缓存命中率。
- `依赖资源面板`：展示依赖冲突、资源新增、权限变化、包体积变化。
- `插件化风险区`：展示宿主插件协议、资源隔离、签名校验、崩溃归因和回滚状态。
- `发布检查清单`：签名、mapping、symbols、R8、灰度、回滚。
- `监控告警面板`：crash-free、ANR、启动、卡顿、业务成功率。
- `技术债看板`：按 P0 / P1 / P2 / P3 管理技术债。
- `治理报告`：自动汇总现象、证据、风险、决策和后续动作，并支持复制或分享。

## 第二部分：体验评分怎么设计

Demo 可以设计 16 个观察点：

| 观察点 | 得分条件 |
| --- | --- |
| 模块边界 | 找出至少一个越界依赖 |
| 组件契约 | 判断组件是否绕过 contract 直接依赖实现 |
| 依赖方向 | 判断 feature 是否依赖了不该依赖的模块 |
| 构建耗时 | 找出最慢 task |
| 缓存命中 | 判断缓存命中率是否低于阈值 |
| 依赖冲突 | 找出一个传递依赖风险 |
| 资源变化 | 判断资源或包体积是否异常增长 |
| 插件风险 | 判断插件协议、资源、签名或回滚是否存在阻塞项 |
| 配置检查 | 确认 release 环境配置 |
| 权限变化 | 找出新增权限或 exported 组件 |
| 签名检查 | 确认 release 签名状态 |
| 符号归档 | 确认 mapping / symbols 是否保存 |
| 灰度方案 | 设置灰度比例和观察指标 |
| 监控告警 | 判断指标是否触发告警 |
| 技术债排序 | 区分阻塞项和延期项 |
| 治理报告 | 写出发布结论和后续动作 |

评分不是为了游戏化而游戏化。

它是为了让读者知道自己有没有完成一次完整体检。

配套 Demo 还提供了三种治理规则：

| 治理规则 | 适合场景 | P1 风险处理方式 |
| --- | --- | --- |
| 保守门禁 | 支付、账号、安全和大版本发布 | 先修复再灰度 |
| 平衡灰度 | 普通业务迭代 | 仅允许小流量灰度 |
| 快速实验 | 内部实验和低风险功能 | 可以 1% 实验灰度 |

这样读者可以看到：工程治理不是永远同一套标准，而是根据业务风险调整阈值。但 P0 底线不能被策略绕过。

可以再加一张发布决策表，让 Demo 不只显示分数，还能给出发布建议：

| 风险等级 | 判断条件 | 发布决策 |
| --- | --- | --- |
| P0 阻塞 | release 构建失败、签名错误、mapping / symbols 缺失、核心路径不可用、插件签名或协议校验失败 | 不允许发布 |
| P1 高风险 | 新版本 crash / ANR 明显升高、依赖冲突可能导致运行时错误、权限或组件异常变化、组件绕过 contract 调用核心能力 | 只能小流量灰度或先修复 |
| P2 可控风险 | 构建耗时回退、非核心性能指标下降、技术债影响局部模块 | 记录负责人和期限后谨慎发布 |
| P3 观察项 | 文档缺失、命名不清、非核心体验优化 | 不阻塞发布，但进入后续治理 |

最终决策可以由两部分组成：

```text
健康分
  -> 帮助读者快速了解工程状态

阻塞规则
  -> 决定这次能不能发布
```

健康分高，不代表一定能发。

例如：

```text
总分 88 分，但 mapping 缺失。
```

结论仍然应该是：

```text
暂停发布。
```

因为一旦线上 crash，团队无法还原混淆堆栈。大型工程治理里，某些底线项不能被平均分掩盖。

## 第三部分：发布前治理报告模板

最终报告可以这样写：

```text
版本：
构建号：
Git commit：
检查时间：

发布结论：
  -> 可以发布 / 暂停发布 / 降低灰度 / 需要修复后再发

阻塞问题：
  -> P0 / P1 风险和证据

可延期问题：
  -> 技术债、影响范围、负责人、触发条件

模块边界：
  -> 是否存在越界依赖

组件 / 插件治理：
  -> 组件契约、独立运行、宿主插件协议、资源隔离、签名校验

构建效率：
  -> 本地构建、CI、最慢 task、缓存命中率

依赖资源：
  -> 依赖冲突、资源变化、包体积变化、权限变化

发布链路：
  -> 签名、mapping、symbols、R8、灰度、回滚

监控基线：
  -> crash、ANR、启动、卡顿、核心业务指标

回归计划：
  -> 关键路径、设备、版本、灰度观察窗口
```

这份报告要能支撑一个明确决策：

```text
发。
不发。
降灰度。
先修复。
带着已知技术债发布。
```

Demo 中的报告支持复制和分享。这样读者可以把它当成一次小型发版评审材料，而不是停留在页面里的展示文本。

## 第四部分：治理工作台里的事故剧本

Demo 可以模拟几个剧本：

| 剧本 | 表面现象 | 隐藏风险 | 应做决策 |
| --- | --- | --- | --- |
| 剧本 A：模块越界 | 功能能跑 | feature 直接依赖另一个 feature 实现 | 暂缓合并或抽 contract |
| 剧本 B：构建变慢 | CI 从 16min 到 31min | KAPT task 全量重跑 | 标记 P1 技术债 |
| 剧本 C：依赖冲突 | 编译成功 | release 运行可能 NoSuchMethodError | 阻塞发布 |
| 剧本 D：权限新增 | 新增读取媒体权限 | 合规和商店审核风险 | 必须评审 |
| 剧本 E：mapping 丢失 | release 包已生成 | crash 无法还原 | 阻塞发布 |
| 剧本 F：灰度异常 | crash-free 下降 | 新版本集中崩溃 | 降灰度或回滚 |
| 剧本 G：组件契约失控 | 支付能打开 | 课程模块直接调用支付实现类 | 抽 contract 后再合并 |
| 剧本 H：插件协议不兼容 | 插件能下载但启动失败 | 宿主协议版本低于插件要求 | 阻塞发布或升级宿主 |

每个剧本都要问：

```text
证据是什么？
影响范围是什么？
是否阻塞发布？
谁负责处理？
如何验证修复？
```

## 第五部分：和第 24 章如何衔接

第 24 章教你写事故证据链。

第 25 章要把证据链放进工程流程：

```text
发版前
  -> 检查风险证据

灰度中
  -> 观察线上指标

事故时
  -> 采集 logcat / dumpsys / bugreport / Perfetto

修复后
  -> 输出回归证据

复盘后
  -> 增加门禁、监控或文档
```

这样，事故不只是被解决。

事故会推动工程变好。

## 第六部分：通往第 26 章的交接清单

如果第 26 章是整门课程的毕业项目，那么完成第 25 章后，读者应该带着一套可复用材料进入终章。

这套材料不是形式感，而是资深工程师在真实项目里会反复使用的工作底稿：

| 交接材料 | 说明 | 对应能力 |
| --- | --- | --- |
| 模块边界图 | 说明 app、feature、core、domain、data、plugin 谁能依赖谁 | 架构治理 |
| 依赖和资源检查 | 记录依赖冲突、资源前缀、权限、包体积和配置变化 | 变更治理 |
| 构建效率快照 | 记录本地构建、CI、最慢 task、缓存命中率 | 反馈速度治理 |
| 发布门禁清单 | 记录签名、mapping、symbols、灰度、回滚和配置版本 | 发布治理 |
| 监控基线 | 记录 crash-free、ANR、启动、卡顿、业务成功率 | 线上反馈治理 |
| 技术债清单 | 记录 P0 / P1 / P2 / P3、负责人、截止时间和触发条件 | 长期演进治理 |
| 工程治理报告 | 汇总本次是否能发布、为什么、怎么验证、如何复盘 | 综合判断能力 |

配套 Demo 中的模板可以作为第 26 章毕业项目的起点：

```text
examples/25-engineering-governance-lab/quality/capstone-governance-handoff-template.md
```

第 26 章可以要求读者把这份交接材料扩展成最终答辩报告：

```text
我做了什么
为什么这样设计
如何证明它能运行
如何证明它可维护
如何证明它能发布
如何证明它出问题后能被定位和治理
```

这就是从“会写功能”到“能负责工程”的最后一步。

## 第七部分：本章通关检查

完成第 25 章后，你应该能回答：

- 这个工程有哪些模块边界？
- 哪些依赖方向不能被打破？
- 构建慢时你会先看哪些证据？
- 发布前哪些检查必须自动化？
- 灰度异常时如何止血？
- 监控告警如何避免噪声？
- 技术债如何记录和排序？
- 一次事故如何沉淀成规则、测试、门禁或文档？

## 本节总结

第 25 章把 Android 工程从“功能开发”推进到“系统治理”。

它关心的不只是一个页面、一个 API 或一个 bug。

它关心的是：

```text
工程能不能继续长大。
团队能不能继续协作。
发布能不能继续稳定。
问题能不能继续被发现、定位、修复和预防。
```

当你能用这套视角看 Android 工程，你已经非常接近资深工程师的工作方式。
