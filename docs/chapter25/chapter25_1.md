# 25.1 为什么要学习大型 Android 工程治理

第 1 章到第 24 章，我们已经走过了很长一段路。

你已经知道：

```text
页面如何写
数据如何流动
架构如何分层
模块如何拆分
系统如何启动 Activity
窗口如何显示
输入如何分发
一帧如何渲染
资源、代码、进程、安全和观测工具如何协作
```

第 25 章要把这些能力收回来，问一个更像资深工程师的问题：

```text
当一个 Android 工程变大以后，怎样让它继续可维护、可构建、可发布、可观测、可协作？
```

这就是大型 Android 工程治理。

## 本节先记住三句话

```text
工程治理不是写更多规则，而是减少系统失控。
大型工程的问题通常不是单点技术问题，而是边界、流程和反馈失效。
资深工程师的价值，不只是能解决事故，还要让同类事故越来越少。
```

## 贯穿案例：Hello Android 学习中心变大了

课程 App 一开始很小：

```text
一个首页
一个详情页
一点本地数据
几个按钮
```

但如果它继续成长，就会出现新的复杂度：

```text
课程首页
学习计划
笔记系统
下载中心
账号登录
支付订阅
消息通知
离线同步
数据埋点
性能监控
多端实验
灰度发布
```

这时问题不再只是“这个页面怎么写”。

你会遇到：

```text
模块越来越多，谁能依赖谁说不清。
构建越来越慢，改一行代码要等很久。
依赖版本冲突，一个库升级牵动半个工程。
资源命名混乱，主题、图片和字符串互相覆盖。
发布流程靠人工，漏开关、漏混淆、漏签名时有发生。
线上出了问题，日志、监控、trace 和版本信息对不上。
团队协作靠口头约定，新人进来很难判断边界。
```

这些问题不是靠某一个新框架就能解决。

它需要治理。

## 现场侦探问题

如果一个工程出现下面这些现象，你觉得根因更可能在哪里？

```text
构建慢
  -> 只是机器不够好吗？

模块互相依赖
  -> 只是开发偷懒吗？

线上 crash 定位困难
  -> 只是日志打少了吗？

发布频繁翻车
  -> 只是测试不够认真吗？
```

大多数时候，答案都不是单点。

真正的问题可能是：

```text
架构边界没有被工具保护。
构建链路没有被持续度量。
质量门禁没有和发布流程绑定。
线上证据没有和版本、功能、实验、设备环境关联。
团队约定没有沉淀成文档、脚本和自动化检查。
```

第 25 章要做的，就是把这些问题变成可以治理的工程对象。

## 学习目标

学完本章后，你应该能够：

- 解释大型 Android 工程为什么会失控。
- 设计清晰的模块边界和依赖方向。
- 区分模块化、组件化和插件化在工程治理里的不同角色。
- 识别影响构建效率的常见原因。
- 建立依赖、资源、配置和发布治理意识。
- 理解灰度、监控、告警、回滚和复盘如何形成闭环。
- 把第 20 到第 24 章的证据链能力接入工程流程。
- 用工程规则保护团队协作，而不是只靠个人经验。

## 第一部分：大型工程失控的四个信号

大型工程不是因为文件多才复杂。

它复杂，是因为变化会互相影响。

常见失控信号有四类：

| 信号 | 表面现象 | 深层问题 |
| --- | --- | --- |
| 边界失控 | 模块互相引用、公共模块越来越胖 | 依赖方向不清晰 |
| 构建失控 | 编译慢、缓存命中低、CI 排队 | 构建链路不可观测 |
| 质量失控 | crash、ANR、性能回退频繁 | 门禁和证据链不足 |
| 发布失控 | 灰度翻车、回滚困难、配置混乱 | 发布流程缺少自动化和可追踪性 |

第 25 章会围绕这四个信号展开。

## 第二部分：工程治理不是管理口号

很多人听到“治理”，会以为它是流程文档。

但真正有效的工程治理应该落在具体工具上：

```text
模块依赖规则
Gradle convention plugin
版本目录
依赖锁定
资源命名约束
静态检查
单元测试和 UI 测试
CI 质量门禁
打包签名脚本
灰度配置
崩溃和性能监控
事故复盘模板
```

规则如果只写在文档里，很容易被忘掉。

规则如果进入脚本、插件、检查和流程，才会真的保护工程。

```text

```

这条路线会从代码边界走到交付边界，再走到线上反馈和团队协作。

如果第 26 章作为毕业项目，那么第 25 章就是它的最后一块准备工作。

第 26 章不应该再从零讲“什么是模块化、什么是发布、什么是监控”，而应该要求读者带着第 25 章的工程治理能力进入综合项目：

```text

```

换句话说，第 25 章负责把“工程能不能长期运转”讲清楚，第 26 章负责让读者证明“我能独立负责一个 Android 工程”。

## 本节总结

第 25 章要回答的是：

```text
一个 Android 工程变大以后，如何继续保持清晰、稳定和可演进？
```

工程治理不是把团队绑起来，而是让团队不用每天靠记忆和运气写代码。

当边界被工具保护，质量被门禁守住，发布可以追踪，线上问题有证据可查，团队才能真正放心地向前走。
