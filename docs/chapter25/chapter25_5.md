# 25.5 发布、签名、灰度、回滚与版本治理

写完代码不等于完成交付。

大型 Android 工程真正危险的地方，常常在发布链路：

```text
签名错了
渠道错了
灰度范围错了
混淆规则错了
mapping 没保存
远程开关误开
线上异常无法回滚
```

第 25 章必须讲发布，因为发布是工程治理接受现实检验的地方。

## 本节先记住三句话

```text
发布不是最后一步，而是一条可验证的工程链路。
灰度的目的不是慢慢发，而是用小流量提前发现问题。
回滚能力决定事故半径。
```

## 贯穿案例：一次看似成功的发布

课程 App 发布了 `2.5.0`。

发布当天一切正常：

```text
构建成功
测试通过
应用商店审核通过
灰度 5%
```

第二天问题出现：

```text
少数用户登录失败。
某些机型 Native Crash 上升。
课程下载功能不可用。
监控只看到 crash，但拿不到对应 mapping 和 symbols。
灰度开关和版本号没有记录清楚。
回滚后部分配置仍然保持新版本状态。
```

这不是单纯“发版翻车”。

这是发布治理不完整。

## 现场侦探问题

如果线上 crash 突然升高，你第一反应是回滚吗？

有时应该立刻回滚。

但同时要问：

```text
影响版本是哪一个？
影响渠道是哪一个？
影响用户比例是多少？
是否只在某些 ABI / Android 版本 / 机型出现？
mapping 和 native symbols 是否能找到？
灰度开关是否可以关闭？
回滚 App 版本是否足够，还是还要回滚服务端配置？
```

发布事故也要有证据链。

## 学习目标

学完本节后，你应该能够：

- 理解 debug、release、flavor、variant 和渠道包的治理方式。
- 解释签名、mapping、symbols、版本号在发布诊断里的价值。
- 设计灰度、开关、回滚和热修策略。
- 建立发布前检查清单。
- 把 crash、ANR、性能和业务指标接入发版观察。

## 第一部分：版本治理

版本治理至少包含：

```text
versionName
versionCode
git commit
build number
flavor
build type
channel
ABI
mapping id
symbols id
remote config version
```

线上事故发生时，你要能回答：

```text
这个 crash 来自哪次构建？
它对应哪份源码？
它对应哪份 mapping？
它对应哪份 native symbols？
它启用了哪些远程开关？
```

如果答不上来，修复会很痛苦。

一个成熟发布系统应该让 crash 能反查到完整构建档案：

```text
crash event
  -> versionCode = 250010
      -> build number = 20260830.17
          -> git commit = a1b2c3d
              -> mapping id = map-250010-17
                  -> native symbols = symbols-arm64-250010-17
                      -> remote config version = rc-20260830-02
```

这样排查时你不是在问“这是不是最新包”，而是在问：

```text
这一次事故对应的代码、混淆映射、native 符号和配置状态分别是什么？
```

## 第二部分：签名和密钥治理

第 16、23 章讲过签名和安全。

第 25 章要从发布角度再看一次：

```text
debug key 不能用于正式发布。
release key 要有权限和备份策略。
签名配置不能随意暴露。
签名证书更换要考虑升级兼容。
签名权限依赖签名一致性。
供应链构建要保证产物可信。
```

签名不是发版时才处理的机械步骤。

它决定系统是否承认这是同一个 App。

## 第三部分：mapping 和 native symbols

如果开启 R8 / ProGuard，Java / Kotlin 堆栈会被混淆。

所以 release 构建必须保存：

```text
mapping.txt
seeds.txt
usage.txt
configuration.txt
```

如果有 native so，还要保存：

```text
unstripped .so
symbol file
ABI 信息
构建版本
```

否则第 20、24 章学到的 crash / tombstone / bugreport 证据会变成半截线索。

能看到崩溃，但不能还原现场。

## 第四部分：灰度发布

灰度不是把发布速度变慢。

灰度是控制事故半径：

```text
1%
5%
20%
50%
100%
```

每一档都要观察：

```text
crash-free rate
ANR rate
启动耗时
卡顿率
核心业务转化
登录成功率
下载成功率
用户反馈
```

如果没有观察指标，灰度只是心理安慰。

一个灰度事故可以这样串起来：

```text
10:00 发布 2.5.0，灰度 5%
10:20 crash-free 从 99.93% 降到 99.40%
10:25 crash 集中在 Android 12 + arm64 + 课程下载入口
10:28 通过 mapping 还原到 DownloadEncryptor.decrypt()
10:34 关闭 download_new_crypto 远程开关
10:45 crash-free 恢复到 99.91%
11:10 暂停继续放量，进入根因分析
```

这就是发布治理里的证据链：

```text
版本
  -> 指标变化
      -> 影响范围
          -> 符号还原
              -> 止血动作
                  -> 指标回归
```

## 第五部分：Feature Flag 和远程开关

远程开关可以降低风险：

```text
新功能先隐藏
异常时关闭入口
性能问题时降级效果
服务异常时切换策略
灰度特定用户群
```

但开关也会带来复杂度：

```text
开关组合爆炸
默认值不一致
客户端和服务端状态不同步
旧版本兼容困难
回滚 App 后配置仍然留在新状态
```

所以开关也要治理：

```text
命名清晰
有负责人
有过期时间
有默认值
有回滚方案
有监控指标
定期清理废弃开关
```

## 第六部分：回滚和止血

事故发生时，优先考虑止血：

```text
关闭远程开关
降低灰度比例
回滚服务端配置
暂停发布
回退 App 版本
下发降级策略
```

修复代码很重要。

但事故中更优先的是：

```text
先让影响不再扩大。
```

然后再进入证据分析、根因修复和复盘。

## 第七部分：发布检查清单

一个 release checklist 可以包含：

```text
版本号是否递增
release 签名是否正确
mapping / symbols 是否归档
R8 是否开启并验证
debug 日志是否关闭
权限变更是否评审
包体积是否异常
核心流程是否回归
灰度指标是否配置
远程开关默认值是否确认
回滚方案是否准备
```

这张表不是为了让发布变慢。

它是为了让发布不靠记忆。

## 本节自测

- 为什么 release 构建必须保存 mapping 和 native symbols？
- 灰度发布为什么必须配合监控指标？
- Feature Flag 带来的风险是什么？
- 回滚 App 版本一定能解决线上事故吗？
- 发布检查清单里哪些项目和第 23、24 章有关？

## 本节总结

发布治理是大型工程的最后一道门。

一个成熟发布流程应该满足：

```text
产物可追踪
签名可信
证据可还原
灰度可观察
异常可止血
修复可回归
复盘可沉淀
```

当发布链路清晰，团队才不会把上线当成赌博。
