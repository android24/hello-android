# 22.3 App 私有存储、缓存、Room、DataStore 与备份恢复

上一节我们把 Android 存储分成了几类：

```text
App 私有数据
App 缓存
共享媒体
用户文档
跨应用共享内容
```

这一节先处理最常见、也最容易被轻视的一类：App 自己的数据。

它看起来朴素：

```text
写文件
写数据库
写配置
清缓存
备份恢复
```

但很多线上事故都藏在这里。

## 本节定位

本节负责回答：

- `filesDir`、`cacheDir`、`externalFilesDir`、`externalCacheDir` 分别适合什么？
- Room、DataStore 和普通文件如何分工？
- 什么数据可以清理，什么数据不能随便清理？
- 备份恢复为什么会让数据库、文件和账号状态对不上？

## 学习目标

学完本节后，你应该能够：

- 为 App 私有数据选择合适位置。
- 区分持久数据、缓存数据、可再生数据和用户重要数据。
- 知道 Room、DataStore、文件存储各自适合的场景。
- 理解备份恢复会带来的数据一致性问题。
- 能设计一次“清缓存不误删”的排查和回归方案。

## 第一部分：App 私有数据也要分等级

App 私有数据不等于全部放在一个目录里。

先分四类：

| 数据类型 | 例子 | 推荐位置 | 是否可清 |
| --- | --- | --- | --- |
| 核心业务数据 | 课程进度、收藏、草稿 | Room / filesDir | 不可随便清 |
| 配置状态 | 登录态、开关、最后同步时间 | DataStore | 谨慎清理 |
| 可再生缓存 | 图片缓存、网络响应缓存 | cacheDir / externalCacheDir | 可以清 |
| 大体积 App 专属文件 | 离线课程包、中间产物 | externalFilesDir | 看业务承诺 |

你可以把 App 私有空间想成自己的工作台：

```text
账本
  -> 不能丢

便签
  -> 要谨慎

临时纸
  -> 可以扔

大箱子
  -> 扔之前要问清楚
```

清缓存事故大多发生在：

```text
把账本当临时纸扔了。
```

## 第二部分：filesDir：稳定但不适合所有东西

`filesDir` 是 App 内部私有目录。

适合：

```text
用户草稿
加密后的业务文件
小型私有 JSON
不希望其他 App 直接访问的数据
和数据库配套的附件索引
```

特点：

```text
默认只有本 App 可访问
卸载 App 后清理
不需要额外存储权限
适合保存 App 生命周期内的数据
```

但它不适合：

```text
用户明确要导出的文件
希望系统相册展示的图片
希望文件管理器长期可见的报告
可以大量增长的临时缓存
```

一个常见误区：

```text
filesDir 很安全，所以所有文件都放进去。
```

更准确的判断是：

```text
这份数据是否只属于 App？
如果用户认为它属于自己，就要提供导出、分享或保存到公共位置的入口。
```

## 第三部分：cacheDir：可以被清，不代表可以乱放

`cacheDir` 的语义是：

```text
为了提升性能保存的临时数据。
```

适合：

```text
图片缩略图
网络缓存
解压临时文件
上传前临时压缩包
预览用中间文件
```

不适合：

```text
唯一一份用户草稿
未同步的学习记录
用户购买后下载的离线课程唯一副本
无法重新生成的编辑结果
```

缓存有一句硬规则：

```text
缓存被清掉后，App 应该还能继续工作。
```

如果清掉后用户会丢数据，那它就不是缓存。

## 第四部分：externalFilesDir：大文件的 App 专属仓库

`getExternalFilesDir()` 常用于 App 专属但可能较大的文件。

例如：

```text
离线课程视频
课程资料包
导入后的原始包备份
日志压缩包
模型文件
```

它的优点：

```text
不需要把文件放进公共目录
比内部私有目录更适合大文件
卸载 App 时通常会被清理
```

它的风险：

```text
用户可能以为离线课程属于自己
清理空间时可能被系统或用户删除
不同设备和厂商文件管理展示不同
不能当成公共导出目录
```

所以离线课程要明确产品语义：

```text
这是 App 内可离线播放的缓存？
还是用户购买后可导出的文件？
```

前者可以放 App 专属目录；后者需要导出或公共文件能力。

## 第五部分：Room、DataStore、普通文件如何分工

不要把所有持久化都塞进数据库，也不要用 JSON 文件模拟数据库。

可以这样分：

| 工具 | 适合 | 不适合 |
| --- | --- | --- |
| Room | 结构化数据、列表、查询、事务 | 超大二进制文件 |
| DataStore | 小型配置、开关、token、时间戳 | 复杂关系查询 |
| 普通文件 | 二进制内容、文档、导入包 | 高频小字段更新 |
| MediaStore | 用户媒体 | App 私有业务状态 |
| SAF URI | 用户选择的文档 | App 内部私有缓存 |

课程 App 可以这样设计：

```text
Room
  -> 课程表、章节表、学习记录、下载任务索引

DataStore
  -> 当前账号、主题、同步水位、用户开关

filesDir / externalFilesDir
  -> 离线课程文件、草稿附件、导入包

cacheDir
  -> 图片缓存、临时压缩文件
```

## 第五部分补充：数据库和文件的一致性

真实项目里，很多数据不是单独存在的。

例如离线课程：

```text
Room 里有课程下载任务
Room 里有章节列表
externalFilesDir 里有视频文件
filesDir 里有字幕或索引
DataStore 里有最后一次校验时间
```

这时最危险的不是某个文件写失败，而是：

```text
数据库说它存在
  -> 文件其实不存在

文件已经写入
  -> 数据库没有索引

写了一半
  -> 页面误认为完成

清理了文件
  -> 没有同步清理索引
```

所以写入大文件时，建议按“事务感”设计，即使文件系统和数据库不能天然放进同一个事务，也要人为维护状态机：

```text
PENDING
  -> 写入临时文件
      -> 校验 size / hash
          -> rename 或标记为 READY
              -> 更新数据库索引
                  -> 删除旧文件或半成品
```

一个更稳的文件命名方式：

```text
course_1001.tmp
  -> 写入中

course_1001.mp4
  -> 校验完成后再暴露给业务
```

对应的 Room 字段可以是：

```text
download_state
local_uri
expected_size
actual_size
checksum
updated_at
last_error
```

这样即使进程在中途被杀，第 19 章讲过的进程回收发生了，也能在下次启动时恢复：

```text
发现 PENDING + tmp 文件
  -> 校验是否完整
      -> 完整则提交
      -> 不完整则删除重试
```

成熟的本地存储设计，往往不是一次 `writeBytes()`，而是一套可恢复状态机。

## 第六部分：备份恢复不是“复制回来就行”

备份恢复最容易制造幽灵事故。

例如：

```text
用户换新手机。
系统恢复了 App 的部分文件。
数据库里有下载记录。
真实离线文件没有恢复。
页面显示“已下载”，点击播放失败。
```

或者：

```text
DataStore 恢复了旧账号 token。
服务器已经失效。
App 以为用户登录了。
同步任务开始失败。
```

备份恢复需要考虑：

```text
数据库和文件是否成对恢复？
账号状态是否还能信任？
本地缓存是否应该参与备份？
下载文件是否应该重新校验？
加密密钥恢复后是否还能解密？
```

一个稳妥的恢复流程：

```text
App 首次启动
  -> 检查是否疑似恢复
      -> 校验账号状态
          -> 校验数据库和文件索引
              -> 缺失文件标记为需重新下载
                  -> 清理无主文件
                      -> 写入恢复日志
```

备份恢复还要特别注意“可再生数据”和“不可再生数据”的边界。

建议策略：

| 数据 | 是否建议备份 | 原因 |
| --- | --- | --- |
| 用户草稿 | 是 | 用户生成内容，丢失代价高 |
| 学习进度 | 视情况 | 服务端已有则可重新同步 |
| 登录 token | 谨慎 | 恢复后可能失效或带来安全风险 |
| 图片缓存 | 否 | 可再生，备份浪费空间 |
| 离线课程视频 | 视业务 | 文件大，可能可重新下载 |
| 导入后不可再生资料 | 是或提示用户 | 取决于版权、大小和恢复承诺 |

如果某份数据不参与备份，页面和恢复流程就要承认这一点：

```text
离线内容需要重新下载
缓存会重新生成
授权文件需要重新选择
```

不要让用户以为“App 恢复了”，结果内部其实只有一半恢复。

这也是第 20 章稳定性诊断的延伸：不要只修崩溃，要修数据一致性。

## 第六部分补充：敏感数据先划边界，安全细节留到第 23 章

第 22 章主要讲“数据放在哪里、谁能访问、系统如何索引”。

但只要聊到存储，就不能完全绕开敏感数据。

课程 App 里可能有这些敏感内容：

```text
登录 token
用户手机号、邮箱、头像原图
学习记录和付费状态
导入的私密课程资料
离线课程授权信息
错误日志里的账号或设备标识
导出的学习报告
```

本章先建立一个边界判断：

```text
普通业务数据
  -> 重点看归属、生命周期、备份和清理

敏感业务数据
  -> 除了归属，还要考虑加密、备份、日志脱敏和导出风险

用户导出数据
  -> 一旦交给用户选择的位置，App 不能再假设它仍处于 App 的保护边界内
```

例如：

| 数据 | 存储建议 | 安全提醒 |
| --- | --- | --- |
| 登录 token | DataStore / 加密存储策略 | 备份恢复后要重新校验有效性 |
| 学习报告 PDF | SAF 导出 | 导出后由用户保存，App 要提醒文件内容 |
| 错误日志 zip | filesDir / cacheDir 临时生成 | 分享前脱敏，过期清理 |
| 离线课程授权 | App 私有目录 / 数据库 | 不要随意导出到公共目录 |
| 头像裁剪图 | filesDir | 原始 Uri 权限失效后仍可展示 |

更深入的加密、签名、密钥、AppOps 和数据保护，会在第 23 章继续展开。

第 22 章先记住一句话：

```text
存储位置决定访问边界，敏感程度决定保护策略。
```

## 第七部分：清缓存功能如何设计

“清缓存”按钮看起来简单，实际很危险。

建议把清理对象分成：

```text
可立即清理
  -> cacheDir 缩略图、网络缓存、临时文件

需用户确认
  -> 离线课程包、导入包备份、大型日志

不可由清缓存清理
  -> 草稿、学习记录、数据库、登录状态
```

清理前应该展示：

```text
将释放多少空间
会影响哪些功能
是否需要重新下载
是否会删除用户生成内容
```

清理后应该记录：

```text
清理时间
清理类型
释放空间
失败文件
是否影响索引
```

这样出事故时，你才知道用户到底清了什么。

## 本节小结

App 私有存储不是“低级知识”，它是数据可靠性的地基。

```text
持久数据
  -> 要保护

缓存数据
  -> 可再生

大文件
  -> 要有索引和校验

备份恢复
  -> 要处理不完整状态

清理功能
  -> 要尊重数据等级
```

第 22.3 节的关键结论是：

```text
能写进去不代表设计正确。
能在异常、清理、迁移和恢复之后仍然解释清楚，才是成熟的存储设计。
```
