# 23.6 Keystore、加密存储、备份恢复与敏感数据保护

第 22 章我们讲过：

```text
存储位置决定访问边界
敏感程度决定保护策略
```

这一节就把“保护策略”展开。

敏感数据不能只靠：

```text
放进 filesDir
```

因为 filesDir 解决的是 App 沙箱内的默认隔离，不解决所有风险。

## 本节先记住三句话

```text
Keystore 主要保护密钥，不是拿来存所有明文数据。
密文能恢复不代表 key 能恢复，备份恢复必须设计失败路径。
日志、导出和崩溃报告也是数据出口，必须脱敏和最小化。
```

## 贯穿案例：换机后为什么登录态失效

`Hello Android 学习中心`把 token 加密后保存到本地。

用户换机恢复数据后，App 发现：

```text
本地密文还在，但无法解密。
```

这时不要先怪：

```text
Keystore 坏了。
```

要继续问：

```text
密文是否被系统备份恢复？
Keystore key 是否随设备恢复？
alias 是否还存在？
key 是否因为锁屏或生物识别变化失效？
token 在服务端是否仍然有效？
失败后是否能清理密文并重新登录？
```

本节要训练的是“安全可恢复”，不是只把数据加密起来。

## 安全侦探问题

用户换机后登录失败。

你看到异常：

```text
AEADBadTagException
```

你会把它先解释成什么？

```text
用户没登录
密文 / iv / tag / key 不匹配
网络失败
权限问题
```

请说明为什么不能直接把它当成普通登录态失效。

## 本节定位

本节负责回答：

- Android Keystore 解决什么问题？
- 加密存储和普通私有存储有什么区别？
- token、密钥、日志、导出文件应该如何分级？
- 备份恢复为什么会影响加密数据？
- 如何避免日志和导出文件泄露隐私？

## 学习目标

学完本节后，你应该能够：

- 理解 Keystore 是密钥保护系统，不是普通键值存储。
- 区分数据、密钥、密文和备份之间的关系。
- 能为 token、草稿、报告、日志设计不同保护策略。
- 知道备份恢复可能导致密钥不可用或账号状态失效。
- 能设计日志脱敏和导出确认流程。

## 本节阅读导航

这一节不要按“怎么调加密 API”来读，要按“数据从哪里来、会去哪里、失败后怎么办”来读：

```text
先看数据分级
  -> token、草稿、报告、日志到底哪个最敏感

再看密钥生命周期
  -> alias、key、iv、tag、密文分别承担什么角色

再看恢复失败
  -> 为什么密文恢复了，Keystore key 可能没有恢复

最后看出口治理
  -> 日志、导出文件、崩溃报告为什么也要做脱敏和确认
```

读完这一节，你要能把一句“token 解不开”拆成：

```text
密文是否还在？
key 是否还在？
iv / tag 是否匹配？
设备安全状态是否变化？
失败后是否能安全退出并重新登录？
```

## 第一部分：Keystore 保护的是密钥

Android Keystore 的核心是：

```text
把密钥生成和使用放进系统保护环境
让 App 尽量不要直接持有原始密钥材料
```

它不是：

```text
把所有数据塞进 Keystore
```

更常见的模式是：

```text
Keystore 生成或保护密钥
  -> App 用密钥加密敏感数据
      -> 密文保存到文件、数据库或 DataStore
```

也就是：

```text
Keystore 管钥匙
filesDir / Room / DataStore 存密文
```

这和第 22 章的存储入口可以组合起来。

## 第二部分：哪些数据需要额外保护

不是所有数据都需要同样强度保护。

先分级：

| 数据 | 风险 | 建议 |
| --- | --- | --- |
| UI 主题、开关 | 低 | DataStore 普通保存 |
| 学习进度 | 中 | Room / 服务端同步 / 账号校验 |
| 用户草稿 | 中 | 私有目录，必要时加密 |
| 登录 token | 高 | 加密存储、失效校验、备份谨慎 |
| 离线授权信息 | 高 | 加密、完整性校验、服务端兜底 |
| 错误日志 | 中到高 | 脱敏、过期清理、用户确认后导出 |
| 学习报告导出 | 取决于内容 | 导出前提示，用户选择位置 |

不要把安全做成：

```text
所有东西都加密
```

也不要做成：

```text
私有目录里就都安全
```

更成熟的做法是：

```text
根据数据敏感度、生命周期和用户预期选择保护等级
```

## 第三部分：token 不是普通配置

登录 token 常被随手放进 DataStore 或 SharedPreferences。

但 token 的语义是：

```text
谁拿到它
  -> 谁可能冒充用户访问服务端
```

所以 token 设计要考虑：

```text
本地是否加密
是否参与系统备份
恢复后是否重新校验
登出时是否清理
账号切换时是否隔离
日志里是否打印
崩溃报告里是否带出
```

一个稳妥流程：

```text
登录成功
  -> token 加密保存
      -> App 启动时解密读取
          -> 向服务端校验有效性
              -> 失效则清理并重新登录
```

不要把“本地还能读到 token”当成“用户仍然登录有效”。

## 第四部分：备份恢复和密钥生命周期

备份恢复对加密数据特别微妙。

可能出现：

```text
密文被恢复了
Keystore 里的密钥没有恢复
结果数据无法解密
```

或者：

```text
token 被恢复了
服务器已经认为它失效
App 误以为用户仍然登录
```

所以恢复流程要把敏感数据当作“不一定可信”：

```text
检测恢复
  -> 尝试读取加密数据
      -> 解密失败则清理密文并重新初始化
          -> token 读取成功也要服务端校验
              -> 重新建立账号状态和本地索引
```

这不是安全洁癖，而是避免幽灵登录、解密失败和数据错乱。

## 第五部分：日志脱敏

很多数据泄露不是被黑客攻破，而是自己写进日志。

常见危险日志：

```text
完整 token
手机号、邮箱、身份证
完整文件路径
用户选择的文档 Uri
接口请求参数
加密前明文
签名密钥路径
```

日志原则：

```text
默认不打印敏感字段
必要时只打印 hash、后四位或类型
线上日志和 debug 日志分级
导出日志前脱敏
日志有过期清理策略
```

例如：

```text
错误：token=eyJhbGciOi...
更好：tokenHash=8f3a..., tokenPresent=true
```

日志是证据，但不能把证据变成泄露源。

## 第六部分：导出文件的安全边界

第 22 章鼓励用户文档通过 SAF 导出。

第 23 章要补一句：

```text
导出之后，它就离开了 App 私有保护边界。
```

所以导出前要问：

```text
这个文件包含哪些敏感数据？
用户是否知道？
是否需要脱敏版本？
是否需要密码或加密格式？
是否应该设置过期？
是否应该提供删除入口？
```

比如学习报告可能包含：

```text
学习时间
课程偏好
账号昵称
设备信息
诊断日志
```

不要只说“导出成功”，还要让用户知道导出的是什么。

## 第七部分：敏感数据事故排查

### 事故一：备份恢复后登录态异常

排查：

```text
token 是否参与备份？
Keystore 密钥是否可用？
服务端是否仍认可 token？
DataStore 和 Room 是否恢复到同一状态？
```

### 事故二：用户上传日志后泄露隐私

排查：

```text
日志是否包含 token、手机号、Uri、路径？
脱敏规则是否生效？
导出前是否提示用户？
日志是否区分 debug 和 release？
```

### 事故三：离线授权被复制到其他设备

排查：

```text
授权文件是否绑定账号或设备？
是否加密？
是否校验完整性？
是否可以被备份恢复？
服务端是否有二次校验？
```

## 第七部分补充：Keystore 的关键不是“加密 API”，而是密钥生命周期

很多人学 Keystore 时，会把注意力放在：

```text
怎么生成 AES key
怎么 encrypt
怎么 decrypt
```

这些当然重要，但原理上更关键的是：

```text
密钥在哪里生成？
密钥能不能导出？
密钥什么时候可用？
密钥和用户认证、设备状态、备份恢复有什么关系？
密钥失效后业务怎么恢复？
```

### alias：App 拿到的是钥匙名，不是钥匙本体

使用 Keystore 时，App 通常通过 alias 找到密钥：

```text
hello_android_token_key
```

但成熟设计里，alias 也应该被纳入治理：

```text
alias 命名要区分业务和版本
key rotation 时要能识别旧 key 和新 key
删除账号时要删除对应 key
解密失败时要知道是 key 不存在、认证失败，还是密文损坏
```

不要把所有敏感数据共用一个永远不变的 alias。

更好的设计是：

```text
业务域
  -> token
  -> offline_license
  -> local_report

版本
  -> v1 / v2

账号或租户
  -> user scoped
```

这样后续迁移和事故排查才有抓手。

### TEE、StrongBox 和软件密钥

Keystore 并不意味着每台设备都用同一种硬件保护。

你可以按安全强度粗略理解：

```text
software
  -> 软件实现，保护强度依赖系统环境

TEE
  -> Trusted Execution Environment，密钥操作在可信执行环境中完成

StrongBox
  -> 独立安全硬件，安全边界更强，但性能和兼容性成本更高
```

StrongBox 不是越多越好。

它适合高安全风险场景，例如高价值凭证、金融身份、强设备绑定。

普通课程 App 的 token 加密，通常更需要：

```text
合理加密
服务端校验
过期策略
登出清理
日志脱敏
备份策略
```

而不是盲目要求所有设备都 StrongBox。

### 用户认证绑定

某些 key 可以要求：

```text
设备解锁后才能使用
用户通过锁屏密码或生物识别后才能使用
认证在一段时间内有效
```

这能提升安全性，但也会影响体验。

例如：

```text
每次打开课程 App 都要验证
  -> 安全更强，但学习体验变差

导出敏感报告前验证
  -> 安全和体验更平衡
```

所以安全设计不是把所有开关打开，而是匹配威胁模型：

```text
谁可能攻击？
攻击后损失多大？
用户愿意为这件事多做几步？
失败后怎么恢复？
```

### 备份恢复失败的真实根因

备份恢复后解密失败，常见根因不是：

```text
Keystore 坏了。
```

更常见的是：

```text
密文随 App 数据恢复到了新设备
但 Keystore key 没有以同样方式恢复
alias 存在但 key material 不匹配
设备安全状态变化导致 key 失效
用户认证绑定条件不满足
服务端 token 已经失效
```

所以恢复流程必须能区分：

```text
key missing
key permanently invalidated
bad padding / AEAD tag mismatch
token expired
server rejected
```

对应的产品策略也不同：

```text
key missing
  -> 清理密文，重新登录或重新生成本地数据

认证条件不满足
  -> 引导用户解锁或认证

token expired
  -> 静默刷新或重新登录

密文损坏
  -> 丢弃本地缓存，从服务端重建
```

这才叫“安全可恢复”。

## 第七部分补充二：Keystore 调用链路怎么拆

Keystore 问题也可以按“谁判断”的方式拆。

一个典型加密保存流程是：

```text
App 生成或获取 key alias
  -> Android Keystore Provider
      -> keystore2 / keystore service
          -> KeyMint / Keymaster
              -> TEE / StrongBox / software backend
                  -> 生成或使用不可导出的密钥
                      -> App 拿到加密结果或解密结果
```

注意：

```text
App 通常不应该拿到原始 key material。
```

App 拿到的是：

```text
alias
  -> 用来索引密钥

ciphertext
  -> 加密后的数据

iv / nonce
  -> 解密需要的随机参数

tag
  -> AEAD 模式下用于完整性校验
```

所以本地保存时，常见结构不是：

```text
保存 key + 保存 token
```

而是：

```text
Keystore 保存或保护 key
App 保存 ciphertext + iv + metadata
服务端保存 token 状态和失效策略
```

### 解密失败要分类型

Keystore 事故不能都写成：

```text
解密失败。
```

至少要区分：

```text
key not found
  -> alias 对应密钥不存在

key permanently invalidated
  -> 锁屏、生物识别、安全状态变化导致 key 不再可用

user not authenticated
  -> 当前用户未完成认证

bad padding / AEAD tag mismatch
  -> 密文、iv、tag 或 key 不匹配，可能是数据损坏或恢复错位

provider / hardware unavailable
  -> 设备实现、StrongBox 可用性或系统状态异常
```

对应修复也不同：

```text
key not found
  -> 清理密文并重新初始化

user not authenticated
  -> 引导用户认证

tag mismatch
  -> 不要继续相信本地密文，尝试服务端重建

hardware unavailable
  -> 降级到普通 Keystore 配置或提示设备不支持
```

### 密钥轮换和数据迁移

成熟项目里，密钥不是永远不变。

可能发生：

```text
加密算法升级
alias 命名规范调整
用户换账号
设备安全能力变化
旧 key 需要废弃
```

迁移流程建议写清楚：

```text
读取旧 alias
  -> 解密旧密文
      -> 用新 alias 重新加密
          -> 写入新密文和版本号
              -> 删除旧密文或标记迁移完成
                  -> 失败时保留可恢复路径
```

不要在启动时静默做不可逆迁移。

最好让迁移具备：

```text
版本号
回滚策略
错误日志脱敏
服务端兜底
用户重新登录路径
```

这会让 Keystore 从“API 使用”升级成“密钥生命周期治理”。

## 本节小结

敏感数据保护要同时看：

```text
放在哪里
  -> filesDir、Room、DataStore、MediaStore、SAF

怎么保护
  -> Keystore、加密、完整性校验

是否备份
  -> 恢复后能否解密、是否仍可信

是否泄露
  -> 日志、导出、分享、崩溃报告
```

第 23.6 节的关键结论是：

```text
私有目录是边界，加密和脱敏才是敏感数据的第二道门。
```
