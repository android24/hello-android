# 19.5 进程优先级、OOM Adj 与 LMKD：为什么后台进程会被杀

Android 不会无限保留所有进程。

当内存紧张时，系统会做选择。

本节进入一个非常现实的问题：

```text
为什么我的 App 在后台突然没了？
```

答案通常和进程状态、OOM Adj、LMKD、前后台行为和内存压力有关。

## 本节定位

本节负责回答：

- Android 如何判断一个进程重要不重要？
- OOM Adj 是什么？
- LMKD 如何参与低内存回收？
- 前台进程、可见进程、服务进程、缓存进程有什么区别？
- 为什么后台任务不能只靠“进程还活着”？

## 学习目标

学完本节后，你应该能够：

- 用工程语言解释进程优先级。
- 理解 OOM Adj 和进程回收的关系。
- 知道 LMKD 不是 Java GC。
- 能排查后台进程死亡、页面状态丢失和低内存重启问题。

## 第一部分：Android 为什么要杀后台进程

移动设备内存有限。

用户可能打开很多 App：

```text
聊天
浏览器
地图
视频
相机
你的 App
```

如果系统永远不回收后台进程，前台体验会被拖垮。

所以 Android 会保留一部分后台进程作为缓存，但在内存紧张时回收它们。

这不是异常行为，而是系统设计。

## 第二部分：进程重要性

进程重要性大致可以这样理解：

```text
前台进程
  -> 正在和用户交互，最重要

可见进程
  -> 用户还能看到，比如 Dialog 背后的 Activity

感知进程 / 前台服务相关进程
  -> 用户能感知其存在

服务进程
  -> 正在执行后台服务

缓存进程
  -> 暂时保留，方便下次快速回来
```

越靠后，越容易被回收。

所以后台 Activity 所在进程并没有“永久存活权”。

## 第三部分：OOM Adj 是什么

OOM Adj 可以理解成系统给进程计算的“可回收等级”。

它不是单纯由你写的代码决定，而是 AMS 根据进程当前状态、组件、可见性、服务绑定等因素综合计算。

```text
Activity 可见
  -> adj 更重要

只剩后台缓存
  -> adj 更容易被杀

有前台服务
  -> adj 可能提升
```

注意：

```text
OOM Adj 不是 Java 堆大小。
```

它是进程重要性相关指标。

Java heap 很大可能带来内存压力；但谁被杀，还要看系统整体内存和进程优先级。

更准确一点说，系统内部会同时维护多种和进程状态相关的信息。

你可以先区分两类：

```text
procState
  -> 更偏“进程当前处于什么运行状态”

oom_score_adj / adj
  -> 更偏“低内存时它有多容易被杀”
```

例如：

| 场景 | procState 直觉 | adj 直觉 |
| --- | --- | --- |
| 正在前台显示 Activity | 很重要 | 很不容易被杀 |
| 正在播放前台服务 | 用户可感知 | 不容易被杀 |
| 绑定到前台组件 | 被前台间接需要 | 重要性被提升 |
| 只剩后台缓存 Activity | 缓存 | 更容易被杀 |
| 空进程 | 仅为缓存保留 | 最容易被杀 |

这也是为什么一个后台 Service 如果被前台 Activity 绑定，重要性可能变化。

Android 不是只看“有没有 Service”，而是看这个进程和用户当前体验、前台组件、系统任务之间的关系。

## 第四部分：LMKD 如何参与低内存回收

LMKD 是 Low Memory Killer Daemon。

它关注系统内存压力，在需要时选择合适进程回收。

核心过程：

```text
系统内存紧张
  -> LMKD 观察内存压力
      -> 结合进程优先级 / OOM Adj
          -> 选择较不重要的进程
              -> 杀掉进程释放内存
```

它不是 Java GC。

区别如下：

| 机制 | 作用对象 | 目标 |
| --- | --- | --- |
| Java GC | 进程内部无用对象 | 回收当前进程堆内存 |
| LMKD | 整个进程 | 释放系统内存 |

如果 App 内存泄漏严重，GC 可能回收不了足够内存，进程占用越来越高，最终增加系统内存压力。

但 LMKD 杀进程是系统级行为，不是帮你清理某个对象。

从排查角度，LMKD 相关问题要看系统证据。

常见入口：

```text
adb shell dumpsys activity processes
adb shell dumpsys meminfo 包名
adb shell cat /proc/<pid>/oom_score_adj
adb logcat | grep -i lmk
adb logcat | grep -i lowmemory
```

其中 `/proc/<pid>/oom_score_adj` 很适合做观察实验：

```text
App 在前台
  -> 记录 oom_score_adj

按 Home 到后台
  -> 再记录 oom_score_adj

启动前台服务
  -> 再记录 oom_score_adj
```

你会看到系统对同一个进程的“可回收程度”不是固定的。

它会随着前后台、组件状态和系统判断而变化。

## 第五部分：后台进程被杀后的表现

进程被杀后，用户再次回到 App，可能出现：

- Application 重新创建。
- Activity 重新创建。
- 内存缓存丢失。
- ViewModel 丢失。
- 单例状态重置。
- 未持久化任务中断。
- 页面依赖旧状态导致空白或崩溃。

如果保存和恢复做得好，用户可能感觉不到太大异常。

如果把关键状态只放在内存里，问题就会暴露。

所以稳定性治理里有一句重要原则：

```text
重要状态不能只依赖进程存活。
```

这里要特别区分三个动作：

| 动作 | 直觉效果 | 关键差异 |
| --- | --- | --- |
| `am kill 包名` | 模拟后台进程被杀 | 通常不等同于用户主动停止 |
| `am force-stop 包名` | 强制停止应用 | 会让应用进入 stopped 状态，广播和后台行为也受影响 |
| 最近任务划掉 | 用户移除任务 | 不同系统和厂商行为可能不同 |

所以做实验时不要只用一种命令就下结论。

后台恢复问题至少要分别验证：

```text
配置变化
  -> Activity 重建

am kill
  -> 进程死亡后恢复

force-stop
  -> 应用被强制停止后的重新启动

低内存回收
  -> 系统压力下真实回收
```

## 第六部分：前台服务不是免死金牌

前台服务能提高进程重要性，但不是无限保护。

尤其在现代 Android 中，后台行为受到越来越多限制。

你需要区分：

- 用户可感知、合理的前台任务。
- 可以延迟的后台同步。
- 应该交给 WorkManager 的可靠任务。
- 不应该长时间占用资源的后台轮询。

为了“保活”滥用前台服务，既不符合系统设计，也会伤害用户体验。

## 第七部分：进程死亡排查路线

遇到“后台回来异常”，不要只看 Activity 生命周期。

可以按这条路线排查：

```text
是否发生进程重启
  -> pid 是否变化
      -> Application 是否重新 onCreate
          -> Activity savedInstanceState 是否恢复
              -> 关键状态是否持久化
                  -> 是否有低内存 / lmk 日志
                      -> 是否依赖后台进程长期存活
```

第一证据通常是：

- pid。
- process start 时间。
- Application 日志。
- savedInstanceState。
- 系统 low memory / lmk 日志。
- 任务是否持久化。

一份比较完整的后台死亡证据可以这样写：

```text
before:
  pid=23145
  processStart=10:21:03
  page=Home
  cacheToken=memory-only

after:
  pid=24880
  processStart=11:02:18
  Application.onCreate again
  savedInstanceState=null
  cacheToken=missing

conclusion:
  发生进程重建，页面依赖内存缓存，缺少持久化恢复路径。
```

这样你就不是在说“好像被系统杀了”，而是在给出证据链。

## 第八部分：和第 9 章稳定性治理的关系

第 9 章讲性能和稳定性。

第 19 章给它补底层解释。

```text
内存泄漏
  -> 进程占用增长
      -> 系统内存压力增加
          -> 后台进程更容易被回收

状态未保存
  -> 进程死亡后无法恢复
      -> 用户看到白屏、空数据或崩溃

后台任务依赖进程
  -> 进程被杀后任务中断
      -> 数据不同步或通知丢失
```

稳定性不是只靠 try-catch。

它也依赖你理解系统什么时候会收回运行空间。

## 本节小挑战

### 后台回来白屏题

用户反馈：

```text
App 切到后台半小时后，再回来首页白屏。
```

你会先查什么？

建议回答：

- pid 是否变化。
- Application 是否重新创建。
- Activity 是否通过 savedInstanceState 恢复。
- 首页数据是否只存在内存缓存。
- 是否有低内存或进程回收日志。
- 是否把后台任务误当成常驻进程任务。

## 本节实践任务

### 基础任务

- 打印 App 启动时 pid 和时间戳。
- 使用开发者选项“不要保留活动”观察状态恢复。
- 使用 `adb shell am kill 包名` 模拟后台进程被杀。
- 使用 `adb shell cat /proc/<pid>/oom_score_adj` 观察前后台 adj 变化。
- 使用 `adb shell dumpsys activity processes | grep 包名 -A 20` 观察系统记录的进程状态。

### 进阶任务

- 对比 `am kill`、`force-stop` 和从最近任务划掉的差异。
- 对比前台、后台、前台服务、绑定服务状态下的 oom_score_adj。
- 观察进程被杀后 ViewModel、单例、DataStore / Room 数据的变化。
- 写一份“后台回来异常”的排查报告。

## 本节小结

Android 会根据进程重要性和系统内存压力回收后台进程。OOM Adj 反映进程回收优先级，LMKD 在低内存时负责杀掉合适进程释放内存。进程死亡不是小概率玄学，而是移动系统的常态之一。关键状态必须能恢复，后台任务必须有可靠机制承接。
