# 19.7 进程体验问题：后台死亡、状态丢失、多进程错乱与保活误区

前面几节讲了进程如何创建、运行和回收。

本节把这些机制放回真实问题里。

你会发现很多“奇怪问题”其实都有进程证据。

## 本节定位

本节负责回答：

- 后台回来页面异常如何排查？
- Application 执行多次是不是 bug？
- 多进程状态不一致为什么发生？
- 为什么不要迷信保活？
- 进程相关问题的诊断报告应该怎么写？

## 学习目标

学完本节后，你应该能够：

- 用 pid 和 processName 判断是否发生进程重启。
- 区分 Activity 重建和进程重建。
- 解释多进程缓存不一致的原因。
- 知道后台任务、前台服务、WorkManager 的边界。
- 写一份进程体验问题诊断报告。

## 第一部分：后台回来页面异常

典型反馈：

```text
App 切后台一段时间后，再回来页面空白。
```

先不要急着怀疑 UI。

第一步看：

```text
pid 是否变化？
```

如果 pid 变化，说明进程已经重启。

这时问题可能不是“页面莫名其妙丢状态”，而是：

```text
进程被系统回收
  -> 内存状态丢失
      -> Activity 被重建
          -> 页面没有从持久化状态恢复
```

排查路线：

```text
pid
  -> Application 创建时间
      -> Activity savedInstanceState
          -> ViewModel 是否重建
              -> 数据是否持久化
                  -> 是否依赖内存缓存
```

## 第二部分：Activity 重建不等于进程重建

Activity 可以因为配置变化重建：

- 横竖屏。
- 深色模式。
- 字体大小。
- 多窗口。
- 系统回收后恢复。

但 Activity 重建不一定意味着进程重建。

判断方式：

```text
Activity onCreate 再次执行
  -> pid 没变
      -> 更像 Activity 重建

Activity onCreate 再次执行
  -> pid 变了
      -> 更像进程重建
```

这两个问题的修复方向不同。

Activity 重建更关注 UI 状态保存。

进程重建还要关注 Application 初始化、内存缓存丢失、后台任务恢复和持久化状态。

## 第三部分：多进程状态不一致

典型问题：

```text
主进程显示已登录
:push 进程认为未登录
```

可能原因：

- 登录态只保存在主进程内存。
- push 进程有自己的单例。
- SharedPreferences 跨进程读取时机不一致。
- DataStore / Room 没有按多进程场景设计。
- 初始化顺序不同。

第一证据：

```text
processName
pid
登录态来源
状态更新时间
IPC / 持久化同步方式
```

不要用“刷新一下就好了”掩盖设计问题。

多进程状态必须有明确的同步机制。

## 第四部分：后台任务突然中断

后台任务中断常见原因：

- 进程被杀。
- 后台执行限制。
- 网络 / 电量 / 存储约束不满足。
- 前台服务使用不合规。
- WorkManager 任务没有正确持久化。

如果任务必须可靠完成，不要只依赖：

```text
开启一个线程
  -> 希望进程一直活着
```

更稳的思路是：

```text
任务持久化
  -> 使用 WorkManager / 前台服务 / 系统能力
      -> 失败可重试
          -> 进程重启可恢复
```

进程存活不是可靠队列。

## 第五部分：保活误区

很多早期 Android 文章会讨论保活：

- 双进程守护。
- 静默拉活。
- 后台常驻。
- 滥用前台服务。
- 监听系统广播自启动。

现代 Android 对后台行为限制越来越严格。

课程不鼓励把“如何绕过系统限制”当成核心能力。

更值得学习的是：

```text
任务是否真的需要后台立即执行？
是否可以延迟？
是否应使用 WorkManager？
是否需要前台服务并明确告知用户？
是否能做到进程死亡后恢复？
```

资深工程师不是想尽办法让进程不死，而是让业务在进程会死的现实里仍然可靠。

## 第六部分：进程问题诊断表

| 现象 | 第一证据 | 可能原因 | 修复方向 |
| --- | --- | --- | --- |
| 后台回来白屏 | pid、Application 时间 | 进程被杀，状态未恢复 | 持久化关键状态、恢复 UI |
| 初始化执行两次 | processName、pid | 多进程各自启动 | 主进程判断、分流初始化 |
| push 状态不同步 | 登录态来源、进程 | 内存不共享 | IPC / 持久化同步 |
| 后台任务中断 | 任务记录、进程日志 | 依赖进程存活 | WorkManager / 前台服务 |
| remote 调用卡住 | Binder 线程栈 | 远程进程阻塞 | 异步、超时、死亡监听 |
| 低端机频繁重启 | 内存、lmk 日志 | 内存压力大，进程被回收 | 降内存、恢复状态 |

## 第八部分：案例拆解：通知进入详情页显示未登录

看一个更接近线上问题的例子。

现象：

```text
用户已经登录。
App 切后台 40 分钟。
用户点击推送通知进入订单详情页。
详情页显示未登录。
用户手动刷新后又恢复正常。
App 有 :push 进程。
```

不要先猜 UI。

先列证据：

```text
通知由哪个进程接收？
点击通知时主进程是否还活着？
点击后新 pid 是多少？
登录态存在哪里？
:push 进程是否有自己的 SessionManager？
详情页读取的是内存 token，还是持久化 token？
刷新后为什么恢复？
```

一种可能链路：

```text
用户登录
  -> token 写入主进程内存和磁盘
      -> App 进入后台
          -> 主进程被 LMKD 回收
              -> :push 进程仍收到通知
                  -> 点击通知拉起详情页
                      -> 主进程重新创建
                          -> 详情页先读内存 token
                              -> token 为空，显示未登录
                                  -> 手动刷新触发磁盘读取
                                      -> token 恢复
```

这时修复方向不是“详情页加延迟”，而是：

- 进程重建后先从持久化状态恢复登录态。
- 通知点击链路不要依赖 push 进程内存状态。
- 日志必须带 `processName`、`pid`、登录态来源。
- 登录态读取要有明确的同步和加载状态。
- 详情页要区分“未登录”和“登录态恢复中”。

这就是进程诊断的价值：它能把一个看似随机的体验问题，拆成可验证的系统链路。

## 本节小挑战

### 保活方案评审题

有人提出：

```text
我们做一个双进程守护，保证后台下载永远不中断。
```

你会如何评审？

建议回答：

- 是否符合现代 Android 后台限制？
- 用户是否能感知任务？
- 是否应该使用 WorkManager 或前台服务？
- 进程死亡后任务是否可恢复？
- 该方案是否增加耗电、合规和稳定性风险？

## 本节实践任务

### 基础任务

- 给日志统一增加 pid、processName、threadName。
- 用 `adb shell am kill 包名` 模拟后台进程死亡。
- 观察页面是否能恢复关键状态。

### 进阶任务

- 制造一个 remote 进程状态不同步问题。
- 写一份进程问题诊断报告。
- 给后台任务增加持久化和恢复逻辑。

## 本节小结

进程体验问题要用进程证据排查。后台死亡、Activity 重建、多进程状态错乱、后台任务中断和保活误区，本质都和进程状态、系统回收、内存压力、IPC 和任务可靠性有关。真正可靠的设计不是假设进程永远活着，而是在进程可能死亡的现实里仍能恢复。
