# 18.6 动态加载、插件化与热修复：能力边界与工程代价

理解 Dex、ClassLoader、ART 和 so 之后，就可以进入一个很有吸引力的话题：

```text
能不能运行时加载新的代码？
```

这会引出动态加载、插件化和热修复。

## 本节定位

本节负责回答：

- 动态加载、插件化、热修复分别是什么？
- 它们共同依赖哪些底层能力？
- 为什么插件化不仅是 DexClassLoader？
- 热修复为什么受类加载时机限制？
- 为什么现代工程中要谨慎使用这类能力？

## 学习目标

学完本节后，你应该能够：

- 区分动态加载、插件化和热修复。
- 说清楚它们和 ClassLoader、Resources、Manifest、so 的关系。
- 理解宿主与插件的边界。
- 能从工程成本角度判断是否值得引入。
- 知道线上热修复的风险。

## 第一部分：动态加载是什么

动态加载最小模型：

```text
运行时拿到一个 dex / apk
  -> 创建 DexClassLoader
      -> loadClass
          -> 反射调用入口
```

这只能说明“类可能被加载”。

它还不是完整插件化。

## 第二部分：插件化是什么

插件化通常想要的是：

```text
宿主 App
  -> 加载插件代码
  -> 加载插件资源
  -> 管理插件页面
  -> 处理插件生命周期
  -> 处理插件 so
  -> 管理插件版本和安全
```

所以插件化至少包含：

- ClassLoader。
- AssetManager / Resources。
- Activity / Service / BroadcastReceiver 生命周期代理。
- 依赖共享和隔离。
- so 解压与加载。
- 签名校验。
- 灰度和回滚。

插件化是一套系统工程，不是一个工具类。

## 第三部分：热修复是什么

热修复的目标通常更窄：

```text
线上出现 bug
  -> 下发补丁
      -> 修复某些类或方法
          -> 避免等待发版
```

常见思路包括：

- Dex 插桩或替换。
- ClassLoader dexElements 调整。
- native hook。
- 资源补丁。

但每种方案都有系统版本、加载时机、兼容性和安全边界。

## 第四部分：热修复为什么怕“类已经加载”

如果某个类已经被 ART 加载，后续再想替换它会变得困难。

很多补丁方案希望：

```text
补丁 dex
  -> 放在原 dex 前面
      -> ClassLoader 查找时先命中补丁类
```

但如果原类已经加载过，这条路就不顺了。

所以热修复往往要很早初始化，甚至在 Application 早期介入。

## 第五部分：插件资源为什么麻烦

插件代码能加载，不代表插件资源能加载。

插件资源需要：

```text
插件 APK 路径
  -> AssetManager 加载
      -> Resources 创建
          -> 插件 Context / 资源 ID 解析
```

还要处理宿主和插件资源 ID、主题、样式、图片、语言、密度。

这和第 17 章内容直接相连。

## 第六部分：依赖共享与冲突

宿主和插件可能都依赖同一个库：

```text
host -> common-lib v1
plugin -> common-lib v2
```

问题来了：

- 到底用哪个版本？
- 同名类由谁加载？
- 公共接口放在哪？
- 类型能不能强转？
- R8 混淆后入口是否还稳定？

插件化的很多事故，都不是加载失败，而是边界设计失败。

## 第七部分：是否应该引入插件化

适合考虑：

- 超大型 App。
- 强业务隔离。
- 独立发版需求。
- 明确灰度和回滚机制。
- 团队有长期维护能力。

不适合：

- 小项目为了炫技。
- 团队没有稳定基础设施。
- 只是为了减少几天发版等待。
- 缺乏安全和监控体系。

## 第八部分：动态加载排查表

| 现象 | 第一证据 | 可能原因 | 修复方向 |
| --- | --- | --- | --- |
| 插件类找不到 | plugin apk、dex path、ClassLoader | 下载失败、路径错误、混淆 | 校验文件、打印加载路径 |
| 插件页面打不开 | Manifest、代理 Activity | 组件未注册或生命周期未托管 | 使用宿主代理或注册策略 |
| 插件资源错乱 | Resources、AssetManager | 资源路径没加载、主题不对 | 创建插件 Resources 和 Context |
| 热修复不生效 | 类是否已加载 | 补丁加载太晚 | 提前初始化或调整补丁策略 |
| 插件 so 失败 | ABI、native path | so 未解压或 ABI 不匹配 | 处理 nativeLibraryPath |

## 本节小挑战

### 插件化边界题

如果一个插件页面需要：

```text
Activity 页面
Compose UI
图片资源
native so
和宿主共享登录态
```

你至少要设计哪些边界？

建议回答：

- 插件 ClassLoader。
- 插件 Resources。
- 页面生命周期托管。
- so 加载路径。
- 宿主 API 合同。
- 安全校验和版本协议。

## 本节小结

动态加载是能力，插件化是系统工程，热修复是高风险线上补救手段。它们共同依赖 Dex、ClassLoader、Resources、Manifest、so 和安全机制。理解第 18 章前几节后，你会发现插件化真正困难的不是“loadClass”，而是边界、生命周期、资源、依赖、安全和长期维护。
