# 11.3 AIDL、Stub、Proxy 与 Parcel

第 11.2 节里，我们认识了 Binder 调用模型。

这一节继续补三个常见名词：AIDL、Stub / Proxy、Parcel。

## 本节剧情钩子

跨进程办事不能只靠一句“帮我处理一下”。

你需要一张表格说明服务接口，需要一个前台窗口接收请求，需要把材料打包成系统能传递的格式。

AIDL 像服务协议，Stub / Proxy 像窗口两端，Parcel 像装材料的信封。

## 本节定位

本节不要求你立刻手写复杂 AIDL，而是先理解它们在 Binder 通信里的角色。

## 学习目标

学完本节后，你应该能够：

- 知道 AIDL 用来描述跨进程接口。
- 理解 Stub 和 Proxy 的分工。
- 知道 Parcel 负责数据序列化。
- 理解为什么跨进程传参有类型和大小约束。

## 第一部分：AIDL 描述接口

AIDL 的全称是 Android Interface Definition Language。

它用于描述跨进程可调用的接口。

例如可以想象有这样一个接口：

```text
interface ICourseService {
    String queryCourseTitle(int id);
}
```

真实工程里，AIDL 会生成 Java 接口和 Binder 相关代码，帮助你少写底层样板。

## 第二部分：Proxy 在客户端

客户端拿到的通常不是服务本体，而是代理。

Proxy 负责：

- 接收客户端方法调用。
- 把参数写入 Parcel。
- 发起 Binder transaction。
- 读取服务端返回结果。

所以客户端看起来像在调本地方法，其实 Proxy 正在帮它跨进程递材料。

## 第三部分：Stub 在服务端

Stub 在服务端接收 Binder 调用。

它负责：

- 读取 Parcel 中的参数。
- 找到对应方法。
- 调用服务端真实实现。
- 把结果写回 Parcel。

可以把 Stub 理解成服务端门口的接待台。

## 第四部分：Parcel 是跨进程信封

进程之间不能直接传普通对象引用。

数据需要被写入 Parcel，再在另一端读出来。

这就是为什么跨进程参数要关注：

- 是否可序列化。
- 数据量是否过大。
- 类型是否被支持。
- 版本变化是否兼容。

跨进程传输不适合塞大对象，也不适合频繁传复杂数据。

## 第五部分：Messenger 和 AIDL 的关系

第 11 章 demo 使用 `Messenger` 做远程 Service 通信。

它不是直接手写 AIDL，但底层仍然依赖 Binder。它适合教学演示，因为能用消息方式观察一次跨进程往返。

你可以先用 Messenger 理解：

```text

```

## 本节小结

AIDL 定义接口，Proxy 站在客户端，Stub 站在服务端，Parcel 负责打包数据。它们共同让跨进程调用看起来像普通方法，但背后仍然是明确的通信协议和数据传输过程。
