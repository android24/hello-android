# 11.2 Binder 通信模型：从本地调用到跨进程调用

Binder 最容易被误解的一点是：它看起来像普通方法调用，但实际上跨过了进程边界。

本节先不看驱动源码，只建立一张能用的通信图。

## 本节剧情钩子

你在 App 里调用一个方法，像是在自己房间里喊一声。

但调用系统服务时，目标对象在另一栋楼。你需要把请求交给一个窗口，窗口把材料送出去，对方处理完再把结果送回来。

Binder 让这件事看起来像“喊了一声就有回应”，但背后其实完成了跨进程递送。

## 本节定位

本节解释 Binder 调用的基本角色和流程。

## 学习目标

学完本节后，你应该能够：

- 区分本地方法调用和跨进程调用。
- 理解 Client、Proxy、Binder Driver、Server 的关系。
- 知道为什么 Binder 调用要关注线程、耗时和异常。
- 用 demo 观察一次远程 Service 消息往返。

## 第一部分：本地调用很直接

普通函数调用通常发生在同一进程内：

```text
对象 A
  -> 调用对象 B 的方法
      -> 共享同一进程内存
          -> 直接返回结果
```

这种调用成本低，失败边界也比较清楚。

## 第二部分：跨进程调用不共享内存

App 进程和系统服务进程不共享普通对象内存。

所以你不能直接拿到系统服务对象本体，只能拿到一个代理。

简化模型：

```text
Client 进程
  -> Proxy
      -> Binder Driver
          -> Stub
              -> Server 进程中的真实服务
```

Proxy 像你手里的窗口号码牌，Stub 像服务端接待窗口，Binder Driver 像楼与楼之间的传递通道。

## 第三部分：Binder 调用不是免费午餐

Binder 让跨进程调用写起来很像普通方法，但它仍然有成本：

- 参数需要打包。
- 线程需要切换。
- 服务端可能排队。
- 对端可能异常。
- 权限需要检查。

所以不要在主线程频繁做重型 Binder 调用。

## 第四部分：同步调用与异步感知

很多 Binder 调用是同步的：调用方会等待结果。

如果对端服务处理慢，调用方也可能被拖住。

这就是为什么 ANR 分析里经常能看到 Binder 相关等待。它不是 Binder “坏”，而是跨进程协作天然需要关注等待时间。

## 第五部分：demo 中的远程 Service

第 11 章 demo 会启动一个独立进程的远程 Service。

简化链路是：

```text
MainActivity
  -> bindService()
      -> 获取远程 Service 的 Binder
          -> 通过 Messenger 发送消息
              -> 远程进程处理消息
                  -> replyTo 回传结果
```

它不是系统服务，但它能帮助你观察 Binder 的基本味道：两个进程、一次请求、一次回复。

## 本节小结

Binder 的入门关键不是先背驱动细节，而是知道它把本地调用伪装成跨进程协作。只要你记住 Client、Proxy、Binder Driver、Stub、Server 这条线，后面再看 AIDL、系统服务和 ServiceManager 就有了落脚点。
