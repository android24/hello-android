# 24.7 观测体验问题：误读、隐私、复现与团队协作

会用工具，不等于会分析问题。

第 24 章最容易出现的误区是：

```text
采了一堆数据
贴了一堆截图
最后还是说不清根因
```

这一节不讲新命令，专门讲观测工具在真实团队里怎么用。

## 本节先记住三句话

```text
没有复现路径的证据，很难复盘。
没有时间点的证据，很难关联。
没有脱敏和结论的证据，很难协作。
```

## 贯穿案例：测试发来一份巨大的 bugreport

测试同学发来一个 80MB 的 bugreport，说：

```text
App 卡了一下，你看下。
```

这时你会很痛苦。

因为你不知道：

```text
什么时候卡？
卡在哪个页面？
做了什么操作？
卡了多久？
是否必现？
设备当时是否低电量、弱网、发热？
是否已经重启过 App？
```

证据不是越大越好。

证据要能被别人读懂。

## 现场侦探问题

如果你只能给测试提一个要求，你会提什么？

我建议是：

```text
请在复现问题后，记录问题发生的准确时间点和操作路径。
```

因为时间点能把 logcat、Perfetto、dumpsys、bugreport 串起来。

## 学习目标

学完本节后，你应该能够：

- 识别常见观测误读。
- 设计可复现、可对比、可共享的取证流程。
- 知道日志、bugreport、trace 的隐私风险。
- 能写出团队能理解的证据链报告。
- 能把工具输出转成工程决策。

## 第一部分：常见误读一：把相关当因果

你看到：

```text
掉帧附近有 GC。
```

不代表：

```text
一定是 GC 导致掉帧。
```

还要继续看：

```text
GC 是否发生在关键帧之前？
GC 是否阻塞主线程？
主线程是否同时有长任务？
RenderThread 是否也被影响？
是否多次复现都一致？
```

证据链要证明顺序和影响，不只是同一时间出现。

## 第二部分：常见误读二：只看平均值

性能体验常常被尾部问题毁掉。

比如：

```text
平均耗时 80ms
```

看起来还行。

但如果：

```text
p95 = 900ms
p99 = 2400ms
```

用户仍然会觉得卡。

观测报告里要尽量写：

```text
平均值
p50
p90 / p95
最大值
异常样本
```

如果没有分布，平均值很容易骗人。

## 第三部分：常见误读三：忽略设备状态

同一段代码，在不同设备状态下表现可能完全不同：

```text
低电量
高温降频
弱网
后台限制
低内存
厂商策略
调试构建
开启录屏或 trace
```

所以报告里要写：

```text
设备型号
Android 版本
App 版本
构建类型
电量和温度状态
网络状态
是否清缓存
是否重启设备
```

没有环境信息，证据很难复用。

## 第四部分：隐私与脱敏

观测文件可能包含敏感信息：

```text
logcat：业务 id、路径、token、手机号
bugreport：设备状态、网络、安装包、系统日志
Perfetto：进程、线程、调度、部分事件名
截图：用户内容
```

分享前要做：

```text
删除无关日志
脱敏用户标识
确认是否允许外发
只保留必要窗口
标注采集时间和目的
```

不要让一次性能排查变成数据泄露。

## 第五部分：证据链报告怎么写

一份好的事故分析报告可以按这个模板：

```text
问题标题：
用户现象：
复现路径：
发生时间：
设备和版本：

第一证据：
  -> logcat / 监控 / 用户录屏

系统状态：
  -> dumpsys / bugreport 片段

时间线证据：
  -> Perfetto / gfxinfo / simpleperf

根因判断：
  -> 为什么这些证据能指向这个原因

修复方案：
  -> 改了什么

回归证据：
  -> 同一复现路径下指标如何变化

残留风险：
  -> 哪些设备或场景还没覆盖
```

报告的目的不是炫工具，而是让团队相信结论。

## 第六部分：团队协作流程

建议团队建立一套小流程：

```text
复现说明
  -> 采集脚本
      -> 文件命名规范
          -> 脱敏检查
              -> 证据链报告
                  -> 修复 PR
                      -> 回归报告
```

文件名可以这样：

```text
2026-08-30_pixel8_android15_course-detail-jank_perfetto.trace
2026-08-30_pixel8_android15_course-detail-jank_bugreport.zip
2026-08-30_pixel8_android15_course-detail-jank_report.md
```

命名清楚，后面复盘会轻松很多。

## 本节自测

- 为什么没有时间点的 bugreport 很难读？
- 为什么平均值不能代表体验？
- 为什么 trace / bugreport 分享前要脱敏？
- 一份证据链报告最少应该包含哪些字段？

## 本节总结

观测工具的终点不是文件，而是团队共识。

真正有价值的证据链应该满足：

```text
可复现
可定位
可解释
可脱敏
可回归
可分享
```

到这里，你已经不仅是在“使用工具”，而是在建立 Android 工程里的事故分析流程。
