# 第26章示例工程：Android 资深工程师毕业项目

这个工程对应课程第 26 章：Android 资深工程师毕业项目：从需求、架构、Framework 到诊断与治理。

它不是一个新的单点实验，而是整门课程的终章工作台。你可以在一个页面里完成课程回顾地图、动手回顾实验室、课程主路径、终章任务板、Framework 因果链、事故剧本、证据时间线、能力雷达、发布门禁和毕业答辩报告。

如果前面的 Demo 是一间间训练室，第 26 章就是最后的毕业考场：读者要在这里重新走一遍前面的能力路线，并用可运行页面、可点击任务、可读证据和可分享报告证明自己真的掌握了。

## 学习目标

运行本工程后，你应该能回答：

- 为什么毕业项目不是功能堆叠，而是需求、架构、系统链路、证据和治理的闭环？
- 如何把前 25 章的能力映射到一个可运行项目里？
- 如何通过课程回顾地图，把第 1 到 26 章重新串成一条能力路线？
- 如何通过动手任务，把“看过知识点”变成“能留下证据”？
- 为什么 Framework 学习不能只背类名，而要讲清因果？
- 如何用 `traceId` 串起点击、ViewModel、Repository、Choreographer 和事故证据？
- 如何模拟课程详情卡顿、后台任务等待、资源错乱、权限降级、签名异常、类加载失败和 release 门禁阻塞？
- 为什么能力雷达应该跟任务、证据和门禁状态动态变化？
- 为什么总分不错，但 mapping 缺失时仍然不能发布？
- 如何用 `Trace.beginSection()`、`Logcat`、`SystemClock.elapsedRealtime()` 和 `BuildConfig` 把 Demo 做出真实工程味道？
- 如何用答辩 Rubric 判断自己是“能跑起来”，还是“能被追问”？
- 一场 10 到 15 分钟的终章答辩应该如何组织，报告又该如何给出补强建议？

## 运行方式

用 Android Studio 打开本目录：

```text
examples/26-senior-android-capstone/
```

等待 Gradle Sync 完成后，运行 `app`。

如果你习惯命令行，并且本机有 Gradle Wrapper 或全局 Gradle，也可以执行：

```bash
./gradlew :app:assembleDebug
```

当前仓库环境没有统一的根 Gradle Wrapper，建议优先用 Android Studio 打开示例工程。

## 实验区域

### 工程快照与真实观察点

第 26 章不是纯 UI 模拟。Demo 会在页面里展示当前工程快照：

```text
applicationId
versionName / versionCode
BUILD_PROFILE
debug
sessionStartMs
```

这些字段来自 `BuildConfig` 与 `SystemClock.elapsedRealtime()`。它们的意义不是炫技，而是提醒读者：真实工程里的每一次诊断，都应该先确认“我观察的是哪个包、哪个版本、哪个构建配置、哪一次会话”。

点击“重新追踪一次点击链路”时，代码会写入：

```kotlin
Trace.beginSection("CapstoneRunTrace")
Log.i("HelloCapstone", "runTrace ...")
SystemClock.elapsedRealtime()
```

点击“注入当前事故证据”时，代码会写入：

```kotlin
Trace.beginSection("CapstoneIncident:<scenarioId>")
Log.w("HelloCapstone", "simulateIncident ...")
```

所以你可以用两种方式观察它：

```text
Logcat 过滤 Tag：HelloCapstone
Profiler / Perfetto 观察 Trace section：CapstoneRunTrace、CapstoneIncident:<scenarioId>
```

这一步把终章 Demo 从“看页面变化”，推进到“看工程证据”。

### 毕业挑战模式

毕业挑战模式把终章体验收束成 6 个关卡：

```text
选定回顾路线
跑一次真实点击链路
注入一次事故
补一条动手证据
修复 P0 门禁
生成答辩材料
```

每个关卡都有目标、完成状态和证据说明。它不会替读者做判断，只会把“下一步该做什么”摆出来。

这能解决一个很现实的问题：终章内容很多，如果没有一条可执行路线，读者容易只是从上往下浏览；有了挑战模式，读者会知道自己还差哪一步才能进入答辩。

### 课程回顾地图

课程回顾地图把整门课重新整理成 6 个阶段：

| 阶段 | 覆盖章节 | 回顾重点 |
| --- | --- | --- |
| 应用基础回顾 | 第 1 到 3 章 | App 如何从能运行，走到能表达页面、状态和导航 |
| 数据与异步回顾 | 第 4 到 6 章 | 数据如何从网络、本地存储和后台任务流向 UI |
| 架构与工程化回顾 | 第 5、7、8、25 章 | 模块边界、依赖方向、测试和治理规则如何保护工程 |
| Framework 主线回顾 | 第 10 到 18 章 | 一次点击如何穿过输入、窗口、渲染、资源和代码加载 |
| 系统诊断回顾 | 第 19 到 24 章 | 进程、后台、存储、安全和观测工具如何组成证据链 |
| 终章答辩回顾 | 第 26 章 | 如何证明自己具备完整交付能力 |

每个阶段都有：

```text
关键问题
动手目标
验收证据
```

这部分是第 26 章 Demo 的总目录。

### 分阶段毕业路线

页面顶部提供 V1 到 V5 的毕业路线：

| 阶段 | 目标 |
| --- | --- |
| V1 主路径可运行 | 课程首页、章节详情、学习进度形成闭环 |
| V2 数据与任务可观察 | 收藏、笔记、离线任务和后台同步能被观察 |
| V3 架构与链路可解释 | 模块边界、数据流和 Framework 因果链能讲清楚 |
| V4 事故可诊断 | 卡顿、后台失败、资源异常和权限拒绝有证据链 |
| V5 发布可治理 | 发布门禁、风险分级、监控基线和答辩材料完整 |

建议先从 V1 开始，不要一上来就追求全部完成。

### 终章任务板

任务板内置 9 个毕业任务：

```text
跑通课程主路径
接入本地状态
讲清模块架构
追踪 Framework 因果链
完成一次事故诊断
观察后台与存储
完成安全检查
完成发版治理
准备终章答辩
```

点击任务可以在这些状态间切换：

```text
未开始
进行中
需要补证据
已完成
```

其中“需要补证据”是本章的灵魂状态。它提醒你：很多工程动作不是没做，而是做了却无法证明。

### 动手回顾实验室

动手回顾实验室把前面的知识变成跨章节任务：

| 任务 | 回顾章节 | 你要做什么 |
| --- | --- | --- |
| 改一个课程状态 | 第 1 到 3 章 | 切换章节，观察 UI 状态和 traceId 变化 |
| 模拟一次后台等待 | 第 4、6、21、22 章 | 注入 WorkManager 约束证据 |
| 讲一次点击的系统因果 | 第 10 到 15 章 | 用“因为...所以...”解释输入、窗口和渲染节点 |
| 补一个资源错乱剧本 | 第 17 章 | 说明 R、AAPT、Theme、Configuration 如何参与 |
| 补一次权限降级体验 | 第 22、23 章 | 设计权限拒绝后的可用路径 |
| 修复一个 P0 门禁 | 第 20、24、25 章 | 解释 mapping 缺失为什么阻塞发布 |

这些任务是精品 Demo 的核心玩法：每个操作都必须对应一个知识回顾点和一个验收证据。

### 课程主路径

Demo 内置了几门关键章节：

| 章节 | 训练重点 |
| --- | --- |
| 第14章 Input 事件分发 | 从一次点击解释输入系统 |
| 第17章 资源系统 | 从主题和资源选择解释 R、AAPT、resources.arsc |
| 第20章 稳定性诊断 | 从 ANR / Crash 进入事故证据链 |
| 第24章 系统观测工具 | 从 logcat、dumpsys、Perfetto 进入系统证据 |
| 第25章 大型工程治理 | 从发布门禁、监控和复盘进入治理闭环 |

切换章节后，页面会更新当前主路径和 traceId。

### Framework 因果链

这一块会展示：

```text
InputDispatcher
ViewRootImpl
ActivityThread
Choreographer
RenderThread
SurfaceFlinger
```

每个节点都回答三件事：

```text
它为什么存在
它解决什么问题
它能留下什么证据
```

终章 Demo 不鼓励机械背源码，它鼓励你把用户现象、系统机制和诊断证据讲成因果链。

### 事故剧本实验区

工程内置七个事故剧本：

| 剧本 | 核心训练 |
| --- | --- |
| 课程详情打开卡顿 | 判断主线程阻塞、帧耗时和本地解析问题 |
| 离线同步迟迟不执行 | 判断 WorkManager 约束、JobScheduler 和后台限制 |
| release 准备发布但被门禁拦截 | 判断 mapping、权限、组件暴露和发布治理 |
| 夜间主题资源错乱 | 判断 R、AAPT、resources.arsc、Theme、Configuration 和资源合并 |
| 权限拒绝后离线导出失败 | 判断权限、AppOps、SAF、系统分享和降级体验 |
| 签名证书指纹异常 | 判断签名证书、升级链路、签名权限和供应链可信度 |
| 动态模块类加载失败 | 判断 ClassLoader、R8、keep 规则、插件 contract 和崩溃证据 |

点击“注入当前事故证据”后，证据时间线会替换成该事故的日志和诊断线索。

同时，Demo 会自动推进相关任务和动手实验状态：未开始会进入进行中，进行中会进入需要补证据，已经完成的任务不会被倒退。例如：

| 注入剧本 | 自动影响 |
| --- | --- |
| 课程详情打开卡顿 | 推进事故诊断、Framework 因果链任务 |
| 离线同步迟迟不执行 | 推进后台与存储、数据异步任务 |
| 夜间主题资源错乱 | 推进资源错乱实验和 Framework 任务 |
| 权限拒绝后离线导出失败 | 推进安全检查、后台与存储任务 |
| 签名证书指纹异常 | 推进安全检查、发版治理任务 |
| 动态模块类加载失败 | 推进发版治理和 Framework 任务 |

这个设计想表达的是：线上事故不是孤立事件。它会立刻改变任务优先级、证据状态和发布判断。

### 复盘问答卡

复盘问答卡用来防止读者只点页面、不做思考。

它会持续追问：

```text
先看业务日志、Perfetto 还是代码？
为什么 Compose Navigation 不能替代 ActivityThread 理解？
为什么 mapping 缺失会阻塞发布？
```

这些问题没有要求读者背答案，而是逼他回到证据、因果和治理。

### 能力雷达

能力雷达包含六个维度：

```text
功能交付
架构设计
Framework 理解
诊断能力
工程治理
表达答辩
```

它不是为了给自己贴标签，而是帮你发现短板。

当前版本的能力雷达已经不是固定分数。它会根据下面这些状态动态变化：

```text
终章任务板状态
动手回顾任务状态
traceId 时间线是否生成
发布门禁是否通过
P0 证据缺口是否清理
```

这意味着读者点任务、补证据、修复门禁之后，顶部能力均分和雷达分数都会跟着变化。

### 发布门禁与毕业结论

Demo 会故意保留一个 P0：

```text
mapping / symbols 未归档
```

所以即使任务完成度和能力均分不低，毕业结论仍然会提示：

```text
暂缓毕业：还有 P0 证据缺口
```

这对应第 25、26 章共同强调的底线：

```text
总分不能掩盖 P0。
```

你也可以点击门禁项切换通过状态。把 P0 修复后，再观察顶部“毕业结论”如何变化，这一步能帮助你理解治理不是静态表格，而是风险状态推动工程决策。

默认门禁中包含两个 P0：

```text
mapping / symbols 未归档
签名证书与历史版本不一致
```

它们都需要补齐证据后，毕业结论才会继续向答辩预演或毕业答辩推进。

### 毕业答辩报告

报告现在会根据当前状态自动生成：

```text
当前结论
工程快照
当前回顾阶段
课程主路径
终章任务板
毕业挑战模式
动手回顾任务

事故剧本
发布门禁
当前最需要补强

```

这份报告不只是结果汇总，它会主动指出最低能力项、未通过门禁，以及答辩时应该优先解释的内容。

### 操作记录与验收轨迹

Demo 会记录最近 12 次关键操作：

```text
切换毕业阶段
选择回顾阶段
打开课程章节
追踪点击链路
选择事故剧本
注入事故
推进终章任务
推进动手实验
切换发布门禁
生成答辩报告
```

这些记录会进入毕业报告。它的作用不是做复杂埋点，而是让读者明白：真实验收不只看“现在是什么状态”，还要看“你是怎么走到这个状态的”。

### 答辩评分 Rubric

Demo 内置了一张从 60 分到 95 分以上的答辩 Rubric：

| 分数 | 标准 | 证据 |
| --- | --- | --- |
| 60 分 | 主路径可以运行 | 能演示首页、章节、详情和进度变化 |
| 70 分 | 架构可以解释 | 能说明 feature / domain / data / core 的职责和依赖方向 |
| 80 分 | Framework 因果链可以讲清 | 能把一次点击追到 Input、ViewRootImpl、ActivityThread 和 Choreographer |
| 90 分 | 事故诊断和发布门禁形成闭环 | 能用证据解释事故，并判断 P0 / P1 是否阻塞发布 |
| 95 分以上 | 具备持续演进和治理意识 | 能提出 CI 门禁、真实 Perfetto、Baseline Profile、DataStore 持久化等后续方案 |

这张表不是为了制造考试焦虑，而是帮读者判断自己已经走到了哪一层。能跑起来是起点，能解释、能诊断、能治理、能演进，才是终章真正想训练的能力。

## 建议玩法

推荐按这个顺序体验：

```text
1. 先在课程回顾地图里选择一个阶段，回答关键问题。
2. 切换 V1 到 V5，理解毕业项目的阶段路线。
3. 点击终章任务板，把部分任务从进行中切到需要补证据或已完成。
4. 在动手回顾实验室里完成一个跨章节任务。
5. 在课程主路径里选择一个章节。
6. 点击“重新追踪一次点击链路”，观察 traceId 时间线。
7. 用 Logcat 过滤 `HelloCapstone`，确认真实日志已经写入。
8. 选择一个事故剧本，注入证据，观察任务状态是否自动变化。
9. 阅读 Framework 因果链，尝试用自己的话解释节点作用。
10. 回答复盘问答卡中的问题。
11. 查看能力雷达，找出最弱的能力项。
12. 查看发布门禁，判断为什么暂缓毕业。
13. 对照答辩 Rubric，判断自己当前能拿出哪些证据。
14. 复制或分享毕业报告。
```

## 进阶练习

- 增加一个“Binder 调用等待导致页面响应慢”的事故剧本，映射第 11、20、24 章。
- 增加一个“多进程状态不一致”的事故剧本，映射第 19 章。
- 把 release gate 的点击结果持久化到 DataStore。
- 把能力雷达分数拆成更细的权重配置。
- 把报告导出为 Markdown 文件或通过系统分享发送。
- 把 `Trace.beginSection()` 产生的 section 导入 Perfetto，并和页面时间线做对照。
- 把 Logcat 中的 `HelloCapstone` 日志导出到事故报告。
- 把答辩 Rubric 拆成可配置评分权重，让不同团队能按自己的标准验收。
